# PD-3056 账户年审提醒邮件与重复触发开发方案

> 状态：需求方案（待产品 / 合规确认未决口径）  
> 日期：2026-11-13  
> 仓库：qbitpay_service

## 1. 目标

账户年审触发时使用新版邮件模板；如果客户在触发后仍未提交年审资料，则在触发后第 15 天、第 27 天各发送一次同一触发邮件。停用本年审流程原有的独立重复提醒邮件，防止客户收到两套重复提示。

邮件中的 `<%日期%>` 固定表示年审首次触发日 + 30 个自然日，即理论冻结日期。当前需求明确的是邮件文案和触发规则；实际冻结、站内通知及其他渠道是否变更仍需确认。

## 2. 现状与代码影响范围

- 新年审 Case 在 `OddAccountReviewService.createNewOddReview()` 中创建，初始状态为 `Processing`，随后调用 `sendOddNotice()` 发送 `Odd_Account_Review_Request`。
- `sendOddNotice()` 对 `Processing` / `Request` 使用同一 `Odd_Account_Review_Request` 模板，并默认创建/更新年审待办。
- `OddAccountReviewService.oddAccountReviewTodoBySchedule()` 会扫描未完成的年审待办并再次调用通知，但当前生产 schedule 未调用该方法。
- 生产任务 `CddSchedule.oddAccountReviewTrigger()` 每日运行 `noticeCustomerByNewOdd()`；后者按 `updateTime` 为 31 天前查询 `Processing` Case，并发送另一模板 `Odd_Account_Review_Notice`。需要确认这是否就是本需求要下线的旧年审提醒。
- `OddAccountReview` 有 `createTime` / `updateTime`，后者会随数据更新而改变，不能作为提醒日期基准。
- 状态包含 `Processing`、`Request`、`Pending`、`AdditionalRecording`、`Closed`、`Passed`。客户首次提交后通常进入 `Pending`；`Request` 可能表示要求补录，单看状态不能区分“从未提交”与“提交后待补录”。
- `SendNotice()` 当前会捕获通知异常但不向调用方抛出，提醒阶段无法根据现有调用可靠区分发送成功与失败。需要为可重试提醒增加能返回明确发送结果的调用路径，或使用通知服务提供的可靠发送队列。

- `src/entity/cdd/odd-account-review.entity.ts`

## 3. 业务规则建议

定义 `createTime` 为年审首次触发时间，提醒日按 Asia/Shanghai 自然日计算：

| 时间点 | 行为 |
| --- | --- |
| D0 | 创建年审 Case 时发送新版 `Odd_Account_Review_Request` |
| D+15 | 若仍未首次提交资料且该阶段未发送成功，发送同一模板 |
| D+27 | 若仍未首次提交资料且该阶段未发送成功，发送同一模板 |
| 提交后 / Case 结束后 | 不再发送未到期提醒 |
| 邮件日期变量 | 始终为 `createTime` 所在自然日 + 30 天 |

建议将“未提交”解释为客户尚未首次提交 KYC/KYB 年审资料。首次提交后即停止该轮提醒；提交后转为 `Request` 补录时也停止。判定依赖现有 CDD 状态/操作日志，需在开发前确认状态覆盖完整。

## 4. 方案选项

### 方案 A：在现有 Case 通知链路增加两次定时提醒（推荐）

保留 `Odd_Account_Review_Request` 为唯一年审触发邮件；复用 Case 的 `createTime` 和既有 `operationLog` 记录 D+15/D+27 发送成功阶段。调度通过 Redis 锁避免并发。停用旧的独立年审提醒调用。

- 优点：提醒时间、Case 状态、提交动作在同一领域内闭环；可通过 Redis 锁防并发，并在现有 `operationLog` 记录发送成功阶段；避免依赖待办状态或会变化的更新时间。
- 代价：需让通知调用返回明确结果；无需数据库结构变更。

### 方案 B：扩展通用待办提醒框架

将 D+15/D+27 配置为通用待办提醒规则，由待办调度统一发送。

- 优点：调度机制可复用。
- 代价：当前年审待办周提醒方法未接入生产调度；通用待办状态不能稳定代表“客户尚未首次提交”；仍需补充模板、幂等和提交状态判断。

### 方案 C：只修改现有提醒阶段

修改当前生产 D+31 检查及模板，尝试让它覆盖 D+15/D+27。

- 优点：改动看起来较少。
- 代价：当前任务基于 `updateTime` 且只覆盖一个时间段，不适合表达两个离散提醒点；另有未接入生产的待办周提醒逻辑，容易造成遗漏或双发。

推荐方案 A。

## 5. 方案 A：详细设计

### 5.1 数据库约束（不新增表、不加字段）

本方案不新增数据库表、不在现有表加字段、不新增 Entity，也不需要数据库 migration。复用现有数据：

- Case 首次触发日使用 `OddAccountReview.createTime`，不使用会变化的 `updateTime`。
- D+15 / D+27 发送成功标记写入现有 `operationLog` 表，使用已有 `businessType = OddAccountReview`、`recordId = oddAccountReview.id` 和 JSON `data.operationType`，分别记为 `AccountReviewReminderD15Sent`、`AccountReviewReminderD27Sent`。
- 客户首次提交判定复用现有 CDD Case 状态和现有年审操作日志，不新增 `firstCustomerSubmitAt` 字段。需在开发前确认现有数据能覆盖首次提交、提交后补录等状态路径。
- 失败原因和阶段写入既有 `operationLog` 失败事件及结构化应用日志；重试次数通过失败事件计数，不加字段。

`OperationLog` 已有 `recordId`、`businessType` 索引及 JSON `data`，可按 Case 查询已发送阶段。新写入仅增加既有 operationLog 表的数据行，不改变表结构。

### 5.2 提醒时间计算

每日调度动态计算到期阶段，不预建提醒任务记录：

- 所有时间判断使用 Asia/Shanghai 自然日；建议在 D+15 / D+27 当天上午 09:00 发送，待产品确认。
- 使用项目现有日期工具显式指定时区，不以固定毫秒数累加天数。
- 邮件日期变量统一由 Case `createTime` 所在自然日 +30 天计算。
- D+15、D+27 的成功与否通过查询既有 `operationLog` 里对应的发送事件判断。

### 5.3 调度与并发控制

新增每日调度入口，例如 `CddSchedule.oddAccountReviewReminderDispatch()`，使用 Asia/Shanghai 时区：

1. 分页查询 `createTime` 已到 D+15 或 D+27 的 Case，过滤已结束的 Case。
2. 对每个 Case 和阶段使用 Redis 分布式锁，锁 key 包含 Case ID 与阶段（例如 `oddAccountReviewReminder:{caseId}:D15`），TTL 覆盖一次通知处理时长。
3. 获锁后重新查一次对应的成功发送日志；已存在 `AccountReviewReminderD15Sent` / `AccountReviewReminderD27Sent` 就跳过，防止重复调度和多实例并发重复发送。
4. 再次校验提交资格；符合条件后发送同一触发邮件。
5. 通知服务确认接受后，立即向既有 `operationLog` 插入发送成功事件，`data.operationType` 使用固定阶段值，并在 `data.params` 记录模板键和日期变量（不写敏感个人信息）。
6. 通知失败时不插入成功标记，写结构化失败日志；释放 Redis 锁，下一次日调度按重试规则再次尝试。
7. 每条 Case 独立处理、分页限流，单条异常不能中断整批。

锁用于抑制并发，operationLog 作为持久化去重依据；锁 TTL 应长于通知调用常规耗时。进程异常退出后锁超时释放，后续调度会检查成功日志再决定是否重试。

### 5.4 发送前资格校验

发送前重新读取 Case、相关 CDD KYC/KYB 记录及年审操作日志，避免调度扫描后客户已提交：

- Case 必须存在且未软删除，且未进入 `Closed` / `Passed` 等终态。
- 按现有 CDD 状态/操作日志判断客户是否已经首次提交；首次提交后停止后续提醒。
- 不应只用 Odd Case 的 `Request` 状态判断是否未提交，因为补录状态需要结合关联 CDD 记录和操作日志确定。
- 确认现有操作日志是否稳定记录 `CustomerSubmitInfo`。若客户首次提交但进入 `Request` 时没有该事件，需要基于关联 CDD KYC/KYB 状态补足判定规则；不得通过新增字段解决。
- 已提交或 Case 结束的记录直接跳过并写结构化跳过日志；未到期或已存在成功发送日志的阶段也跳过。

提交动作与邮件发送可能并发。发送前校验可缩短竞态窗口；若通知服务已接受邮件后客户才提交，邮件无法撤回，需接受此边界并记录时间线。

### 5.5 通知发送与去重边界

D0、D+15、D+27 使用同一个 `Odd_Account_Review_Request` 模板，Case ID、`kyCaseId` 与现有参数保持一致。邮件日期变量由 Case `createTime` 所在自然日 +30 天计算。

当前 `SendNotice()` 会吞掉异常，不能用它判断提醒是否发送成功。需为此提醒增加能返回明确结果的发送入口，检查 `NoticeTemplateV2Service.sendNoticeByTemplate()` 对缺模板、无收件人、API 客户不发送、供应商拒绝等情况的行为，并区分“供应商已接受”“按策略跳过”“发送失败”。发送成功日志表示供应商已接受，不表示最终送达或客户阅读。

成功发送后向既有 `operationLog` 插入阶段标记：`AccountReviewReminderD15Sent` 或 `AccountReviewReminderD27Sent`。每次失败向既有 `operationLog` 写入阶段失败事件（例如 `AccountReviewReminderD15Failed`），记录异常类型和重试序号，不新增字段；按每日调度策略重试，超过上限后停止并告警。

若供应商支持幂等键，使用 `oddAccountReviewId + stage`。若供应商不支持幂等，存在“供应商已接受邮件、进程在写成功日志前崩溃”的小概率重复窗口。仅靠现有表数据无法让外部邮件发送和 operationLog 写入成为同一原子事务；需接受该边界或使用供应商幂等能力。先写成功日志再发送会产生漏发风险，不推荐。

重复提醒只发送模板通知，不重复创建、重置或改变账户待办。可将 `sendOddNotice()` 拆分为“发送模板通知”和“upsert 年审待办”两个职责；D0 保持现有行为。

### 5.6 旧提醒下线

- 停止 `CddSchedule.oddAccountReviewTrigger()` 中对旧 D+31 方法的年审提醒调用，或改为仅保留与本需求无关的行为。
- 如果 `noticeCustomerByNewOdd()` 只服务于这封旧年审提醒，删除生产调用并清理方法；若有手动/测试入口，标记弃用并移除对应误导性注释。
- 不要因本需求删除 `Odd_Account_Review_Notice` 模板枚举或平台配置，先搜索确认所有消费者，再分别处理模板中心下线。
- `oddAccountReviewTodoBySchedule()` 当前不在生产 schedule 中；确认它不是应保留的另一个业务提醒后，将其保持不调度或清理。上线后年审 D+15/D+27 只允许一条提醒链路。
- 对其他 ODD 通知模板和自动冻结任务做回归核查，不改动其行为，除非产品把冻结也纳入范围。

### 5.7 模板和变量

- 更新模板中心 `Odd_Account_Review_Request` 的中文/英文邮件标题、正文。
- 日期变量按实际模板配置字段映射；当前参数 DTO 只声明 `eventData`，需核实模板服务能否从事件参数解码出邮件所需变量。若不能，扩展该模板 DTO 参数并贯通到模板渲染。
- 核实 `verifiedName`、`clientID`、`emailPrefix` 在现有通知模板服务中的公共注入与不同账户语言逻辑。
- 模板所示“7天内完成”与业务日期 D+30 需一致核对。若模板正文同时存在固定 7 天要求，应按最终批准文案统一，不能保留互相矛盾的承诺。
- 如果通知模板会同时产生站内信/推送，须确认本次是否接受重复触发这些渠道；若只要求邮件，需采用邮件专用发送能力或模板渠道配置，不能默认每次 `SendNotice` 都只发邮件。

### 5.8 失败补发、过期和停机恢复

推荐默认策略（待产品确认）：

- D+15 任务当天开始发送；短暂失败按退避策略在后续调度中重试。
- D+27 到期时，如果 D+15 仍未成功且客户仍未提交，跳过 D+15 的过期补发、直接发送 D+27，避免恢复服务时连续收到两封。
- D+27 只在 D+27 至 D+30 冻结日前发送；超过有效期后查询条件自然排除，不补发过期邮件，并记录跳过日志。无需在 Case 上额外保存 Skipped 状态。
- 若产品要求错过提醒也必须补发，可改为两阶段均有效直到 D+30，但要限制同一账户每日最多一封，并确定 D+30 当天的优先级。

### 5.9 可观测性与运维

每次处理记录 Case ID、阶段、资格判定结果、发送结果和耗时；失败次数从 operationLog 统计。日志禁止包含身份证件、完整邮箱等敏感数据。

建议增加指标：
- 到期任务数、成功数、跳过数、失败数；
- 按阶段统计既有 operationLog 中的失败次数、成功数和 Redis 锁冲突数；
- D+15/D+27 发送延迟分布；
- 通知服务拒绝/缺少模板/无收件人的分类计数。

告警至少覆盖持续失败、Redis 锁冲突异常和发送量异常突增。模板中心在生产环境启用前，应先核对模板存在及关键变量可渲染。

## 6. 验收标准

1. 新 Case D0 只发送新版触发邮件，日期变量正确显示为 D+30。
2. 未首次提交 Case 在 D+15、D+27 各收到一次同模板邮件，主题、正文、变量与最终批准模板一致。
3. D+15 / D+27 重跑或多实例并发时，Redis 锁和成功日志可阻止常规重复发送；通知失败可按失败事件计数重试。供应商接受发送后进程崩溃这一边界按第 5.5 节约定处理。
4. 首次提交后不再发送未到期提醒；覆盖提交后转 `Request` 补录的状态路径。
5. 提醒不会重复创建或重置待办。
6. 缺模板、API 客户不发信、无收件人等通知服务结果能被明确分类，不误记为已发送。
7. 旧的独立年审提醒不再发出；其他 ODD 通知与冻结流程不受影响。
8. Asia/Shanghai 自然日计算符合确认的发送时刻；覆盖 D+15、D+27、D+30 边界。
9. 不新增提醒计划记录；到期阶段由每日任务根据 Case `createTime`、CDD 状态和 operationLog 动态计算。为避免误触发存量 Case，建议增加配置化生效时间，仅处理该时间之后创建的 Case。
10. 监控可查询到每个阶段的发送时间、失败次数和跳过/失败原因日志。

## 7. 待产品 / 合规确认

1. **冻结语义：** D+30 是邮件中的理论日期，还是系统实际冻结日？若实际执行，是否纳入 PD-3056，是否与本需求采用同一个 `createTime`？
2. **提交定义：** 客户提交后进入 `Request` 补录时，是否停止 D+15/D+27 提醒？建议按首次提交时间停止。
3. **执行时刻：** D+15 / D+27 发送日的具体时刻是否为上海时间上午 9 点？
4. **停机补发：** 错过 D+15 后 D+27 已到期时，是否跳过旧阶段，只发 D+27？超过 D+30 是否停止补发？
5. **发送渠道：** 表格中通知标题/内容等是否一并更新？重复触发当前模板会触发哪些渠道？
6. **存量范围：** 新规则只对上线后的 Case 生效，还是需要回填尚未提交的存量 Case？
7. **“7天”文案：** 新模板中的 7 天提示是否需改为与 D+30 冻结日期一致？最终模板以哪一列/版本为准？

## 8. 实施任务拆分

### 后端

1. 不需要数据库 migration；复用现有 `operationLog` 写入发送成功/失败标记，不修改数据库结构。
2. 复用 Case 已有 `createTime` 作为基准，不新增触发时间列，也无需创建提醒任务记录。
3. 核实并复用现有 CDD 状态和年审操作日志判断首次提交，不新增字段。
4. 实现现有 Case 查询、资格校验、Redis 并发锁、operationLog 成功/失败事件去重和严格发送结果。
5. 拆分 Case 通知发送与待办 upsert，确保重复提醒不会重置待办。
6. 接入独立定时调度，分页限流，单条异常隔离。
7. 停用旧 D+31 年审提醒和确认不应启用的待办周提醒入口。
8. 增加日志、指标及失败/堆积告警。

### 模板与配置

1. 更新 `Odd_Account_Review_Request` 邮件中英文标题/正文。
2. 明确日期占位符映射到 Case `createTime + 30 天`。
3. 检查多语言、账户名称、clientID、签名和邮件渠道配置。
4. 如模板中心配置需人工发布，制定配置发布与后端部署顺序，避免先发送后模板未更新。

### 验证与发布

1. 覆盖 D0、D+15、D+27 和各状态变化的服务层场景。
2. 覆盖并发领取、重复调度、发送超时、发送失败重试、发送成功后进程崩溃的幂等边界。
3. 覆盖历史 Case、停机恢复和模板缺失。
4. 先在测试环境验证模板渲染与邮件内容，再灰度启用调度。
5. 灰度观察提醒数量、失败率和状态分布；确认无双发后扩大范围。
6. 回滚时先关闭提醒调度，再回滚应用；operationLog 中已记录的成功标记保留，避免旧逻辑重复发送。

## 9. 仍需技术确认

- Redis 锁的现有调用方式、TTL 和任务超时策略。
- 邮件供应商是否支持幂等键，以及 `sendNoticeByTemplate()` 返回值能否表示“供应商已接受发送”。
- 模板引擎日期参数的格式、时区和转义规则。
- CDD 首次提交事件是否能在状态更新事务内可靠记录，不得通过新增字段解决。
