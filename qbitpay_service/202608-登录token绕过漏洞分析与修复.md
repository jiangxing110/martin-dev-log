# 2026-08 登录漏洞修复记录（token绕过）

## 一句话说清楚这个漏洞

**只要拿到一个没过期的"登录凭证"（token），不用输入账号密码、不用验证码，就能随便换新的登录凭证，想换多少换多少。**

打个比方：就像你家的门禁卡丢了，捡到的人不用知道你家密码，也不用按指纹，只要拿这张卡在门上一刷，就能再配一把新钥匙，然后一直拿新钥匙进进出出，永远也不需要真正的密码。

---

## 1. 漏洞基本信息

| 项目 | 内容 |
|---|---|
| 漏洞名称 | 登录时用token绕过账号密码校验 |
| 危险程度 | 中等 |
| 出问题的地方 | `https://global.service.test.qbitnetwork.com/auth/login`（登录接口） |

---

## 2. 攻击者是怎么做到的（大白话版）

- 正常登录要：输账号 + 输密码 + 输验证码，才能换到token。
- 但这个接口有个"后门"：**只要请求里带上一个还没过期的token，系统就以为"你已经登录过了"，于是跳过账号密码，直接给你一个新token。**
- 攻击者只需要偷到一个token，就能反复刷新token，永远不会失效，等于永久的控制权。

---

## 3. 到底哪个代码出错了

这个"带token就跳过账号密码"的逻辑，**写在所有登录接口共用的底层认证策略里**，所以不只是 `auth/login`，`acquiring/login`（收单机构）、`admin/login`（后台）这几个登录接口**全都受影响**（`admin/login` 因为额外多了谷歌验证码，稍微安全一点点）。

漏洞实际有**两层**：

### 第一层：跳过账号密码（真正的开关）

文件：`src/common/special-modules/auth/strategies/local.strategy.ts`

**第 59 行** —— 判断请求里带的token是否有效（没过期）：
```typescript
const useJWTLogin = token && this.authService.verifyJwt(token);
```
只要token签名验证通过（没过期），`useJWTLogin` 就变成 `true`。

**第 71-76 行** —— 真正绕过账号密码的地方：
```typescript
if (useJWTLogin) {
  const jwtData = this.authService.decodeJwt(token) as JwtData;
  return this.authService.jwtLogin(jwtData, headers, realIp);  // 直接用token里的用户信息返回
}
const productLine = this.authService.getProductLineByReq(req); // 只有没带token才走到这里
```

**关键在 local.strategy.ts:71 的 `if (useJWTLogin)`。** 条件一成立，就直接用token里的用户信息放行了，`account` 账号和 `password` 密码根本不会被验证。

### 第二层：跳过验证码

文件：`src/common/special-modules/auth/auth.service.ts`

**第 112-114 行** —— 再判断一次token：
```typescript
const token = jwtFromRequest(req);
const useJWTLogin = token && this.verifyJwt(token);
```

**第 146-153 行** —— 有token就跳过验证码：
```typescript
if (!useJWTLogin) {
  await this.checkCode(user, loginDto, req);  // 没token才校验验证码
  ...
} else {
  const payload = (await this.decodeJwt(token)) as JwtData;
  role = payload.role;  // 有token，直接跳过验证码
}
```

### 一句话总结

**local.strategy.ts:71 的 `if (useJWTLogin)` 是"跳过账号密码"的真正开关**，而 `useJWTLogin` 在 **第 59 行**由 `token && this.verifyJwt(token)` 决定 —— **只要请求带的token能通过签名验证（没过期），就跳过账号密码放行**，攻击者的目的就达成了。`auth.service.ts:112-153` 是第二层同样逻辑，负责跳过验证码。

## 4. 怎么修复（方案对比）

讨论时想到过几种修法，并实地核对了既有代码，列在下面对比一下，方便决策。

### 补充分析：`jwtLogin` 现有校验 vs 漏洞缺口

深入查了 token 登录真正落地的 `jwtLogin` 方法（`auth.service.ts:225-254`），它**已经做了一部分校验**：

| 检查项 | 代码位置 | 说明 |
|---|---|---|
| token里的userId对应的用户**在库里真实存在** | 227-231 | `userRepo.findOne({id})` |
| token里的account与库中用户手机/邮箱**是否匹配** | 233 | `user.phone===account \|\| user.email===account` |
| token里的accountId与该用户的accountUser**是否匹配** | 234-242 | 不一致则拒绝 |

**所以伪造的、对不上数据库的token在 `jwtLogin` 就已经被挡住了（抛1001）。**

**但它漏掉的正是漏洞本质 —— 第233行只拿token里的account和库里比对，从没和"本次登录输入的账号"比对：**
```json
{"account":"account","password":"pwd"}
```
攻击者带一个**真token**（如 `+8617639370503`）走 `jwtLogin`：token里的account在库里匹配通过，而输入的假账号**根本没人管** → 直接放行、发新token。

### 方案A：登录接口直接拒收token（曾推荐，但不可行❌）

**思路：登录接口只要带了token就拒绝，一律走账号密码。**

**不可行原因（重要的业务约束）：** "带token直接登录"是**历史遗留的既有业务功能**，不是独立bug。git历史显示该分支早在 #171（"All in 3.0 qbit card"）就存在，`local.strategy.ts:43` 注释也写明"支持直接传入2.0系统的JWT来登陆"。说明确有调用方依赖它。直接删掉、或一律拒收token，会**破坏既有业务**。所以不能采用。

### 方案B：保留token登录，但校验"token身份 == 本次输入账号"（新方向，待评估✅/⚠️）

**思路：在token登录分支里，把"token承载的身份"和"本次登录输入的账号"做比对，二者不一致就拒绝。**

- ✅ 既有"带token登录"业务不破坏（token和输入账号匹配时照常）
- ✅ 攻击者拿**别人的**token、输入**假账号** → 两者对不上 → 被挡

**关键待确认点：** 既有"带token登录"的正常调用方，请求里传的 `account` 字段，**是否等于token里的account？** 如果相等，那么加"输入账号==token账号"这道比对不会误伤正常调用；如果既有调用的 account 字段是空的或不同的，加了就会把正常业务也挡掉。**这一点需要在实现前向相关方核实。**

以此为依托，实修落点有两个选择：
1. 在 `local.strategy.ts:71` 的 `if (useJWTLogin)` 分支里，用本次请求的 `account` 与 `jwtData.account` 比对；
2. 在 `auth.service.ts:225` 的 `jwtLogin` 入口增加同样比对（对整个调用链生效）。

### 方案C：校验token后再要求二次验证

思路：`verifyJwt` 只验证了"卡是真的"，要再验证"你是不是卡主人"（输账号密码/验证码）。比方案B更严格，但改动更大、更复杂，且同样要面对"既有业务是否传账号"的问题。

### 方案对比小结

| 方案 | 思路 | 能否彻底堵住 | 改动量 | 可行性 |
|---|---|---|---|---|
| A | 登录一律拒收token | ✅ 能 | 小 | ❌ 破坏既有"带token登录"业务 |
| B | token身份与输入账号比对 | ⚠️ 单独用不够 | 中 | ✅ 方向可行 |
| C | token + 二次验证 | ✅ 能 | 大 | 备选 |

**最终方案（在B上加强，落实现代固定）：** 保留token登录分支，但带token时强制同时满足以下三条，任一不满足即拒绝：
1. **token身份 == 本次输入账号**（挡住"拿别人的token、输别的账号"）
2. **本次输入的密码正确**（挡住"真账号+假密码" → 用 `findUsers({value, password, type:'login'})` 验证，且校验命中的用户id与token一致）
3. token本身仍须通过签名验证（`useJWTLogin`，原本就有）

这样既保留既有"带token登录"正常业务（账号密码都对得上时照常），又堵死了泄露token被用来无限换新token的漏洞。

**疑似重复校验点（后续可简化）：** 仓库里 `user.service.ts:4430-4448` 的 `checkAccount` 已存在类似的"token对应账号 == 输入account/user"校验，且它只比对手机/邮箱、不校验密码。新增逻辑与之处在同一目标下，可后续评估是否合并。

## 4.5 顺带发现：单token机制早已存在，但被"角色继承+例外"钻了空子

在核对方案时发现，系统其实**已经有"一个账户同时只能用一个token"的机制**，只是没能在登录换token时拦住攻击者。

### 已有的单token机制（两个环节）

| 环节 | 位置 | 说明 |
|---|---|---|
| 写入 | `user.service.ts:4951-4974` `cacheToken()` | `signJwt` 发新token时，覆盖写入 Redis `USER_SESSION:<userId>`（单一key，天然"后token覆盖前token"） |
| 校验 | `session.guard.ts:56-64` `SessionGuard` | 每个请求强比对 Redis里存的token == 请求带的token，不一致 → 401 踢下线 |

**理论上**：`auth/login` 每次发新token都会覆盖Redis里的旧token → 上一个是"失效"的。

### 为什么漏洞报告说"获取一次，上一个不失效"——两个破绽

**破绽1：`Qbit`/`Temporary` 角色不参与单token机制**
- `cacheToken` 例外（user.service.ts:4952-4955）：role为 `Qbit`/`Temporary` 时**不写Redis**
- `SessionGuard` 例外（session.guard.ts:53）：token里role为 `Qbit`/`Temporary` 时**跳过Redis比对**

**破绽2：`auth/login` 会"继承攻击者token的role"**
- `auth.service.ts:150-152`：登录时 `role = payload.role`，即**用攻击者带来的token里的role去签发新token**
- 于是：只要攻击者拿一个 role 是 `Qbit`/`Temporary` 的token走登录接口，新token也不写Redis → 单token校验形同虚设 → 旧token永不失效

> 报告示例token的role是 `"Admin"`（普通角色会写Redis），所以单token机制对它本应生效；但攻击者换一个 `Qbit`/`Temporary` 角色的token，即可完全绕过"上一个失效"。

### 单token机制与已用方案的关系

- 已实现的**方案B（账号密码强校验）已经堵死了 `auth/login` 凭token换token这条路径**，能独立修好当前漏洞。
- "单token彻底化"（修补 `role` 继承 + `cacheToken` 例外）是**更强的一层加固**，能同时修复"旧token不失效"这个报告点名的危害。

**当前决策：** 保留已实现并验证过的方案B作为本次修复；将"单token彻底化"列为**后续加固项**（改动面涉及角色继承与缓存例外，需单独评估，避免影响 `Qbit`/`Temporary` 相关既有流程）。

## 5. 改成这样之后的效果

| 情况 | 之前 | 修复后 |
|---|---|---|
| 带token，账号==token账号，密码正确（正常业务） | 放行 | 放行 ✅ |
| 带token，账号==token账号，但密码假（攻击者） | 放行（漏洞） | 拒绝 ❌ |
| 带token，输别人的/假账号 | 放行（漏洞） | 拒绝 ❌ |
| 不带token，正常输账号密码 | 正常发token | 正常发token ✅ |
| 其它登录入口（admin登录等） | 不受影响 | 不受影响 ✅ |

---

## 6. 怎么验收（怎么算修好了）

1. 带token，账号==token账号，密码正确 → 正常登录（既有业务不受影响）
2. 带token，账号==token账号，**密码错误** → 拒绝，拿不到新token（堵死"真账号+假密码"）
3. 带token，输的是**别的/假账号** → 拒绝，拿不到新token
4. 不带token，正常输账号密码+验证码 → 正常登录
5. 其它登录接口（比如admin登录）→ 跟以前一样正常
6. 拿个假token去碰运气 → 被挡下来
