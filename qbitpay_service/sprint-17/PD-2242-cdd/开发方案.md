# PD-2242 / PD-1999 CDD 品牌名（DBA）采集与搜索增强开发方案

## 1. 需求结论

本需求不是单纯给 Admin 列表增加两个输入框，而是一次“品牌信息统一采集、按账户汇总、跨来源同步、列表检索”的数据链路改造。需求文档明确了三项工作：

1. 在商户端和 Admin 端新增非必填的品牌名/DBA，多品牌最多 10 个，单个品牌最多 128 个字符，重复值剔除。

## 3. 推荐架构与数据模型

### 3.1 推荐方案：账户维度统一品牌表 + 统一可检索字段

明确结论：品牌名/DBA 新增到一张账户维度的品牌明细表 `account_brand_name`，不要直接加在单条 KYC 或 KYB 记录上。官方网站不新增重复来源字段，继续读取现有来源字段，并在客户信息汇总表中维护统一查询值。

推荐为账户建立独立的品牌记录表，而不是把多个品牌拼接到一个字符串字段中：

```text
account
  └── account_brand_name
        account_id
        brand_name
        source_type       -- KYC / KYB / API_COMPLIANCE / ADMIN
        source_id         -- 来源记录 id
        normalized_name   -- 去前后空格后的名称，用于去重
        created_at
        updated_at
        delete_time
```

结合 qbit-assets 当前使用的 `BaseV4`（`Long id`、`version`、软删除时间）和账户表字段类型，实际落地结构如下：

```sql
CREATE TABLE account_brand_name (
    id BIGINT PRIMARY KEY,
    remarks VARCHAR(500),
    account_id VARCHAR(64) NOT NULL,
    brand_name VARCHAR(128) NOT NULL,
    normalized_name VARCHAR(128) NOT NULL,
    source_type VARCHAR(32) NOT NULL,
    source_id VARCHAR(64),
    created_by VARCHAR(64),
    updated_by VARCHAR(64),
    create_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    delete_time TIMESTAMP NULL,
    version INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX idx_account_brand_name_account_id
    ON account_brand_name (account_id)
    WHERE delete_time IS NULL;

CREATE INDEX idx_account_brand_name_normalized
    ON account_brand_name (account_id, normalized_name)
    WHERE delete_time IS NULL;

CREATE UNIQUE INDEX uk_account_brand_name
    ON account_brand_name (account_id, normalized_name)
    WHERE delete_time IS NULL;

-- 数据量较大且需要包含匹配时启用 pg_trgm 后创建
CREATE INDEX idx_account_brand_name_search
    ON account_brand_name USING gin (brand_name gin_trgm_ops)
    WHERE delete_time IS NULL;
```

字段约定：`brand_name` 保存实际展示名称并保留大小写；`normalized_name` 保存 trim 后转小写的值，用于同一账户内去重；`source_type` 取 `KYC`、`KYB`、`API_COMPLIANCE`、`ADMIN`；`source_id` 保存来源记录 ID，便于来源修改或删除；`delete_time` 按项目规范实现软删除。`account_id` 和 `brand_name` 不应设置物理外键约束，遵循现有数据库规范。

品牌最多 10 个是账户维度、跨来源的业务规则，不能只靠上述唯一索引实现。保存服务必须在事务中查询当前有效品牌数量，合并本次变更后去重，再在超过 10 个时整体回滚并返回“品牌数量超限，保存失败”。

品牌表建议放在 `/Users/martinjiang/IdeaProjects/qbit-assets/qbit-core` 对应的账户/客户数据模块中；当前建表和回填脚本统一放在需求目录，发布时从以下路径执行：

- [account_brand_name.sql](/Users/martinjiang/VsCodeProjects/martin-dev-log/qbitpay_service/sprint-17/PD-2242-cdd/account_brand_name.sql)：建表、索引和唯一约束。
- [account_brand_name_backfill.sql](/Users/martinjiang/VsCodeProjects/martin-dev-log/qbitpay_service/sprint-17/PD-2242-cdd/account_brand_name_backfill.sql)：API 合规历史品牌名回填；回填 ID 为基于来源信息生成的稳定正数，不使用负数临时 ID。

如果品牌录入逻辑最终由 `qbitpay_service` 管理，则由该服务维护同等结构，并通过内部接口或消息同步给 qbit-assets，不能让两个服务各自维护一套品牌表。

同时在“用户全量信息”所依赖的账户扩展/客户汇总表中保存可直接分页检索的汇总字段：

- `brand_name_dba`：展示值为 `account_brand_name` 去重后的品牌名数组；qbit-assets 列表 VO 和 CDD GraphQL 均直接返回数组，品牌查询实际通过品牌明细表 `EXISTS`，避免列表联表造成分页重复。
- `official_website`：账户维度统一官方网站，保留原始 URL 字符串；该字段属于客户信息汇总字段，不替代 `CddCompanyBusinessInformation.websiteUrl`、API 合规表中的 `url`。

理由：品牌来自 KYC、量子卡 KYB、全球账户 KYB、API 合规打标等多个来源，需求又要求每个页面展示客戶全部品牌；使用来源记录直接拼接会造成分页重复、删除困难、超过 10 个无法原子校验，也无法正确处理修改和重复。独立记录表可以统一做去重、上限校验、审计和 SQL `EXISTS` 模糊查询。

如果 qbit-assets 已存在等价客户扩展字段或汇总表，应复用已有客户信息表，只新增 `account_brand_name` 明细表和缺失的 `brand_name_dba`/`official_website` 汇总字段；不要新建第二套同语义字段。最终表名以实际数据库命名规范为准，推荐 `account_brand_name`，客户信息汇总表沿用现有表名。

### 3.2 字段规则

- `brand_name_dba` 为非必填；空字符串按无值处理。
- 单个品牌 trim 后长度不得超过 128；最多 10 个有效、去重后的品牌。
- 去重建议使用 `trim + lower` 作为 `normalized_name`，展示保留第一次录入的原始大小写。
- 同一账户同一来源记录重复品牌不重复保存；不同来源出现同名品牌也只展示一次，但保留来源记录以支持来源修改/删除。
- 超过 10 个时整个保存失败，返回“品牌数量超限，保存失败”，不能静默截断。
- 品牌修改必须记录操作人、时间、修改前后值；沿用现有 Admin 操作日志能力。
- 纯文本模糊搜索使用 PostgreSQL `ILIKE '%keyword%'`，参数必须绑定，不能字符串拼接。

### 3.3 官方网站统一口径

推荐新增账户维度官网汇总值，来源优先级如下：

1. Admin/API 合规打标中的 `url`（后续修改实时覆盖对应来源）。
2. `CddCompanyBusinessInformation.websiteUrl`。
3. 当前有效 KYC/KYB 详情中 `key = 'website'` 的值。

若业务确认一个账户需要展示多个官网，应与品牌一样建立 `account_official_website` 明细表；本需求文字只要求一个“官方网站”搜索字段，第一期按账户汇总文本实现，保留向多值扩展的接口边界。

## 5. 测试方案

### 单元测试

- 品牌输入为空：保存成功且不阻塞注册。
- 单项 128 字符通过，129 字符失败。
- 10 个品牌通过，11 个品牌失败；跨 KYC/KYB/API 来源合计超过 10 个也失败。
- 同名品牌大小写/前后空格重复时只保留一个展示值。
- 修改/删除来源数据后，账户汇总立即反映最新结果。
- 官网与品牌单独、组合过滤均生效；空过滤不改变旧查询结果。

- CDD 3.0：验证 `total` 与 `data` 一致，重复品牌记录不会造成 Case 重复。
- 用户全量信息：验证第 1 页、第 2 页结果都满足筛选条件，证明不是分页后内存过滤。
- API 客户主列表、子客户查询、子客户审核：验证 CAAS/BAAS 多来源品牌均可命中，`accountId` 预筛为空时返回空页且 total 为 0。
- 历史回填重复执行两次，结果不增加重复记录。
- 增量修改在事务提交后可查询到；事务回滚时列表不出现半成品数据。

## 6. 发布与数据风险

1. 先发布表结构和回填程序，再发布读路径；读路径上线前确认旧数据无字段时仍保持原结果。
2. 回填先 dry-run，输出超限和来源冲突清单，确认后分批执行。
3. 增量同步先灰度一个环境，监控消息积压、失败重试、品牌数量超限和列表查询耗时。
4. 对品牌/官网模糊查询评估索引：普通 `ILIKE '%x%'` 无法有效使用 B-tree，数据量较大时为 `brand_name`、`official_website` 增加 `pg_trgm` GIN 索引；上线前用 `EXPLAIN ANALYZE` 验证。
5. 不允许把需求中示例 curl 的 Authorization、fingerprint、nonce、sign 等凭证写入代码、脚本或日志；测试请求使用测试环境临时凭证并在共享文档中脱敏。
