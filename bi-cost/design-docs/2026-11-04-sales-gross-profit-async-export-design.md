# 销售毛利看板异步导出设计

## 摘要

将销售毛利汇总、明细两个导出接口改为后台异步生成文件，并在完成后通过 WebSocket 通知当前用户。导出数据覆盖当前筛选条件命中的全部记录，不受页面当前页码和分页条数影响。

## 意图与范围

- 汇总和明细导出均使用请求中现有的筛选条件。
- 忽略分页游标，导出全部匹配数据；沿用 CSV Handler 循环分页读取。Handler 请求每页 2,500 条，但查询服务将 page size 上限归一为 500，因此实际每次查询最多返回 500 条；保留该查询分页上限，不扩大普通分页接口。
- HTTP 请求快速返回受理结果；后台循环分页并将所有结果合并成一个 CSV，不压缩为 ZIP。
- 文件生成后，使用项目现有 `AbstractReportHandler.notifyExport` 流程向发起用户推送一次下载通知；空结果生成仅含表头的文件。
- 文件名以 `userId_yyyyMMddHHmmss` 开头，并保留报表类型、月份和明细 saleId。
- 查询请求不再接受 `provider`、`metricCode` 两个明细筛选字段；它们仍可作为明细结果列返回。
- 保留两个分页查询接口及其响应行为，不改查询 SQL、数据口径和权限范围。

## 当前实现与约束

- `SalesGrossProfitController` 的两个导出端点目前返回文件 URL 列表。
- 两个 CSV Handler 在后台按每页 500 条循环读取所有分页，将全部记录暂存后写入一个 CSV；流程参考自然人黑名单导出。
- 导出服务依赖 `UserContext` 解析数据权限。异步线程必须显式传递并设置发起用户上下文，任务结束时清理上下文。
- 销售毛利代码位于 `qbit-assets` 仓库；本设计记录位于 `bi-cost` 笔记仓库。

## 方案比较

1. **同步返回 URL 列表**：改动最小，但请求需等待完整导出，与用户提供的账单 CSV 接口行为不一致。
2. **异步分页读取并生成单个 CSV（采用）**：沿用黑名单导出“取完筛选结果、生成一个文件、完成后通知”的模式，接口快速返回且用户只收到一条下载通知；实现简单并且不需要 ZIP。代价是写文件前需要将全部结果暂存在内存中，后续如数据量增大可改为流式写入。

采用方案 2，以符合黑名单导出的单文件异步通知模式及用户给出的 `downloadStatementCsv` WebSocket 交付方式，并按用户要求保留 CSV、不打 ZIP。

## 交付与验证

- 修改汇总、明细两个导出入口及其异步编排逻辑；分页查询接口保持不变。
- 不改变查询条件和权限规则；导出覆盖条件命中的所有数据。
- 不运行编译，按用户此前要求进行源码检查与 `git diff --check`。
- 不提交或推送代码。

## 待实现细节

- 在请求线程校验条件并捕获当前用户；异步任务恢复 `UserContext` 后逐页生成 CSV，每个数据库分页最多读取 500 条。
- 所有分页写入一个 CSV 并推送一次下载链接；无记录时生成表头文件；任务异常时发送失败通知并记录异常。
- 文件名保留汇总/明细类型、结算月、明细 saleId，并以 `userId_yyyyMMddHHmmss` 开头；CsvService 为存储路径追加唯一时间戳。
