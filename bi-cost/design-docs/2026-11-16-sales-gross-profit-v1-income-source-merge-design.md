# 销售毛利 V1 收入及调账来源补齐设计

## 摘要

将 V2 增加的三类来源合并到现有销售毛利 V1：Open API 月账单收入、量子卡渠道返现收入、`ods_bi_month_tag` 月度收入/返现调整。V1 的成本来源和日归属保持不变，尤其 IQ 成本仍按上游已处理好的日数据直接汇总，不复制返佣视图的月度销售成本分摊。

## 意图与范围

- 修改现有 `dws.mv_sales_gross_profit_recent_estimate` 定义，不创建 V2 物化视图。
- 将三类新来源加入 V1 既有 `all_rows` 聚合流程，继续使用 V1 已有派生公式和输出结构。
- 月账单/API 与 BI 月度调账按业务月份 1 日作为 `report_date`；不伪造日分布。
- 渠道返现沿用来源 `report_date` 和 `sale_id`，按来源日加入收入。
- 调账收入按 tag 符号映射到收入，返现调整映射到客户返现；保留有符号金额。
- 保持 V1 按日成本归属；BB `volume_fee_cost` 直接取上游已分摊到日的字段，不在视图中重复计算月度阶梯费。
- 不改快照表或刷新任务；不改数据表结构。

## 现状与依据

- V1 已有日指标收入、月账单应收、渠道原始日成本及 IQ 日成本来源。
- V2 相对 V1 新增 `monthly_api_income_rows`、`qbit_card_channel_rebate_rows`、`bi_month_adjustment_rows` 三个 CTE，并在 `all_rows` 中 UNION。
- V2 同时变更了 DWM 成本日期逻辑；该成本改动不合并。用户确认成本已在上游处理到日期粒度，毛利视图应直接按日、销售归属汇总，不做二次分摊。
- BB 附件的客户成本明细从 `dws_bb_card_finance_daily_v2_p.volume_fee_cost` 取已处理的日成本；V1 目前重新按月度阶梯费率计算该项，需切换为直接读取列值。

## 方案比较

1. **新增独立 V2 视图**：可以并行验证，但维护两份逻辑并要求后续消费者切换；用户已明确选择修改现有 V1。
2. **把 V2 三类收入/调账来源并入 V1（采用）**：直接补齐当前使用视图的收入覆盖，避免消费者切换；成本与 V1 现有口径保持稳定。

采用方案 2，范围由用户明确选择为把 V2 新增来源合入 V1。

## 约束与风险

- `offline_api_income_amount` 与已有 `dws_sales_metric_daily` 收入指标必须避免重复计入；迁移前核对 metric code 和产品口径。
- BB/QI/BZ 渠道返现作为收入来源加入；按每日源数据和销售 ID 聚合，保留负值，不使用 `ABS`。
- BI 月度调账仅处理 V2 当前列出的 tag；业务月首日作为日期，销售归属按调账业务时间匹配有效账户销售关系。
- 不改变 V1 输出列、派生毛利公式及其他 provider 成本算法；IQ 成本仍保留日归属。佣金视图 `cogs` 的月度销售权重分摊不引入毛利视图。
- BB `volume_fee_cost` 使用成本源列直接按日汇总，移除视图侧月度阶梯费重算，避免重复处理。

## 评审重点

- 是否确认三类来源和 V2 当前的 tag 映射全部迁入 V1。
- `offline_api_income_amount`、渠道返现与现有收入/返现指标之间不存在重复计数。
- 月度来源统一按业务月份 1 日记入 V1 的日粒度结果。
