# 销售佣金发薪看板开发文档

## 1. 文档目标

本文档用于指导销售佣金发薪看板的前后端、数据任务和权限开发。

关联需求文档：

- [销售佣金发薪看板需求文档](销售佣金发薪看板需求文档.md)

关联示意图：

- [销售佣金仪表盘原始月份翻译版](销售佣金仪表盘原始月份翻译版.png)

## 2. 功能范围

本期只做一个销售佣金页面，不做团队聚合页、不做部门汇总页。

不同角色通过同一页面顶部筛选器查看不同销售 / AM 的数据：

| 角色 | 页面范围 | 是否聚合 |
|---|---|---|
| 销售 | 只看自己 | 否 |
| AM | 只看自己 | 否 |
| 销售主管 | 可筛选自己及下属销售 / AM | 否 |
| 超级管理员 | 可筛选部门及部门下销售 / AM | 否 |

页面包含两个主要数据区：

| 页面区域 | 作用 |
|---|---|
| 我的钱包 | 展示已结算、已回款、可发薪的数据 |
| 我的绩效 | 展示活动月份绩效，以及后续发薪管道 |

## 3. 核心时间规则

### 3.1 发薪规则

发薪日期固定为每月 12 号。

```text
结算月份 M
-> M+1 月 8 号生成快照
-> M+1 月 12 号发薪
```

示例规则：

```text
2026年4月结算数据
-> 2026年5月8日生成快照
-> 2026年5月12日发4月实时回款佣金
```

原图还包含一个发薪管道示例：

```text
2026年4月 API 月账单
-> 2026年5月20日到期回款
-> 2026年5月结算
-> 2026年6月12日发佣金
```

### 3.2 数据起始月份

上线展示数据从 `2026-06` 开始；本文接口样例沿用示意图中的 `2026-04` 数据，方便和图片逐项对照。

前端和后端都要限制：

```text
settlement_month >= '2026-06'
```

示意图中的 `2026-04` 仅作为开发联调样例，不代表生产可查询起始月份。

历史事件可以记录在底层表，但接口不返回 2026 年 6 月以前的展示数据。

### 3.3 快照规则

每月 8 号跑数并固化快照。

8 号前后查询规则：

- 8 号前：页面查询近三个月佣金预估物化视图，金额允许随半天刷新变化；
- 8 号当天：先刷新近三个月佣金预估物化视图，再把目标结算月份写入佣金快照；
- 8 号后：钱包区和已结算口径只查询 `sales_commission_snapshot` 与 `sales_commission_snapshot_detail`，不再查询每日刷新过程表；
- `dws_sales_revenue_monthly` 是每日刷新过程表，不具备历史结算冻结能力，不能作为 8 号后的发薪回看数据源。

快照生成后：

- 金额不再因为源数据变化而重新计算覆盖；
- 页面回看历史月份时读取快照表；
- 8 号快照生成后，我的钱包区域只查询快照主表和快照明细表，不再实时查询收入、成本、回款等源数据；
- 快照只记录 8 号当天给财务使用的返佣金额和组成细节；
- 本报表不处理调账、扣减和财务发薪审批；
- 页面发薪状态根据结算月份推导出的发薪日期和当前日期自动判断，不需要在快照表维护状态。

### 3.4 示意图月份基准

开发文档中的接口样例和金额示例以原图月份为准：

| 图中位置 | 月份 / 日期 | 说明 |
|---|---|---|
| 数据筛选 | 2026年4月（已结算） | 当前查看的结算 / 活动月份 |
| 我的钱包 | 5月12日发放 | 展示 4 月结算后进入 5 月 12 日发薪的数据 |
| 已回款毛利明细 | 3月实时处理费、2月账单及条件拒付、1月逾期发票 | 这些是进入当前钱包发薪批次的历史回款来源 |
| 我的绩效 | 4月1日 - 4月30日活动 | 展示 4 月活动绩效 |
| 下一次发薪 | 5月12日 | 4 月实时回款费用进入 5 月 12 日发薪 |
| 未来发薪 | 6月12日 | 4 月 API 月账单在 5 月 20 日到期回款，进入 6 月 12 日发薪 |

## 4. 计算口径

### 4.1 主链路

```text
Real-time processing
- Client Rebate
= Effective Revenue

Effective Revenue
- COGS
= Gross Profit / GP

GP × Commission Rate
= Commission
```

### 4.2 明细行计算

```text
commission_base = gp
commission_amount = commission_base × commission_rate
```

API 费用存在特殊口径时：

```text
commission_base = api_actual_fee
commission_amount = api_actual_fee × api_commission_rate
```

### 4.3 快照佣金金额

```text
total_commission = SUM(snapshot_detail.commission_amount WHERE commission_stage = 'current_payout')
```

本报表不做调账和扣减，因此页面展示的实际发佣金合计直接使用：

```text
snapshot_commission_amount = total_commission
```

### 4.4 饼图数据

回款来源月份饼图和已回款毛利明细同源，不需要后端返回单独的饼图字段。

前端直接基于 `/wallet.collectedItems` 计算饼图：

```text
source_amount = collectedItems[].gp
total_amount = SUM(collectedItems[].gp)
ratio = source_amount / total_amount
```

示例：

```text
处理费：6800
账单/拒付：4900
逾期发票：1700
合计：13400
```


## 5. 发薪管道口径

发薪管道解释同一活动月份下，不同费用类型因为回款时间不同，会进入不同发薪批次。

以原图 `2026年4月` 数据为例：

| 管道 | 数据来源 | 发薪逻辑 |
|---|---|---|
| 下一次发薪：5月12日 | 4月1日-4月30日实时回款费用 | 4月已实际回款，进入4月结算，因此5月12日发佣金 |
| 未来发薪：6月12日 | 4月 API 月账单 | 5月20日到期回款后计入5月结算，因此6月12日发佣金 |

注意：

```text
未来发薪不是下一个活动月份的绩效。
未来发薪是当前活动月份里，因为账单回款滞后而进入后续发薪批次的佣金管道。
```

## 6. 数据模型

### 6.0 枚举定义

来源类型和产品类型只在后端保存和接口返回枚举值，不返回中文展示名。

#### 6.0.1 source_type

`source_type` 表示佣金来源类型，用于明细表、饼图聚合和发薪管道判断。

| 枚举值 | 页面展示建议 | 说明 |
|---|---|---|
| real_time_processing_fee | 处理费 | 实时处理费回款 |
| billing_decline_fee | 账单/拒付 | 月账单、条件拒付等回款 |
| past_due_invoice | 逾期发票 | 历史逾期发票回款 |
| api_monthly_billing | API 月账单 | API 月账单类收入；通常在次月 20 号生成，可能只进入未来发薪展示 |

#### 6.0.2 product_type

`product_type` 表示产品模块，用于按产品维度拆分收入、成本、GP 和佣金。

| 枚举值 | 页面展示建议 | 说明 |
|---|---|---|
| qbit_card | 量子卡 | 卡产品，匹配 `dws_sales_revenue_monthly.product` |
| group_account | 全球账户 | 入金、付款、汇差，匹配 `dws_sales_revenue_monthly.product` |
| crypto | 加密稳定币 | 承兑，匹配 `dws_sales_revenue_monthly.product` |
| treasury | 理财 | 理财产品，匹配 `dws_sales_revenue_monthly.product` |
| open_api | OpenAPI | API 接入费、设计费、部署费、月费，匹配 `dws_sales_revenue_monthly.product` |

#### 6.0.3 pipeline_type

`pipeline_type` 表示发薪管道类型，用于右侧“下一次发薪 / 未来发薪”卡片。

| 枚举值 | 页面展示建议 | 说明 |
|---|---|---|
| next_payout | 下一次发薪 | 当前活动月份中已满足回款条件、预计进入最近一次发薪的数据 |
| future_payout | 未来发薪 | 当前活动月份中因回款滞后、预计进入后续发薪批次的数据 |

#### 6.0.4 commission_stage

`commission_stage` 表示明细是否参与当前钱包快照汇总。

| 枚举值 | 页面展示建议 | 是否参与主表汇总 | 说明 |
|---|---|---|---|
| current_payout | 当前发薪 | 是 | 参与当前 `settlement_month` 的 `total_commission` |
| future_payout | 未来发薪 | 否 | 只用于展示未来发薪，不参与当前 `settlement_month` 的主表汇总 |

主表汇总规则：

```text
total_effective_revenue = SUM(detail.effective_revenue WHERE commission_stage = 'current_payout')
total_cogs = SUM(detail.cogs WHERE commission_stage = 'current_payout')
total_gp = SUM(detail.gp WHERE commission_stage = 'current_payout')
total_commission = SUM(detail.commission_amount WHERE commission_stage = 'current_payout')
```

API 月账单特殊规则：

```text
4月 API 月账单在 5月20日生成后，可以补入 4月快照明细。
这类明细 commission_stage = 'future_payout'，只用于右侧 Future Payout 展示。
它不参与 4月快照主表 total_commission。
等进入 5月结算快照时，再作为 current_payout 参与 5月主表汇总。
```

#### 6.0.5 rule_code

`rule_code` 只记录实际命中的佣金规则编码，前端不依赖它展示文案。

| 规则编码 | 说明 |
|---|---|
| gp_qbit_card_0_180 | 量子卡毛利，活跃 0-180 天 |
| gp_group_account_181_365 | 全球账户毛利，活跃 181-365 天 |
| gp_crypto_366_1095 | 加密稳定币毛利，活跃 366-1095 天 |
| gp_treasury_0_180 | 理财毛利，活跃 0-180 天 |
| open_api_api_one_time_fee_15pct | API 一次性合规及接入费、卡面设计费、白标系统部署费，按实际收费 15% |
| open_api_monthly_0_365 | API 月费，活跃 0-365 天，按实际收费 10% |
| open_api_monthly_366_1095 | API 月费，活跃 366-1095 天，佣金率 0% |
| overseas_sales_2_direct_gp_20pct | 海外销售二部直邀客户，GP 佣金率 20% |
| overseas_sales_2_non_direct_gp_10pct | 海外销售二部非直邀客户，GP 佣金率 10% |

### 6.1 DWS 建表基础字段

本需求新增 DWS 表时，需要沿用现有分区表规范。

注意：`report_date` 是 DWS 分区字段，属于建表必须字段；佣金业务时间只使用 `settlement_month`。

所有物理表必须包含以下基础字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int8 | 主键 ID |
| report_date | date | 报表日期 / 分区日期 |
| version | int4 | 数据版本，默认 `1` |
| remarks | varchar(255) | 备注 |
| create_time | timestamp | 创建时间，默认 `now()` |
| update_time | timestamp | 更新时间，默认 `now()` |
| delete_time | timestamp | 软删除时间 |
| sale_id | varchar(64) | 销售 / AM ID |

建表要求：

```sql
PRIMARY KEY (id, report_date)
PARTITION BY RANGE (report_date)
```

2026 年分区示例：

```sql
CREATE TABLE dws.xxx_2026 PARTITION OF dws.xxx_p
FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
```

快照主表建表示例：

```sql
CREATE TABLE dws.sales_commission_snapshot_p (
  id int8 NOT NULL,
  report_date date NOT NULL,
  version int4 DEFAULT 1,
  remarks varchar(255),
  create_time timestamp(6) NOT NULL DEFAULT now(),
  update_time timestamp(6) NOT NULL DEFAULT now(),
  delete_time timestamp(6),
  sale_id varchar(64),
  settlement_month varchar(7) NOT NULL,
  total_effective_revenue numeric(18, 2) DEFAULT 0,
  total_cogs numeric(18, 2) DEFAULT 0,
  total_gp numeric(18, 2) DEFAULT 0,
  total_commission numeric(18, 2) DEFAULT 0,
  CONSTRAINT sales_commission_snapshot_pkey PRIMARY KEY (id, report_date)
)
PARTITION BY RANGE (report_date);

CREATE TABLE dws.sales_commission_snapshot_2026 PARTITION OF dws.sales_commission_snapshot_p
FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
```

### 6.4 表关系

本期建议只新增 2 张快照物理表：

| 表 | 是否新增物理表 | 用途 |
|---|---|---|
| `sales_commission_snapshot_p` | 是 | 钱包区快照汇总 |
| `sales_commission_snapshot_detail_p` | 是 | 钱包区快照组成明细 |

绩效活动视图和发薪管道不在本期新增物理表，优先从已有 BI 宽表、现有 DWS 表或查询服务中实时计算。

两张快照表通过稳定业务键串起来，不依赖销售名称、客户名称、部门名称等展示字段。

核心业务关联键：

```text
settlement_month + sale_id
```

`report_date` 只作为 DWS 分区字段使用，查询时可以带上它做分区裁剪，但不作为佣金业务时间口径。

关系说明：

| 表 | 关系 | 说明 |
|---|---|---|
| `sales_commission_snapshot_p` | 主表 | 每个 `settlement_month + sale_id` 一条快照汇总 |
| `sales_commission_snapshot_detail_p` | 明细表 | 通过 `settlement_month + sale_id` 关联主表，一条快照对应多条组成明细 |

钱包区数据来源：

```text
sales_commission_snapshot_p
  -> 汇总金额、结算月份

sales_commission_snapshot_detail_p
  -> 已回款毛利明细
  -> 前端基于 collectedItems 生成回款来源饼图
```

绩效区数据来源：

```text
已有 BI 宽表 / DWS 查询服务
  -> 绩效活动视图

已有回款、账单、成本、佣金规则查询
  -> 下一次发薪
  -> 未来发薪

sales_commission_snapshot_detail_p
  -> 20号 API 月账单生成后补入 future_payout 明细
  -> 可用于生成右侧 Future Payout 展示
```

示例：

```text
settlement_month = 2026-04
sale_id = sale_001

主表：1 行，记录 4 月结算后的 8 号快照汇总
明细表：多行，记录这笔佣金由哪些来源、产品、客户、回款月份组成
```

### 6.5 8 号前预估物化视图

8 号前接口不直接现场 join 多张过程表，统一查询近三个月佣金预估物化视图。

建议物化视图：

```text
dws.mv_sales_commission_recent_estimate
```

刷新频率：

```text
每半天刷新一次。
8 号快照任务执行前必须先刷新成功。
```

物化视图范围：

```text
近三个月 settlement_month 数据。
```

物化视图输入：

| 数据 | 来源 | 说明 |
|---|---|---|
| 收入 | `dws.dws_sales_revenue_monthly` | 每日刷新过程表，精确到底层 account |
| 全球账户成本 | `dwm.dwm_finance_channel_cost_p` | `product_line = GLOBAL_ACCOUNT`，provider 目前包含 `BZ`、`CL` |
| 量子卡成本 | 现有 total cost 脚本结果 | 参考 `bi-cost/flink/total_cost/dws_online_total_channel_cost_daily_v3-batch-sql.sql`，覆盖 BB、QI |
| 量子卡 BPC 成本 | `dwm.dwm_finance_channel_cost_p` | `product_line = QUANTUM_CARD`，provider = `BPC` |
| 加密承兑成本 | 规则计算 | `assets_acceptance_fee_gt_zero * 0.09% + assets_acceptance_fee_eq_zero * 0.09%` |
| 量子卡渠道返现 | BB / QI 日表 | BB 使用 `cashback_income`；QI 参考 total cost 脚本中的 HK regular / VIP 返现逻辑 |
| 活跃时间 | `dim.dim_account_analysis` | 按产品取对应激活时间计算活跃天数 |
| 邀请归因 | `dim.dim_account_analysis.referral_user_id` | 只保存邀请码归属用户 ID，不保存直邀判断结果 |
| 销售关系 | `salesAccountRelation` | 快照生成时按当期有效销售关系判断直邀 / 非直邀 |
| 返佣规则 | `dim.dim_sales_commission_rule` | 按部门 ID、产品、provider、item、活跃天数、直邀类型命中规则 |

底层 account 需要统一到 `root_account_id`：

```sql
COALESCE(aar.root_id, source.account_id) AS root_account_id
```

有效收入口径：

```text
effective_revenue = real_income_value - channel_cashback
```

成本口径：

```text
cogs = 全球账户成本 + 量子卡成本 + BPC成本 + 加密承兑成本
```

毛利口径：

```text
gp = effective_revenue - cogs
```

物化视图建议输出字段：

| 字段 | 说明 |
|---|---|
| settlement_month | 结算月份 |
| root_account_id | 顶层客户 ID |
| product | 产品线 |
| provider | 服务商 / 渠道 |
| source_type | 页面回款来源类型 |
| sale_id | 销售 ID |
| operation_manager_id | 运营经理 ID |
| am_id | AM ID |
| effective_revenue | 有效收入 |
| cogs | 成本 |
| gp | 毛利 |
| commission_base | 计佣基数 |
| commission_rate | 佣金率 |
| estimated_commission | 预估佣金 |
| active_days | 活跃天数 |
| invite_type | 直邀类型，`direct` / `non_direct` / `all` |
| rule_code | 命中的返佣规则编码 |

直邀类型不落在 `dim.dim_account_analysis` 中。快照生成时使用当前明细归属的 `sale_id`（来自当期有效 `salesAccountRelation`）和 `dim.dim_account_analysis.referral_user_id` 判断：

```text
referral_user_id = sale_id => direct
referral_user_id <> sale_id 或 referral_user_id 为空 => non_direct
```

计算结果写入 `sales_commission_snapshot_detail.invite_type`，保证 8 号快照生成后历史月份不受后续销售关系调整影响。

### 6.6 返佣规则维表：dim_sales_commission_rule

返佣政策需要建表维护，不写死在代码里。规则表用于：

- 支持部门差异；
- 支持产品差异；
- 支持活跃天数阶梯；
- 支持 OpenAPI 按实际收费计佣；
- 支持海外销售二部直邀 / 非直邀特殊规则；
- 支持历史规则按时间追溯。

`department_id` 使用部门 ID，不使用部门名称。

部门 ID：

| 部门 ID | 部门名称 | 说明 |
|---|---|---|
| 1740319905791647746 | 销售一部 | 国内业务 |
| 1740319923059597313 | 销售二部 | 国内业务 |
| 2066369412858433538 | 销售三部 | 国内业务 |
| 2077248232127864834 | 销售四部 | 国内业务 |
| 1740320716902932481 | 大客户管理部 | 海外 / 大客户 |
| 1740320675756810242 | 海外业务销售部 - 1 | 海外业务 |
| 1851130772357509121 | 海外业务销售部 - 2 | 海外业务，直邀 / 非直邀特殊规则 |
| 1762301052057112578 | 其他 | 其他 |
| 1760576792068489218 | 创新业务部 | 创新业务 |

规则关键字段：

| 字段 | 说明 |
|---|---|
| rule_code | 规则编码，写入快照明细用于追溯 |
| department_id | 部门 ID |
| product | 产品线，可为空；为空表示全部产品 |
| provider | 服务商 / 渠道，可为空 |
| item | 收费项，可为空 |
| commission_base_type | 计佣基数，`gp` 或 `actual_fee` |
| active_days_min | 活跃天数下限，可为空 |
| active_days_max | 活跃天数上限，可为空 |
| commission_rate | 佣金率 |
| invite_type | 直邀类型，`all` / `direct` / `non_direct` |
| start_time | 生效开始时间 |
| end_time | 生效结束时间，默认 `2099-01-01 00:00:00` 表示长期有效 |
| priority | 优先级，数字越小优先级越高 |

规则时间使用左闭右开：

```text
start_time <= rule_match_time < end_time
```

`end_time` 不使用空值；默认 `2099-01-01 00:00:00` 表示长期有效。

规则命中顺序：

1. `enabled = true`；
2. 命中 `start_time` / `end_time`；
3. 命中 `department_id`；
4. 命中 `product`、`provider`、`item`，空值表示通配；
5. 命中 `active_days_min` / `active_days_max`；
6. 命中 `invite_type`；
7. 按 `priority` 从小到大取第一条。

海外销售二部特殊规则：

```text
department_id = 1851130772357509121
直邀客户：Gross Profit * 20%
非直邀客户：Gross Profit * 10%
```

加密承兑成本特殊处理：

```text
assets_acceptance_fee_gt_zero * 0.09%
+ assets_acceptance_fee_eq_zero * 0.09%
```

该成本在物化视图中计算到 `cogs`，返佣规则表只维护佣金率，不维护成本公式。

建表 SQL 见：

```text
sales_commission_rule.sql
```

## 9. 快照任务设计

### 9.1 任务时间

物化视图每半天刷新一次。

每月 8 号运行快照任务。

建议任务名称：

```text
sales_commission_snapshot_monthly_job
```

### 9.2 任务输入

如果任务在 `2026-05-08` 运行：

```text
settlement_month = 2026-04
```

### 9.3 任务步骤

8 号前半天刷新任务：

1. 读取近三个月 `dws_sales_revenue_monthly`。
2. 统一底层 account 到 `root_account_id`。
3. 补齐渠道返现、全球账户成本、量子卡成本、BPC 成本、加密承兑成本。
4. 关联 `dim_account_analysis` 计算活跃天数。
5. 命中 `dim.dim_sales_commission_rule` 计算佣金率和规则编码。
6. 刷新 `dws.mv_sales_commission_recent_estimate`。

每月 8 号快照任务：

1. 获取本次需要生成快照的结算月份。
2. 快照任务开始前强制刷新 `dws.mv_sales_commission_recent_estimate`，刷新失败则停止任务。
3. 从物化视图读取目标结算月份的数据。
4. 生成 `commission_stage = current_payout` 的快照明细。
5. 写入 `sales_commission_snapshot_detail`，保存最终 `effective_revenue`、`cogs`、`gp`、`commission_rate`、`commission_amount`。
6. 仅聚合 `commission_stage = current_payout` 的明细到快照主表金额。
7. 写入 `sales_commission_snapshot`。
8. 校验主表合计与明细合计一致。
9. 输出任务日志。

每月 20 号 API 月账单生成后：

1. 查询本月生成的 API 月账单。
2. 找到对应活动月份的快照明细，例如 4 月 API 月账单对应 `settlement_month = 2026-04`。
3. 写入或更新 `commission_stage = future_payout` 的明细。
4. 设置 `payable_settlement_month` 为预计进入发薪的结算月份，例如 `2026-05`。
5. 不更新快照主表的 `total_effective_revenue`、`total_cogs`、`total_gp`、`total_commission`。
6. 右侧 Future Payout 展示可读取这部分明细。

### 9.4 幂等要求

同一个 `settlement_month + sale_id` 只能有一份有效快照。

建议写入策略：

```text
如果快照不存在：insert
如果快照已存在：默认不覆盖
如果需要补跑：必须显式传入 force_rebuild，并记录补跑日志
```

本期目标是保证 8 号提供给财务的报表金额稳定，因此快照生成后不随源收入或成本变化自动重算。

8 号后页面查询：

```text
钱包区：只查 sales_commission_snapshot / sales_commission_snapshot_detail
已结算绩效口径：优先查 sales_commission_snapshot_detail 聚合
未到 8 号的预估月份：查 dws.mv_sales_commission_recent_estimate
```
