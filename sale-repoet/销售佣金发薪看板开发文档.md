# 销售佣金发薪看板开发文档

## 1. 文档目标

本文档用于指导销售佣金发薪看板的前后端、数据任务和权限开发。

关联需求文档：

- [销售佣金发薪看板需求文档](销售佣金发薪看板需求文档.md)

关联示意图：

- [销售佣金仪表盘原始月份翻译版](销售佣金仪表盘原始月份翻译版.png)

## 2. 功能范围

本期只做一个销售佣金页面，不做团队聚合页、不做部门汇总页。

不同角色通过同一页面顶部筛选器查看不同销售 / AM 的数据：

| 角色 | 页面范围 | 是否聚合 |
|---|---|---|
| 销售 | 只看自己 | 否 |
| AM | 只看自己 | 否 |
| 销售主管 | 可筛选自己及下属销售 / AM | 否 |
| 超级管理员 | 可筛选部门及部门下销售 / AM | 否 |

页面包含两个主要数据区：

| 页面区域 | 作用 |
|---|---|
| 我的钱包 | 展示已结算、已回款、可发薪的数据 |
| 我的绩效 | 展示活动月份绩效，以及后续发薪管道 |

## 3. 核心时间规则

### 3.1 发薪规则

发薪日期固定为每月 12 号。

```text
结算月份 M
-> M+1 月 8 号生成快照
-> M+1 月 12 号发薪
```

示例规则：

```text
2026年4月结算数据
-> 2026年5月8日生成快照
-> 2026年5月12日发4月实时回款佣金
```

原图还包含一个发薪管道示例：

```text
2026年4月 API 月账单
-> 2026年5月20日到期回款
-> 2026年5月结算
-> 2026年6月12日发佣金
```

### 3.2 数据起始月份

上线展示数据从 `2026-06` 开始；本文接口样例沿用示意图中的 `2026-04` 数据，方便和图片逐项对照。

前端和后端都要限制：

```text
settlement_month >= '2026-06'
```

示意图中的 `2026-04` 仅作为开发联调样例，不代表生产可查询起始月份。

历史事件可以记录在底层表，但接口不返回 2026 年 6 月以前的展示数据。

### 3.3 快照规则

每月 8 号跑数并固化快照。

快照生成后：

- 金额不再因为源数据变化而重新计算覆盖；
- 页面回看历史月份时读取快照表；
- 快照只记录 8 号当天给财务使用的返佣金额和组成细节；
- 本报表不处理调账、扣减和财务发薪审批；
- 页面发薪状态根据结算月份推导出的发薪日期和当前日期自动判断，不需要在快照表维护状态。

### 3.4 示意图月份基准

开发文档中的接口样例和金额示例以原图月份为准：

| 图中位置 | 月份 / 日期 | 说明 |
|---|---|---|
| 数据筛选 | 2026年4月（已结算） | 当前查看的结算 / 活动月份 |
| 我的钱包 | 5月12日发放 | 展示 4 月结算后进入 5 月 12 日发薪的数据 |
| 已回款毛利明细 | 3月实时处理费、2月账单及条件拒付、1月逾期发票 | 这些是进入当前钱包发薪批次的历史回款来源 |
| 我的绩效 | 4月1日 - 4月30日活动 | 展示 4 月活动绩效 |
| 下一次发薪 | 5月12日 | 4 月实时回款费用进入 5 月 12 日发薪 |
| 未来发薪 | 6月12日 | 4 月 API 月账单在 5 月 20 日到期回款，进入 6 月 12 日发薪 |

## 4. 计算口径

### 4.1 主链路

```text
Real-time processing
- Client Rebate
= Effective Revenue

Effective Revenue
- COGS
= Gross Profit / GP

GP × Commission Rate
= Commission
```

### 4.2 明细行计算

```text
commission_base = gp
commission_amount = commission_base × commission_rate
```

API 费用存在特殊口径时：

```text
commission_base = api_actual_fee
commission_amount = api_actual_fee × api_commission_rate
```

### 4.3 快照佣金金额

```text
total_commission = SUM(snapshot_detail.commission_amount)
```

本报表不做调账和扣减，因此页面展示的实际发佣金合计直接使用：

```text
snapshot_commission_amount = total_commission
```

### 4.4 饼图数据

回款来源月份饼图后端只返回各来源金额和合计金额，不返回占比。

默认金额口径按 GP 汇总：

```text
source_amount = SUM(snapshot_detail.gp)
total_amount = SUM(source_amount)
```

示例：

```text
处理费：6800
账单/拒付：4900
逾期发票：1700
合计：13400
```

前端根据后端返回值计算占比：

```text
ratio = item.amount / total
```

## 5. 发薪管道口径

发薪管道解释同一活动月份下，不同费用类型因为回款时间不同，会进入不同发薪批次。

以原图 `2026年4月` 数据为例：

| 管道 | 数据来源 | 发薪逻辑 |
|---|---|---|
| 下一次发薪：5月12日 | 4月1日-4月30日实时回款费用 | 4月已实际回款，进入4月结算，因此5月12日发佣金 |
| 未来发薪：6月12日 | 4月 API 月账单 | 5月20日到期回款后计入5月结算，因此6月12日发佣金 |

注意：

```text
未来发薪不是下一个活动月份的绩效。
未来发薪是当前活动月份里，因为账单回款滞后而进入后续发薪批次的佣金管道。
```

## 6. 数据模型

### 6.0 枚举定义

来源类型和产品类型只在后端保存和接口返回枚举值，不返回中文展示名。

前端根据 `sourceType` 做文案映射：

| 枚举值 | 页面展示建议 | 说明 |
|---|---|---|
| real_time_processing_fee | 处理费 | 实时处理费回款 |
| billing_decline_fee | 账单/拒付 | 月账单、条件拒付等回款 |
| past_due_invoice | 逾期发票 | 历史逾期发票回款 |
| api_monthly_billing | API 月账单 | API 月账单类收入 |

前端根据 `productType` 做文案映射：

| 枚举值 | 页面展示建议 | 说明 |
|---|---|---|
| quantum_card | 量子卡 | 卡产品 |
| api | API | API 产品 |
| account_service | 账户服务 | 账户类服务 |

前端根据 `pipelineType` 做发薪管道文案映射：

| 枚举值 | 页面展示建议 | 说明 |
|---|---|---|
| next_payout | 下一次发薪 | 当前活动月份中已满足回款条件、预计进入最近一次发薪的数据 |
| future_payout | 未来发薪 | 当前活动月份中因回款滞后、预计进入后续发薪批次的数据 |

### 6.1 DWS 建表基础字段

本需求新增 DWS 表时，需要沿用现有分区表规范。

所有物理表必须包含以下基础字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int8 | 主键 ID |
| report_date | date | 报表日期 / 分区日期 |
| version | int4 | 数据版本，默认 `1` |
| remarks | varchar(255) | 备注 |
| create_time | timestamp | 创建时间，默认 `now()` |
| update_time | timestamp | 更新时间，默认 `now()` |
| delete_time | timestamp | 软删除时间 |
| sale_id | varchar(64) | 销售 / AM ID |

建表要求：

```sql
PRIMARY KEY (id, report_date)
PARTITION BY RANGE (report_date)
```

2026 年分区示例：

```sql
CREATE TABLE dws.xxx_2026 PARTITION OF dws.xxx_p
FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
```

快照主表建表示例：

```sql
CREATE TABLE dws.sales_commission_snapshot_p (
  id int8 NOT NULL,
  report_date date NOT NULL,
  version int4 DEFAULT 1,
  remarks varchar(255),
  create_time timestamp(6) NOT NULL DEFAULT now(),
  update_time timestamp(6) NOT NULL DEFAULT now(),
  delete_time timestamp(6),
  sale_id varchar(64),
  settlement_month varchar(7) NOT NULL,
  snapshot_generated_at timestamp(6) NOT NULL,
  role_type varchar(32),
  total_effective_revenue numeric(18, 2) DEFAULT 0,
  total_cogs numeric(18, 2) DEFAULT 0,
  total_gp numeric(18, 2) DEFAULT 0,
  total_commission numeric(18, 2) DEFAULT 0,
  snapshot_status varchar(32) DEFAULT 'settled',
  CONSTRAINT sales_commission_snapshot_pkey PRIMARY KEY (id, report_date)
)
PARTITION BY RANGE (report_date);

CREATE TABLE dws.sales_commission_snapshot_2026 PARTITION OF dws.sales_commission_snapshot_p
FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
```

### 6.2 快照主表：sales_commission_snapshot

用途：保存某个销售 / AM 在某个结算月份下的发薪快照汇总。

建议业务字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| settlement_month | string | 结算月份，格式 `YYYY-MM` |
| snapshot_generated_at | datetime | 快照生成时间 |
| role_type | string | `sales` / `am` |
| total_effective_revenue | decimal | 有效收入合计 |
| total_cogs | decimal | 成本合计 |
| total_gp | decimal | GP 合计 |
| total_commission | decimal | 佣金合计 |
| snapshot_status | string | `settled` |

唯一约束：

```text
UNIQUE(report_date, settlement_month, sale_id)
```

### 6.3 快照明细表：sales_commission_snapshot_detail

用途：保存发薪金额来源明细。

建议业务字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| settlement_month | string | 结算月份 |
| customer_id | string | 客户 ID |
| source_type | string | 来源类型 |
| product_type | string | 产品模块 |
| activity_month | string | 活动月份 |
| collection_month | string | 回款月份 |
| effective_revenue | decimal | 有效收入 |
| cogs | decimal | 成本 |
| gp | decimal | 毛利 |
| commission_base | decimal | 计佣基数 |
| commission_rate | decimal | 佣金率 |
| commission_amount | decimal | 佣金金额 |
| active_days | integer | 活跃天数 |
| rule_code | string | 规则编码 |

### 6.4 表关系

本期建议只新增 2 张快照物理表：

| 表 | 是否新增物理表 | 用途 |
|---|---|---|
| `sales_commission_snapshot_p` | 是 | 钱包区快照汇总 |
| `sales_commission_snapshot_detail_p` | 是 | 钱包区快照组成明细 |

绩效活动视图和发薪管道不在本期新增物理表，优先从已有 BI 宽表、现有 DWS 表或查询服务中实时计算。

两张快照表通过稳定业务键串起来，不依赖销售名称、客户名称、部门名称等展示字段。

核心关联键：

```text
report_date + settlement_month + sale_id
```

关系说明：

| 表 | 关系 | 说明 |
|---|---|---|
| `sales_commission_snapshot_p` | 主表 | 每个 `report_date + settlement_month + sale_id` 一条快照汇总 |
| `sales_commission_snapshot_detail_p` | 明细表 | 通过 `report_date + settlement_month + sale_id` 关联主表，一条快照对应多条组成明细 |

钱包区数据来源：

```text
sales_commission_snapshot_p
  -> 汇总金额、快照生成时间、结算月份

sales_commission_snapshot_detail_p
  -> 已回款毛利明细
  -> 按 source_type 聚合后生成回款来源饼图数据
```

绩效区数据来源：

```text
已有 BI 宽表 / DWS 查询服务
  -> 绩效活动视图

已有回款、账单、成本、佣金规则查询
  -> 下一次发薪
  -> 未来发薪
```

示例：

```text
report_date = 2026-05-08
settlement_month = 2026-04
sale_id = sales_001

主表：1 行，记录 4 月结算后的 8 号快照汇总
明细表：多行，记录这笔佣金由哪些来源、产品、客户、回款月份组成
```

## 7. 后端接口

接口统一要求：

- 所有接口都要校验当前登录用户权限；
- 不允许通过传参越权查看其他销售 / AM；
- 生产环境结算月份小于 `2026-06` 时直接返回错误或空列表；示例 JSON 使用图片中的 `2026-04`；
- 金额字段统一返回 number，前端负责格式化。

本页面不新增部门 / 销售筛选接口，直接复用系统现有下拉能力。

本页面新增接口建议控制为 2 个：

| 接口 | 页面区域 |
|---|---|
| `GET /api/sales-commission/wallet` | 我的钱包 |
| `GET /api/sales-commission/performance` | 我的绩效 |

## 8. 权限设计

### 8.1 权限判断输入

后端从登录态获取：

| 字段 | 说明 |
|---|---|
| current_user_id | 当前用户 ID |
| current_role | 当前角色 |
| current_department_id | 当前用户部门 |

接口入参中的 `salesId` 只能作为查看对象，不能作为权限依据。

### 8.2 可见人员规则

```text
销售 / AM：
visible_sales_ids = [current_user_id]

销售主管：
visible_sales_ids = [current_user_id] + subordinate_sales_ids

超级管理员：
visible_sales_ids = sales_ids under selected department
```

每个查询接口都必须校验：

```text
request.salesId IN visible_sales_ids
```

不满足时返回：

```json
{
  "code": "FORBIDDEN",
  "message": "无权限查看该销售数据"
}
```

## 9. 快照任务设计

### 9.1 任务时间

每月 8 号运行。

建议任务名称：

```text
sales_commission_snapshot_monthly_job
```

### 9.2 任务输入

如果任务在 `2026-05-08` 运行：

```text
settlement_month = 2026-04
snapshot_generated_at = 2026-05-08 当前任务时间
```

### 9.3 任务步骤

1. 获取本次需要生成快照的结算月份。
2. 查询可计佣销售 / AM 列表。
3. 按销售 / AM 聚合产品收入、返利、成本、GP。
4. 按部门、产品、活跃天数应用佣金率。
5. 生成快照明细。
6. 聚合快照主表金额。
7. 写入 `sales_commission_snapshot`。
8. 写入 `sales_commission_snapshot_detail`。
9. 校验主表合计与明细合计一致。
10. 输出任务日志。

### 9.4 幂等要求

同一个 `settlement_month + sale_id` 只能有一份有效快照。

建议写入策略：

```text
如果快照不存在：insert
如果快照已存在：默认不覆盖
如果需要补跑：必须显式传入 force_rebuild，并记录补跑日志
```

本期目标是保证 8 号提供给财务的报表金额稳定，因此快照生成后不随源收入或成本变化自动重算。

## 10. 前端页面数据流

### 10.1 页面初始化

1. 复用系统现有部门 / 销售下拉能力。
2. 根据角色渲染页面筛选器：
   - 销售 / AM：隐藏部门和销售下拉；
   - 销售主管：显示销售下拉；
   - 超级管理员：显示部门和销售下拉。
3. 默认选择最近一个已结算月份。
4. 调用本页面数据接口。

### 10.2 页面数据接口调用

当 `salesId` 或 `settlementMonth` 改变时：

```text
GET /api/sales-commission/wallet
```

当活动月份或页面默认绩效月份改变时：

```text
GET /api/sales-commission/performance
```
