# PD-3047 通知验证码接口拆分实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans or superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** 为通知验证码两条接口新增独立 `/api/admin/...` 入口，保留商户原 URL，并确保 Admin 与商户请求各自使用对应身份上下文。

**Architecture:** 新建 Admin Controller，分别承接登录前的 `code` 和已登录的 `codes`；复用现有验证码 Service，不在 Controller 之间转存用户上下文。商户 Controller 和 URL 保持原样，Admin 路径的 IP 白名单由入口网关/WAF 配置。

**Tech Stack:** Java 17、Spring Boot 3.0.2、Spring MVC、Jakarta Validation、现有 QbitNotificationService、JUnit/项目现有 MVC 测试设施。

**Spec:** 本文档“目标与边界”“方案选择”“接口与安全决议”部分（本文自包含设计要求）。

## Global Constraints

- 只处理故事 Excel 中分配的两条接口；其他作者名下接口不进入本次变更。
- 仅修改 qbit-assets 后端；不修改 `qbit_admin`、`qbit-admin-v3`、`qbit_web` 前端代码。
- 商户端继续使用 `/api/notification/send/verify/code(s)`，不得转入 Admin 用户上下文。
- Admin 路由使用业务语义短横线命名规则；路径为 `/api/admin/notification/send/verify/code` 与 `/api/admin/notification/send/verify/codes`。
- 保留现有验证码类型、验证码校验、图形验证、fingerprint、IP/联系方式频控和封禁语义；任何收件人绑定规则须先按实际调用场景确认。
- 不自动创建分支、commit、push 或 PR；不覆盖其他人的未提交修改。

## Review Focus

1. Admin `/code` 是免登录入口：必须保留验证码类型限制、图形验证码及发送风控；覆盖匿名请求的允许/拒绝场景。
2. Admin `/codes` 必须经过 Admin 登录和接口权限校验；覆盖匿名拒绝和无权限拒绝。
3. 新 Admin `/codes` 不得加入 `AuthorityAspect.SKIP_CHECK_URLS`；检查它不会继承旧商户路由的权限跳过。
4. `emailPhone` 来自请求体：按已确认的调用用途覆盖联系方式属于当前 Admin 与不属于当前 Admin 两种情况；若是找回密码流程，则验证既有允许规则。
5. 商户与 Admin URL 同时存在：验证商户入口仍走商户拦截器、Admin 入口走 Admin 拦截器，且商户请求不能借 Admin 身份上下文。

## 目标与边界

将商户与 Admin 的 HTTP 入口拆开，使 Admin 流量能按 `/api/admin/...` 在网关/WAF 配置 IP 白名单；商户继续使用原 `/api/notification/...` 路径。两个入口可以调用同一通知 Service，但各自由对应拦截器建立身份上下文，不跨入口复制或复用登录用户。

- `POST /api/notification/send/verify/code` → 新增 Admin `POST /api/admin/notification/send/verify/code`
- `POST /api/notification/send/verify/codes` → 新增 Admin `POST /api/admin/notification/send/verify/codes`

不改变短信/邮件模板和验证码业务规则，不处理其它接口。网关/WAF 的 IP 白名单属于部署侧配置，Assets 仓库本身未发现该两条路由对应的白名单实现。

## 当前实现与调用情况

- 两个商户路由位于 `QbitNotificationController`，类级路径为 `/api/notification`。
- `/send/verify/code` 使用 `@NoAuth(NO_LOGIN)`，调用 `sendSmsEmailNotification(..., false)`；Service 限制验证码类型必须属于 `SmsCodeEnum.NO_AUTHS`，并执行图形验证（适用类型）、频控和黑名单检查。
- `/send/verify/codes` 没有 `@NoAuth`，调用 `sendSmsEmailNotification(..., true)`；旧商户路径在 `AuthorityAspect.SKIP_CHECK_URLS` 中跳过菜单权限检查。
- `/api/admin/**` 由 `AdminRequestParamInterceptor` 处理；普通 Admin 请求校验登录并设置 Admin `UserContext`。`@NoAuth(NO_LOGIN)` 绕过登录拦截，因此 Admin 的登录前 `/code` 需要网关/WAF IP 白名单。
- 本地静态搜索确认 `qbit_admin` 在忘记密码和修改密码流程调用 `/code`；`qbit-admin-v3` 在忘记密码、修改密码流程调用 `/code`，并生成了 `/codes` 请求封装但未找到运行时调用。Excel 将 `/codes` 分配给 `qbit-admin`，实施前需按声明行复核实际调用方与用途。
- Excel 记载 `qbit-web` 对 `/code` 有业务引用。当前本地文本搜索未定位到对应引用时，应复核动态封装/生成调用，不能据此删除商户路由或判为未使用。

## 方案选择

1. **新增独立 Admin Controller（采用）**：Admin URL 经 `/api/admin/**` 拦截器建立 Admin 身份；商户 Controller 与 URL 保持现状；底层复用通知 Service。边界清楚，改动集中。
2. **在现有商户 Controller 上添加双路径映射（不采用）**：同一方法同时承接 Admin 与商户 URL，身份与免登录语义容易混杂。
3. **复制一套验证码 Service（不采用）**：会复制验证码、风控和频控逻辑，造成规则漂移。

## 接口与安全决议

| 用途 | Admin 路径 | 认证方式 | Service 调用 | 约束 |
|---|---|---|---|---|
| 登录前验证码 | `POST /api/admin/notification/send/verify/code` | `@NoAuth(NO_LOGIN)`；网关/WAF 按 Admin 路径做来源 IP 白名单 | `sendSmsEmailNotification(dto, request, false)` | 保留 `NO_AUTHS` 类型限制、适用的图形验证码、fingerprint、IP/联系方式频控与封禁。白名单内来源仍可调用，IP 白名单不是用户身份认证。 |
| 已登录验证码 | `POST /api/admin/notification/send/verify/codes` | Admin JWT、Admin 拦截器及对应接口权限；同时应用 IP 白名单 | `sendSmsEmailNotification(dto, request, true)` | 不加入 `AuthorityAspect.SKIP_CHECK_URLS`；先确认目标联系方式与当前 Admin 的关系。 |

商户两个原路由继续保留原注解、参数和 Service 调用，不重定向到 Admin 路径。Admin 与商户各自由拦截器设置/清除 `UserContext`；Controller 只交由 Service 处理当前请求，不手工转存另一侧用户身份。

### 纵向权限结论

商户旧 URL 不会因新增 Admin Controller 获得 Admin 路由能力。Admin `/codes` 应要求 Admin 拦截器认可的登录身份，并通过接口权限校验；仅有 `/api/admin` 前缀不等于仅管理员可访问，网关 IP 白名单和应用层身份/权限都必须生效。Admin `/code` 是登录前入口，不能靠登录身份隔离；非白名单来源必须由网关/WAF 拒绝。若商户请求来自被白名单覆盖的网络，单靠 IP 白名单无法区分商户和后台用户，这是免登录路由的已知限制。

### 横向数据结论

当前 DTO 允许请求方提交任意 `emailPhone`，Service 未把联系方式绑定到当前登录用户。`/code` 承担登录/找回密码流程，目标用户可由请求指定，横向风险包括对他人联系方式发码、滥用验证流程和验证码探测；现有图形验证、频控和封禁需保持。`/codes` 若用于 Admin 修改本人密码，应校验目标邮箱/手机属于当前 Admin 身份；若用于代表他人操作，需按真实调用流程确认授权规则。该用途复核完成前不切换该接口的前端调用。
