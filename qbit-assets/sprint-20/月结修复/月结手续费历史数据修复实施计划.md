# 月结手续费历史数据修复实施计划

> **For agentic workers:** 执行本方案时，按任务逐步实现并在每个任务后运行对应测试。此方案只定义修复流程和实现边界，不在本文阶段直接改动生产数据。

**目标：** 在现有 `sync_caas_month_tx` 定时任务中，按交易发生时的有效费率时间和历史月结区间重算指定手续费类型，并且每次只更新指定 `feeType`，保留同一 `fees` 数组中的其他费用。

**架构：** Asset 继续作为批处理入口，沿用现有交易筛选和分页流程，并批量读取账户配置操作日志以构建月结时间区间；Node 根据批处理传入的交易有效时间及历史月结状态选择 CAAS/普通费率。昨天整组重算的交易先通过任务参数指定的 OSS 文件中的 `修复前API fees` 恢复，再按指定 feeType 重跑；写回只合并目标项，其他费用保持恢复后的值。

**技术栈：** Java / Spring Boot / XXL-JOB / MyBatis；Node.js / TypeScript / NestJS；PostgreSQL。

**方案依据：** 本文记录与用户确认的修复规则；涉及代码位置见“文件职责”。

## 全局约束

- 修复仍通过现有 `sync_caas_month_tx` 定时任务执行。
- 交易筛选窗口沿用 Asset 当前按卡交易 `completeTime` 过滤的行为；不新增固定 `status = 'Closed'` 条件，状态沿用现有业务处理并保留在记录中。
- 费率查询时间沿用现行业务切换：北京时间 2026-10-01 00:00 前的交易使用卡交易 `completeTime`；从该边界起使用卡交易 `createTime`。切换判定字段必须与现网既有实现一致，不能用 API 记录的 `create_time` 代替卡交易时间。
- 交易有效时间超过 4 小时后，月结归属按该有效时间匹配历史配置日志区间；不得只读账户当前 `statementType`。日志按账户/任务批量读取并构建区间，不逐笔查询大日志表。
- 明确的 `Realtime` 日志与没有覆盖该时间的日志是不同情况。缺少历史日志时不得静默套用当前配置；记录为未能判定并跳过该笔修复，供核对。
- 0 是有效费率和有效计算结果，按正常值写入；不以“金额为 0”推断费率缺失。
- 每次任务可以指定一个或多个目标 `feeType`。只有目标类型参与重算和写回；数组中其他费用项原样保留。
- 昨天批次中被整组重算的交易，先将完整 `fees` 恢复到传入 OSS 文件的 `修复前API fees`，再执行后续重算。
- 后续每次只重算任务参数明确指定的 `feeType`。未指定的 `settlementFee` 保持恢复后的历史值；如果明确指定修复 `settlementFee`，必须使用适用于该历史时期的算法，不能直接套用当前算法。
- 重跑必须可重复执行；同一交易、同一目标类型重复执行应得到一致结果，不应重复追加费用项。

## Review Focus

- 10 月切换边界附近：用交易时间的北京时间判定，API `create_time` 只作同步窗口字段时不得影响费率时间选择。
- 账户曾在 Realtime/Monthly 间切换：按交易有效时间匹配对应历史日志区间。
- 操作日志没有覆盖交易有效时间：不误用当前配置，不把“未知”当成 `Realtime`。
- 指定单一费种且原 JSON 中同时存在其他费种：仅目标项变化，其他项保持原值和币种。
- 目标费种结果为 0、目标项原先不存在、重复执行：正确置零/补项且不重复添加。

## 1. 现状与问题

`ApiClientTransactionJob.syncTxJob()` 触发 `sync_caas_month_tx`，进入 Asset 的同步服务。卡交易分页查询沿用 `completeTime` 窗口；按账户配置日志建立的 `statementMonthMap` 用于判断历史月结。当前消费费用计算会生成一组费用，且费率请求带有时间；Node 的 `getCaasMonthFee` 则根据当前 `openApiClientConfig.statementType` 决定走普通费率或 CAAS 月结费率。因而修复历史交易时可能出现：交易有效时间属于月结区间，但账户当前已改成 Realtime，Node 仍按普通费率查询。

当前消费费用更新也可能以新生成的整组 `fees` 覆盖 API 交易记录。修复某个单项时，这会连带改变其他未指定费用。SettlementFee 另有历史算法变化，本次先恢复其原始值并保护，不用当前公式重算。

## 2. 修复规则

### 2.1 三种时间用途

| 用途 | 时间规则 |
|---|---|
| 任务筛选交易 | 沿用现有卡交易 `completeTime` 起止窗口，不调整筛选行为。 |
| 费率生效时间 | 2026-10-01 00:00（Asia/Shanghai）前取卡交易 `completeTime`；从该边界起取卡交易 `createTime`。 |
| 月结区间匹配 | 使用同一笔交易的费率生效时间，与 root 账户操作日志中的配置区间匹配。 |

`completeTime` 和 `createTime` 可能处于不同日期；边界归属需按 `sync_caas_month_tx` 现有生产分界实现确定，并在代码中集中成单一方法，禁止在筛选、月结判断、费率请求中分别硬编码不同分界。

### 2.2 历史月结判断

1. 每次任务按参与账户批量读取本次日期范围所需的 Open API 配置操作日志。
2. 按 root account 与日志生效时间排序，构建 `Realtime`/`Monthly` 的左闭右开区间；最后一条有效配置的区间结束时间为空。
3. 对每笔交易先计算费率生效时间，再匹配区间。`Monthly` 且交易超过 4 小时走异步月结费率类型；明确的 `Realtime` 走普通费率。最近 4 小时沿用既有 current-trade 规则。
4. Asset 已在任务中批量构建日志区间；对每笔交易把历史判定结果随费率请求传给 Node（字段 `statementTypeAtFeeTime: Monthly | Realtime`）。Node 对本次月结同步请求优先使用该上下文，不让当前 `statementType` 覆盖历史结果。其他在线调用未携带该字段时保留现有行为。
5. 找不到覆盖该交易时间的日志时记录交易 ID、root ID 和有效时间并跳过该笔修复；不从当前设置推断历史状态。

### 2.3 指定费用类型更新

任务参数增加可选 `feeTypes`（允许一个或多个）；未提供时保持既有定时任务的默认处理方式。专项修复必须显式传入目标类型，且 `settlementFee` 在本次修复中排除。

对每笔 API 交易执行：

1. 读取修复前的 `fees` JSON 数组。
2. 只调用目标 feeType 对应的计算逻辑；不为未指定类型重新查询费率或重算金额。
3. 对每个目标类型，在原数组中替换其条目；原数组没有该类型时新增一条。计算结果为 0 时仍写入 0。
4. 未指定的费用项及其 `currency`、顺序和额外字段保持不变。目标类型存在重复条目时记录异常并停止该交易更新，避免静默丢项。
5. 写入前保存交易 ID、account ID、目标 feeTypes、旧 fees、新 fees 和各目标项差额；同一个目标类型重复执行采用替换而非追加。

示例：目标仅为 `crossBorderFee` 时，原 `settlementFee`、`fxFee`、Apple Pay、ATM 等项保持原样。目标不包含 `settlementFee` 时，不从新的整组计算结果删除或覆盖它。

### 2.4 用 OSS 文件恢复昨天的费用数据

昨天那批整组重算的结果不作为有效修复结果。先由调用方传入昨天修复前导出的 OSS 文件；恢复程序使用其中的 **`修复前API fees`**，把该批交易的完整费用数组恢复到昨天修复前状态。恢复范围以传入文件中的交易明细为准；只回写 `api_client_transaction.fees`，不恢复交易状态、provider 或时间字段。

1. 增加显式 `RESTORE_BASELINE` 模式和 `restoreOssKey` 参数，通过项目现有 OSS 客户端读取 XLSX；不写死本机路径，不把 OSS 凭证写入任务参数或日志。
2. 校验表头包含 `交易ID`、`API账户ID`、`修复前API fees`。该列是唯一恢复值；`修复后API fees`、总金额和差额列不参与恢复计算。
3. 用 `交易ID + API账户ID` 定位 API 交易。遇到重复候选时，使用 `provider`、`API创建时间`进一步唯一定位；仍不唯一或找不到时记录并跳过，不能猜测。
4. 将 `修复前API fees` 解析为完整费用 JSON 数组，只更新 `api_client_transaction.fees`。空单元格、JSON `null`、空数组 `[]` 按文件约定区分；非法 JSON、缺字段或缺行不得默认为空费用。
5. 先 dry-run，列出文件行数、唯一交易数、可定位数、待恢复数、已相同数、重复键、缺行和 JSON 错误；确认后分批恢复，并记录 OSS object key、行号、交易 ID、账户 ID 和结果。
6. 恢复结束后重新读取，逐笔确认数据库 `fees` 等于 OSS 中的 `修复前API fees`。没有成功恢复的交易不进入后续重跑。

字段结构参考文件：`/Users/martinjiang/IdeaProjects/qbit-assets/qbit-core/target/exports/api-fee-time-before/all-transactions-before.xlsx`。其中逐笔 `交易ID`、`API账户ID`、`API创建时间`、`provider` 可定位记录，**H 列 `修复前API fees` 是恢复 `fees` 的值**。正式执行时仍从传入的 OSS object key 读取；客户/月/feeType 汇总表不具备逐笔恢复能力。

`RESTORE_BASELINE` 按 OSS 文件行定位交易并恢复，不套用 `REPAIR_FEES` 的卡交易时间窗口、月结资格或状态筛选；恢复对象是文件中明确列出的 API 交易行。

### 2.5 恢复后按指定 feeType 重新处理

1. `RESTORE_BASELINE` 完成并核验后，单独以 `REPAIR_FEES` 模式重跑，不将恢复和重算合成一个不可审查的写操作。
2. `REPAIR_FEES` 必须明确传入一个或多个目标 `feeTypes`。未指定的费用项（包括 `settlementFee`）保持已恢复的原值，不重算、不覆盖。
3. 如果明确指定修复历史 `settlementFee`，必须按交易所属时期选取对应历史算法；不能把当前 SettlementFee 公式顺带应用到历史交易。
4. 每笔写回仅替换目标 feeType；目标结果为 0 时照常写 0，目标项不存在时新增，非目标项保持原值。

## 5. 运行顺序

1. 将昨天修复前导出的 XLSX 上传到 OSS，任务参数传入 `restoreOssKey`；固化昨天实际处理的交易范围。
2. 暂停同范围自动任务，以 `RESTORE_BASELINE` 执行 dry-run，确认文件列、交易定位和 `修复前API fees` 解析正确。
3. 执行恢复，只将 OSS 的 `修复前API fees` 写回 `api_client_transaction.fees`；复查每笔数据与该列一致。错误/未匹配行不进入重跑。
4. 以 `REPAIR_FEES` 对恢复成功的交易执行 fee 计算 dry-run，检查历史月结状态、有效费率时间和指定 feeType 金额。
5. 确认后只重跑明确指定的 feeTypes；未指定的类型保持恢复值。
6. 按交易 ID 检查目标项符合新逻辑、非目标项与 OSS 的修复前 `fees` 一致，并保存运行参数及恢复/重跑结果。

## 6. 验收标准

- 任务仍从 `sync_caas_month_tx` 运行，原有筛选范围与状态业务保持不变。
- 10 月切换前后的费率时间符合既有规则，筛选窗口仍按原卡交易完成时间。
- 大于 4 小时的历史交易按日志生效区间判定月结，不受账户当前 statementType 覆盖；日志缺失可见且不会静默套用当前配置。
- 昨天实际修复范围可由任务传入的 OSS 文件恢复；数据库 `fees` 与文件 `修复前API fees` 逐笔一致。
- 恢复与重跑为两个显式阶段；重跑只更新指定的 feeType，其他费用保持 OSS 文件的修复前值。
- 历史 SettlementFee 未被指定时保持基线；被指定时按历史时期算法单项重算，不连带更新其他费用。
- 结果为 0 的目标费用正常写入；任务重跑不会重复费用项或产生二次金额变化。
- 修复前后逐笔对账可通过 transaction ID 复现目标项和非目标项变化。
