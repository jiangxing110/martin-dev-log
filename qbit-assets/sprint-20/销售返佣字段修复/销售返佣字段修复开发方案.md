# 销售返佣字段修复开发方案

> **方案状态：待评审**  
> **Created Time：2026-11-17 22:21:24**  
> **Updated Time：2026-11-18 11:03:00**

## 摘要

`POST /api/admin/sale/commission/performance` 已有 `realTimeProcessing` 字段，前端用它展示 `Total Generated Performance`。本次只修正这个字段的取值：改为按客户实际收入组成汇总，并计入 BB、QI 渠道返现；不新增响应字段，也不调整其他返回值。

本方案建议新增一张销售客户收入物化视图和一张独立的收入快照明细表。每月 8 号运行快照批处理，将当期已确认的收入组成明细固化；8 号前查询物化视图，快照生成后查询收入快照。现有佣金毛利、有效收入、佣金金额和发薪管道计算保持不变。

## 目标与范围

### 目标

- 按销售/AM、顶层客户、产品线、渠道和收入项目记录收入组成。
- `realTimeProcessing` 保留现有字段名和响应结构，改为承载绩效卡片的实际收入总额，包含 BB、QI 渠道返现。
- 每月 8 号将收入明细与佣金快照一并固化；生成后历史查询使用快照，避免源数据变化导致回看金额改变。
- 销售数据仍按授权范围查询；同时保留 `sale_id` 和 `am_id` 归属。

### 不在范围内

- 不改佣金率、返佣规则、GP、有效收入、成本或佣金金额算法。
- 不改 `wallet` 接口及 `payoutPipeline` 的字段和计算。
- 不把收入行写入现有佣金明细表，不把收入金额混入 `effective_revenue`、`gp` 或 `commission_amount`。
- 不新增产品、渠道的展示名称；响应沿用编码和金额。
- 不调整 Controller 的 Mock/Real 服务委托策略；只在真实服务中实现收入指标来源切换。

## 当前情况

- `SaleCommissionPerformanceVO` 已有 `realTimeProcessing`、`effectiveRevenue`、`cogs`、`gp`、`estimatedCommission` 和 `payoutPipeline`；本次不新增 `totalGeneratedPerformance`。
- 绩效查询服务先判断佣金快照是否存在，再分别读取佣金快照明细或 `mv_sales_commission_recent_estimate`。
- 当前 Mapper 的 `realTimeProcessing` 是 `source_type = 'real_time_processing_fee'` 对应的 `effective_revenue` 汇总。
- 8 号 Flink batch 当前固化 `dws_sales_commission_snapshot_detail_p` 和 `dws_sales_commission_snapshot_p`，没有收入毛额快照。
- 现有佣金明细记录服务于佣金核算；把新收入组成塞入该表会混淆金额语义并影响已有汇总条件。

## 指标口径

### `realTimeProcessing`（前端 Total Generated Performance）

按用户确认的组成汇总：

```text
realTimeProcessing =
    global_account_income
  + main_fee
  + virtual_card_create_fee
  + recharge_fee
  + pc_channel_rebate
  + crypto_connect_income
  + offline_income
  + card_creation_fee
  + month_revenue
  + BB 渠道返现
  + QI 渠道返现
```

金额均按销售/AM、root account、活动月份归属后汇总。渠道返现只纳入 BB 和 QI，避免把未确认纳入本指标的渠道返现扩展进来。客户返现、成本和佣金不作为该 KPI 的独立加项。

- 不增加 `totalGeneratedPerformance` 字段；现有 `realTimeProcessing` 就是此绩效卡片对应的 API 字段。
- 从独立收入数据域统计上表各项实际收入；在同一客户、月份及销售归属下纳入 BB/QI 渠道返现。总额只计算一次，不在服务层再次叠加返现。
- 接口示例中的 `162198.1489` 仅用于说明返回格式，不是固定值或默认值；实际金额由所选月份和授权销售范围动态汇总。
- 保持 `realTimeProcessing` 的 JSON 字段名和数值类型；更新 JavaDoc/Swagger 对其业务含义的说明即可。
- `effectiveRevenue` 继续表示佣金计算口径，不因本次修复改成毛收入。

### 月份字段

- 所有收入行按月粒度存储，`activity_month` 统一记录为该月 1 号（例如 `2026-09-01` 表示整个 2026 年 9 月，不表示仅 9 月 1 日）。
- 普通收入来源按其业务发生/实收日期归属 `activity_month`；BB/QI 源表是日粒度，先按 `report_date` 汇总整月，再将 `activity_month` 记为该月 1 号。
- BB/QI 返现月汇总仍按来源记录中的 `sale_id`、`am_id`、客户和渠道拆分，不把不同销售/AM 的记录合并。
- OpenAPI `month_revenue` 特殊处理：`report_date` 是实际还款月份，用于活动月份归属；源 `settlement_month` 是该笔还款对应的账单月份，作为 `bill_month` 保留，不能用账单月份替代实收月份。
- 对于 8 号快照，快照的 `activity_month` 固定记录被固化的收入月份；快照生成日期单独记录为 `snapshot_date`。

## 收入来源映射

| 收入项目编码 | 来源/字段口径 | 说明 |
|---|---|---|
| `global_account_income` | `dwm.dwm_global_account_sales_revenue_daily`：`deposit_fee`、`payment_fee`、`fx_income` | 三项手续费收入求和；不使用客户返现扣减后的 `main` 作为本指标来源。 |
| `main_fee` | `dwm.dwm_qbit_card_main_fee_sales_detail` | 量子卡主收入。 |
| `virtual_card_create_fee` | `dwm.dwm_qbit_virtual_card_create_fee_sales_detail` | 虚拟卡开卡收入。 |
| `recharge_fee` | `dwm.dwm_qbit_card_recharge_fee_channel_monthly_share` | 账户充值手续费收入。 |
| `pc_channel_rebate` | `dwm.dwm_qbit_card_cash_back_file_up_sales_detail` | 按当前收入项目 SQL 中确认的 `qbit_card_cash_back_file_up_amount` 纳入。 |
| `crypto_connect_income` | `dwm.dwm_crypto_connect_sales_revenue_daily`：`assets_acceptance_fee` | 加密承兑收入。 |
| `offline_income` | `dwm.dwm_bi_month_tag_sales_attribution_detail`：`offline_api_income_amount` | 线下收入。 |
| `card_creation_fee` | `dwm.dwm_qbit_card_wallet_fee_sales_detail`：`card_creation_fee_amount` | 统计实际制卡费收入，不将实体卡成本或实体卡 GP 当成收入。 |
| `month_revenue` | `dwm.dwm_open_api_monthly_revenue_attribution_detail` | 按实际还款日期归属活动月，并保留对应账单月。沿用已确认的收费项纳入/排除清单及实际收款残差算法。 |
| `bb_channel_cashback` | `dws.dws_bb_card_finance_daily_v2_p`：`cashback_income` | 底层 `account_id` 经 `public.api_account_relation` 映射到 `root_id` 后按客户聚合；按 `report_date` 汇总到月初。保留返现记录发生日的 `sale_id`、`am_id`，只计渠道返现，不计客户返现。 |
| `qi_channel_cashback` | `dws.dws_qi_card_finance_daily_v2_p`：`rebate_interchange_base_amt`、`rebate_interchange_rate`、`rebate_incentive_base_amt`、`rebate_incentive_rate` | 底层 `account_id` 经 `public.api_account_relation` 映射到 `root_id` 后按客户聚合；按 `report_date` 汇总到月初。完全沿用用户提供的 QI v2 查询 SQL：Interchange 与 Incentive 的 `base * rate` 相加，且只统计 `special_fee_type IS NULL`。保留返现记录发生日的 `sale_id`、`am_id`，不计入 QI 成本总计。 |

收入来源 SQL 以目录内 `收入项目` 为基础。实施时应将每个来源先聚合到统一粒度，再 `UNION ALL` 汇总，不能在未经预聚合的明细间直接多表 JOIN，以免收入重复放大。

## 数据模型

### 收入物化视图

建议名称：`dws.mv_sales_commission_performance_income_recent`。

视图粒度：

```text
activity_month, root_account_id, product, provider,
income_type, sale_id, am_id
```

建议输出字段：

| 字段 | 用途 |
|---|---|
| `activity_month` | 绩效活动/实收月份，月份月初日期。 |
| `bill_month` | 可空；保留 OpenAPI 的账单月份，和实收月份分开。 |
| `root_account_id` | 顶层客户 ID。BB/QI 来源是底层 `account_id`，需经 `public.api_account_relation` 映射为 `root_id` 后存储；未找到有效映射时保留来源 `account_id`。 |
| `product` | 产品线编码。 |
| `provider` | 渠道/服务商编码，可空。 |
| `income_type` | 本方案收入项目枚举。 |
| `sale_id` / `am_id` | 直接使用各收入来源记录的发生日销售及 AM 归属；不通过当前人员关系重新归属。 |
| `income_amount` | 对应收入项目的金额。 |
| `refreshed_at` | 视图刷新时间，用于排查数据新鲜度。 |

物化视图沿用当前数据库中已验证可维护的 MV 语法和刷新机制；纳入销售佣金与合伙人利润现有 Flink JDBC 串行刷新链路，不启用 `pg_cron`。不能为了增量维护使用数据库不支持的 CTE、非 `UNION ALL` 视图结构；若数据源的维护限制不允许单视图实现，先依据现有环境验证可维护语法，再决定是否拆内部来源视图，API 仍只依赖统一收入视图。

### 8 号收入快照明细

建议新增独立表：`dws.dws_sales_commission_income_snapshot_detail_p`。

建议字段：

| 字段 | 用途 |
|---|---|
| `id` | 稳定明细 ID；按快照日期、活动月、客户、产品、渠道、收入项目及销售归属确定。 |
| `snapshot_date` | 快照生成日期及分区键，通常是每月 8 号。 |
| `activity_month` | 被固化的实收/活动月份。 |
| `bill_month` | OpenAPI 对应账单月；非 OpenAPI 可空。 |
| `root_account_id` | 顶层客户 ID。 |
| `product` / `provider` | 产品线和渠道编码。 |
| `income_type` | 收入项目枚举。 |
| `sale_id` / `am_id` | 固化的销售和 AM 归属。 |
| `income_amount` | 收入金额。 |
| `version`、`remarks`、`create_time`、`update_time`、`delete_time` | 沿用 DWS 快照表审计字段规范。 |

该表不保存佣金率、GP、成本、佣金阶段、销售姓名、客户名称或发薪状态。它与现有佣金快照明细在同一 8 号作业中生成，但单独存储；以免将实际收入和佣金计佣基数混为一谈。接口直接按该明细表汇总，不另建收入汇总主表。主键/索引、年度分区及字段注释在实施 DDL 时参照当前 `dws_sales_commission_snapshot_detail_p` 规范。

### 8 号作业行为

- 在现有 8 号 Flink batch 增加收入物化视图读取和收入快照 sink；收入视图和佣金视图使用同一 `snapshot_date`、同一目标 `activity_month`。
- 同一个 batch / Statement Set 写入三张表：`dws_sales_commission_snapshot_p`（佣金主表）、`dws_sales_commission_snapshot_detail_p`（佣金明细）、`dws_sales_commission_income_snapshot_detail_p`（收入明细）。不增加收入汇总主表；现有佣金主表/明细字段映射不改。
- API 以该活动月份是否已有收入快照数据为切换条件，不按当前销售是否恰好有收入明细行来判断；该月已有快照但所选销售没有匹配明细时返回 0，不回查实时视图。
- 新明细 ID 必须确定性生成，支持同一作业的安全重试。
- 使用现有 sink 的 upsert 行为写入，不在本次方案中设计额外的批次完成标记、部分 sink 恢复或快照纠错版本流程。
- 数据库中的收入物化视图刷新应先成功，batch 再读该视图；记录本次 `refreshed_at` 便于审计快照使用的数据版本。

## 接口与服务改动

### 接口返回

- 保持 `SaleCommissionPerformanceVO` 字段集合不变，不新增 `totalGeneratedPerformance`。
- `realTimeProcessing` 字段映射到上文定义的实际收入总额，供前端 `Total Generated Performance` 卡片使用。
- `clientRebate`、`effectiveRevenue`、`cogs`、`gp`、`estimatedCommission` 和 `payoutPipeline` 均保持现有返回和计算口径。
- 更新 `realTimeProcessing` 的 JavaDoc/Swagger 描述及对接文档；JSON 字段名不变。

### 数据选择

服务层按活动月份独立判断收入快照数据是否已写入，不仅复用佣金快照存在标记，也不按当前 `saleId` 是否有明细行判断：

| 查询状态 | 佣金相关字段 | `realTimeProcessing` |
|---|---|---|
| 该月还没有收入快照数据 | 现有佣金预估视图 | 收入物化视图 |
| 该月已有收入快照数据 | 现有佣金快照明细 | 收入快照明细表；无匹配收入行时为 0 |

如果两类快照暂时不一致，`realTimeProcessing` 只按该月份是否已有收入快照数据选择数据源，不回退到佣金明细伪造收入。该月尚无收入快照时真实服务查询收入物化视图；该月已有收入快照时，即使所选销售没有收入明细也返回 0。同时验证现有非生产环境分支不会把本次真实查询意外短路为空。

### Java / Mapper 变更点

- `SaleCommissionPerformanceVO.java`：保留字段不变，只更新 `realTimeProcessing` 的 JavaDoc 和 Swagger 业务说明。
- `SaleCommissionMapper.java`、`DwsSaleCommissionMapper.java`、`DwsSaleCommissionMapper.xml`：新增收入物化视图和收入快照的简洁聚合查询，以及收入快照存在性查询。
- `SaleCommissionRealServiceImpl.java`：在 `queryPerformance` 中分别选择收入数据源，将该汇总写入现有 `realTimeProcessing`；空结果金额统一补零。
- Mapper SQL 仅做筛选、`SUM(income_amount)` 及简单分类聚合；来源枚举补零和字段合并放在 `SaleCommissionRealServiceImpl`，避免 XML 承载复杂 CASE/枚举补齐逻辑。
- 保留现有查询参数、数据权限校验及销售/AM 数据范围逻辑；不从请求参数放宽可见范围。

## 验收标准

1. `realTimeProcessing` 与核验后的收入分项之和相等，包含 BB、QI 渠道返现且没有重复计算。
2. API 响应字段集合不变；`realTimeProcessing` 取自实际收入数据域，不再直接用佣金视图中的 `effective_revenue` 代表实际收入。
3. 8 号前真实绩效查询读取收入物化视图；收入快照生成后读取收入快照明细。
4. 快照含收入项目级客户明细，销售和 AM 归属可分别查询，客户销售变更不会重写已固化历史。
5. OpenAPI 实收月与账单月分别保留，月份筛选不混用。
6. `clientRebate`、`effectiveRevenue`、成本、GP、预计佣金、发薪管道及其余响应字段均无变化。

## 风险与控制

| 风险 | 控制措施 |
|---|---|
| BB/QI 返现与收入源重复计入 | 源数据逐项对账，明确每个收入项目的包含关系；返现单独保留收入类型。 |
| 客户返现被误当渠道返现 | 只接入确认的 BB/QI 渠道返现来源，不连接客户返现明细。 |
| 多源 JOIN 导致金额膨胀 | 各源先聚合到目标粒度后使用 `UNION ALL`。 |
| root account 映射重复或类型不一致 | 账户关系先唯一化并统一 cast；验证 UUID/varchar 来源及 root 映射覆盖率。 |
| 销售/AM 归属被当前关系覆盖 | 直接复制来源数据中发生日的 `sale_id`、`am_id`，不关联当前销售关系。 |
| 物化视图语法无法增量维护 | 先在目标数据库验证可维护 DDL 和刷新行为，再部署生产刷新任务。 |

## 已确认决策

1. `realTimeProcessing` 对应前端 `Total Generated Performance`，沿用当前字段，按本方案列出的收入项及 BB/QI 渠道返现重算；不新增 API 返回字段。
2. 单独建立收入快照明细表；不扩展佣金明细表，也不建立收入汇总主表。
3. 每月 8 号同一批处理写入佣金主表、佣金明细表和收入快照明细表。
4. 该月尚无收入快照数据时查询收入物化视图；该月已有收入快照数据后查询收入快照明细。判断按月份，不因单个销售没有明细而回查视图。
5. OpenAPI 实收月份按 `report_date`，原账单月份保留在 `bill_month`。
6. QI 渠道返现完全按用户提供的 QI v2 查询 SQL 计算：interchange + incentive 的 base × rate，仅 `special_fee_type IS NULL`，作为返现收入处理。
7. 所有收入来源直接使用其数据中记录的发生日 `sale_id` / `am_id`；不使用客户当前销售归属，也不再关联销售关系表重新分配。

## 实施边界

- 不设计额外的批次完成标记、部分 sink 失败恢复机制或快照纠错/新版本流程。
- 实现时保留收入来源原有的发生日销售/AM 归属字段；不 join 当前销售关系或重新归属。
