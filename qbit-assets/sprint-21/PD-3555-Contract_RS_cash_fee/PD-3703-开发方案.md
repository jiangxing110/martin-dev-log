# PD-3703 合同 RS 返现费率处理开发方案

## 1. 目标

合同中配置 QI 或 BZ 的 RS 毛利返现并映射到账户费率后，确保对应卡组的 Scheme Fee 默认配置写入 `accountFee`。

同一账户同一卡组的 RS 毛利返现与 NR 消费返现不能并存：QI RS 与 QI NR 互斥，BZ RS 与 BZ NR 互斥。

本需求只处理费率配置的生成、读取和持久化，以及互斥校验；不调整 Scheme Fee 金额或 RS 返现金额的计算逻辑。

## 2. 当前代码与参考实现

- 合同费率快照由 `ContractFeeSnapshotAssembler` 将合同申请数据映射为 `ContractAccountFeeVO`；当前 fee type 映射按 `AccountFeeType` 枚举生成，已知的 QI/BZ RS 类型可被识别。
- 合同费率下发由 `ProductFeeDispatchTransactionService.saveAccountFees` 将合同费率转换为 `AccountFee` 并事务性替换同类型记录。这里是评估补充 RS 对应 Scheme Fee 默认费率的主要落点。
- `CashBackJob` 已从返现项目类型中收集 RS 返现费率，并有 QI/BZ RS 的统计映射；统计通过现有账户费率读取触发。无需新增统计侧的卡组费率持久化结构，也不扩展统计数据对象来保存 fee type、provider 或费率区间。
- `ApplyServiceImpl` 处理账户费率申请，与合同创建和下发不是同一链路；本需求合同互斥校验放在合同入口，不修改 `ApplyServiceImpl`。
- 参考项目 `qbitpay_service` 的 `account-business-fee-apply-handler.service.ts` 已有审核通过后创建 RS Scheme Fee 默认费率的处理，可作为费率项、provider、默认区间和替换策略的依据。

## 3. 实施方案

### 任务一：梳理并固定 QI/BZ 默认费率映射

1. 对照参考项目现有 `autoCreateSchemeDefaultFees`，整理 QI、BZ 对应的全部 Scheme Fee `AccountFeeType`、provider、默认 rate、mathType、阶梯区间及生效时间规则。
2. QI 与 BZ 分别按 `QbitIssuing`、`I2c` provider 生成各自默认费率；不得跨 provider 写入。
3. 检查 Assets 当前 `AccountFeeType` 是否已含参考配置涉及的全部类型。已有枚举复用；缺失时再补充枚举和默认 math type 映射。
4. 将映射集中在合同费率下发职责内的私有方法或单一配置协作者，避免在统计服务中复制费率表。

**验收点：**只配置 QI RS 时只生成 QI provider 的完整默认费率；只配置 BZ RS 时只生成 BZ provider 的完整默认费率；两项同时配置时两组独立生成。

### 任务二：合同费率下发时写入默认 Scheme Fee 配置

1. 在 `ProductFeeDispatchTransactionService.saveAccountFees` 中识别当前合同费率列表是否包含 QI/BZ RS 类型。
2. 在合同账户费率保存事务内，按 RS 类型补齐对应渠道的 Scheme Fee 默认 `AccountFee` 记录，确保合同费率与默认费率写入具备原子性。
3. 默认费率的旧记录处理遵循参考项目行为，并严格限定到当前 account、provider 和关联 fee type；不得误删另一卡组、其他 provider 或不相关的人工费率。
4. 重复下发同一合同费率应保持幂等，不产生重复有效配置；合同不再包含某 RS 类型时，按现有合同费率替换语义处理其关联默认配置。
5. 对配置写入失败保留现有事务回滚语义，并记录可定位的 account、contract/apply 与 fee type 信息。

**验收点：**合同下发重试后每组费率只有一份有效配置；QI/BZ 的 provider、阶梯边界和默认值与参考配置一致；任一写入失败时不留下部分更新。

### 任务三：补充合同费率互斥校验

1. 在 `ContractInfoManagerImpl` 的创建、修改和重新发起入口调用 `ContractFeeValidator`，避免非法合同进入持久化或审核流程。
2. 校验本次合同费率清单中的 QI RS/QI NR、BZ RS/BZ NR；同渠道有效期重叠时拒绝，非重叠时允许，QI 与 BZ 之间不互斥。
3. 按账户 ID 查询 `account_fee` 中相关 RS/NR 类型，与本次合同费率做有效期比较；修改路径须在作废 DocuSign envelope 前完成校验。
4. 空起止时间在互斥判断中按无边界处理。

**验收点：**同合同或账户现有费率中，同渠道 RS/NR 有效期重叠时拒绝；有效期不重叠时允许；跨 QI/BZ 渠道允许。

## 4. 主要文件

| 文件 | 计划变更 |
| --- | --- |
| `qbit-core/src/main/java/com/qbit/common_all/contract/manager/impl/ProductFeeDispatchTransactionService.java` | 合同费率下发时按 RS 类型写入对应 Scheme Fee 默认配置，并保持事务和幂等 |
| `qbit-core/src/main/java/com/qbit/common_all/contract/manager/impl/ContractInfoManagerImpl.java` | 合同创建、修改、重启时校验并在 DocuSign 作废前拦截冲突 |
| `qbit-core/src/main/java/com/qbit/common_all/contract/manager/impl/ContractFeeValidator.java` | 校验合同费率与账户现有 AccountFee 的互斥类型和有效期 |
| `qbit-core/src/main/java/com/qbit/common/enums/AccountFeeType.java` | 仅当参考映射涉及的 Scheme Fee 类型缺失时补枚举 |
| 相关单元测试目录 | 覆盖默认配置生成、下发幂等、互斥接受/拒绝路径 |

`CashBackJob` 当前已有 RS 费率触发和 QI/BZ 映射，本需求不新增统计侧费率持久化。实现时只需回归确认现有费率读取链路仍覆盖 RS 类型，不修改统计对象或金额计算链路。

## 5. 验证方案

- 费率映射验证：覆盖 QI、BZ、QI+BZ、无 RS 四种输入，检查生成的类型、provider、费率及区间完整性。
- 下发验证：覆盖首次写入、重复下发、仅更新一个卡组、另一卡组已存在、写入异常回滚。
- 互斥验证：覆盖同组 NR+RS 双向拒绝、跨组并存允许、非重叠有效期允许，以及已有 AccountFee 费率冲突场景。
- 回归确认 `CashBackJob` 仍能基于已存在的账户 RS 返现费率触发 QI/BZ 对应统计；不增加费率配置落库测试。
- 先执行目标测试，再按仓库规范集中运行 `mvn -pl qbit-core -am verify -DskipTests=false` 和 `git diff --check`；若真实数据库场景无法运行，记录为待验收，不以 Mock 代替数据库风险验证。

## 6. 暂定实现边界

- 参考项目的默认费率数值、阶梯区间及 provider 为配置来源；实现前逐项比对，不重新推导数值。
- “默认费率”与账户手工费率冲突时，严格限定替换范围并沿用参考项目策略；若合同下发可能覆盖手工配置，应根据现行数据规则确认。
- 统计侧只沿用审核后写入 `accountFee` 的费率读取，不另存卡组费率配置。
- 不修改 Scheme Fee 金额计算、RS 毛利计算、返现比例或 `cash_back_bonuses.scheme_fee` 的计算/来源。
