## 二、`[P0-BIZ-3]` 毛利返佣有效期半开区间与“月末 23:59:59.999”冲突

### 1. 源码证据对照

系统中关于 `partner_commission_mode.expiration_time` 的**写入标准**与**加点消费标准**高度统一，唯独 `d458f01b45` 新增的毛利返佣判定偏离了该约定：

1. **客户初始化写入**（`PartnerMerchantServiceImpl.java:304-312`，毛利初始化 `doInitializeCustomer` 第 369 行同样调用该方法）：
   ```java
   LocalDate anniversaryMonth = customer.getCreateTime().toInstant()
           .atZone(BUSINESS_ZONE).toLocalDate().plusYears(1);
   Date expirationTime = Date.from(anniversaryMonth.with(TemporalAdjusters.lastDayOfMonth())
           .plusDays(1).atStartOfDay(BUSINESS_ZONE).toInstant().minusMillis(1));
   ```
   统一存为**上海时区（`Asia/Shanghai`）对应月末 `23:59:59.999 +08:00`**。例如注册于 `2025-11-01`，失效时间落库为 `2026-11-30 23:59:59.999 +08:00`（见 `PartnerMerchantGrossMarginWindowTest.java:95-105`）。

2. **后台修改有效期写入**（`CustomerCommissionModeService.java:71-72, 101-113`）：
   校验 `expirationTime` 必须是上海时区当月或之后的月末日期，并同样规范化落库为 `expirationDate.plusDays(1).atStartOfDay(BUSINESS_ZONE).toInstant().minusMillis(1)`（即当月末 `23:59:59.999 +08:00`）。

3. **加点分佣有效期判断**（`PartnerCommissionFeeTransactionService.java:249-256`）：
   ```java
   return !createTime.before(commissionMode.getEffectiveTime())
           && !createTime.after(commissionMode.getExpirationTime());
   ```
   采用**闭区间 `[effectiveTime, expirationTime]`**，`2026-11` 整月交易全部计佣。

4. **毛利返佣有效期判断（Bug 位置）**（`PartnerGrossMarginCommissionServiceImpl.java:230-242`）：
   ```java
   YearMonth effectiveMonth = YearMonth.from(mode.getEffectiveTime().toInstant()
           .atZone(BUSINESS_ZONE).toLocalDate());
   YearMonth expirationMonth = YearMonth.from(mode.getExpirationTime().toInstant()
           .atZone(BUSINESS_ZONE).toLocalDate());
   return !settlementMonth.isBefore(effectiveMonth) && settlementMonth.isBefore(expirationMonth);
   ```

### 2. 边界推演与口径演变说明（为何会误以为存“次月 01 日 00:00:00”）

- **Git 历史核查（提交 `c27ed49a5e` / PR `#7994`，2026-11-19）**：
  - 在 `#7994` 之前，老初始化逻辑只是简单在 `customer.getCreateTime()` 上 `add(Calendar.YEAR, 1)`，并未规整到月初或月末；
  - 在 `#7994` 中，后端将客户初始化（`PartnerMerchantServiceImpl.initializeCustomerCommissionModeWindow`）与后台有效期修改（`CustomerCommissionModeService.update`）**全部统一为上海时区当月末 `23:59:59.999 +08:00`**；
  - 值得注意的是：实现代码写法是先计算**次月 1 日 `00:00:00 +08:00`**（`lastDayOfMonth().plusDays(1).atStartOfDay(BUSINESS_ZONE)`），**紧接着执行了 `.minusMillis(1)` 退回当月末 `23:59:59.999 +08:00`**，且 `CustomerCommissionModeService.validateExpirationTime` 硬校验前端必须传**月末日期**（传月初 01 号会被 400 拒绝）。
  - 因此如果毛利计算侧按“存次月 01 日 00:00:00 的半开区间 `[生效月, 失效月)`”来理解并截断为 `YearMonth`，就会和 `#7994` 实际落库的 `月末 23:59:59.999` 发生错位。
- **测试环境抓包与落库实测验证（已确认）**：
  - 接口：`POST /api/admin/partner/customer/commission-mode/update`
  - 前端请求实传：`"expirationTime": "2027-12-31T23:59:59+08:00"`
  - 服务端处理：`CustomerCommissionModeService.validateExpirationTime` 仅提取上海时区日期 `2027-12-31`（忽略前端秒级时分秒），随后 `update` 通过 `expirationDate.plusDays(1).atStartOfDay(BUSINESS_ZONE).toInstant().minusMillis(1)` 统一补齐到当天最后 1 毫秒（避免加点分佣毫秒级闭区间 `!createTime.after(expirationTime)` 在 `.001~.999` 漏算）；
  - 数据库实存（PG `timestamptz` 按 UTC 展示）：`2027-12-31 15:59:59.999000 +00:00`（等价于上海时区 `2027-12-31 23:59:59.999 +08:00`）。
- **错误推演（以实测落库值为例）**：
  - 实测库内值 `2027-12-31 15:59:59.999 +00:00` 转上海时区为 `2027-12-31 23:59:59.999 +08:00`，截断为 `YearMonth` 得到 `expirationMonth = 2027-12`。
  - 现网代码执行 `settlementMonth = 2027-12` 结算时：`2027-12.isBefore(2027-12)` 返回 **`false`**，2027-12 整月返佣被排除归零；
  - 改为月区间交集后：`2027-12` 的 `monthStart = 2027-11-30 16:00:00 +00:00`（命中 `true`），`2028-01` 的 `monthStart = 2027-12-31 16:00:00 +00:00`（不晚于 `monthStart`，返回 `false` 准确失效）。
- **业务后果**：
  - 所有正常到期客户在**最后一个有效月（到期当月）返佣直接被置 0**，少发整整 1 个月返佣；
  - 若后台将当月注册客户的有效期设为当月末，该客户连当月也会被直接归零；
  - 同一客户在同月份下“加点模式有效、毛利模式失效”，口径严重分裂。

### 3. 修复方案评估（同时兼容“本月末 23:59:59.999”与“次月 01 日 00:00:00”）

**推荐方案：使用上海时区结算月 `[monthStart, nextMonthStart)` 与 `[effectiveTime, expirationTime]` 求交集**（相比简单把 `YearMonth` 改成闭区间更安全，且天然兼容两种存储约定）：

```java
private boolean isWithinEffectiveMonth(YearMonth settlementMonth, PartnerCommissionMode mode) {
    if (mode.getEffectiveTime() == null || mode.getExpirationTime() == null) {
        return false;
    }
    Instant effectiveInstant = mode.getEffectiveTime().toInstant();
    Instant expirationInstant = mode.getExpirationTime().toInstant();
    if (effectiveInstant.isAfter(expirationInstant)) {
        return false;
    }
    Instant monthStart = settlementMonth.atDay(1).atStartOfDay(BUSINESS_ZONE).toInstant();
    Instant nextMonthStart = settlementMonth.plusMonths(1).atDay(1).atStartOfDay(BUSINESS_ZONE).toInstant();
    return effectiveInstant.isBefore(nextMonthStart) && expirationInstant.isAfter(monthStart);
}
```

**边界覆盖验证**：

| 场景 | `effectiveTime` (+08:00) | `expirationTime` (+08:00) | `settlementMonth` | 现网结果 | 修复后结果 |
| --- | --- | --- | --- | --- | --- |
| 正常到期月（月末 23:59:59.999） | `2025-11-01 18:00:00` | `2026-11-30 23:59:59.999` | `2026-11` | `false`（漏发） | **`true`** |
| 到期次月 | `2025-11-01 18:00:00` | `2026-11-30 23:59:59.999` | `2026-12` | `false` | **`false`** |
| 历史脏数据存次月 1 日 00:00 | `2025-11-01 00:00:00` | `2026-12-01 00:00:00.000` | `2026-11` | `true` | **`true`** |
| 历史脏数据存次月 1 日 00:00 | `2025-11-01 00:00:00` | `2026-12-01 00:00:00.000` | `2026-12` | `false` | **`false`**（不会多发） |
| 生效前月份 | `2025-11-15 10:00:00` | `2026-11-30 23:59:59.999` | `2025-10` | `false` | **`false`** |
| 倒挂异常数据 | `2026-12-01 00:00:00` | `2026-11-01 00:00:00` | `2026-11` | `false` | **`false`** |

## 三、`[P0-BIZ-4]` 客户维度分组后 `saveGroup` 循环 `upsert` 与 32-bit `stableId` 碰撞（拆分核实）

### 1. 数据粒度核实与历史成因

对照 `PartnerGrossMarginProfitMapper.xml:21-57` 的 `selectSnapshotRows` SQL：
- `s.product` 到 `product_line_type` 是严格 **1:1 映射**（`qbit_card` / `crypto` / `group_account` 各自唯一映射）；
- 三层 JOIN（`s.root_account_id -> account c` → `c."referralCodeId" -> "referralCode" r` → `r."accountId" -> account p`）均按主键多对一关联，**不会引入行膨胀**；
- 因此，**只要 DW 源表 `dws.dws_partner_account_profit_snapshot_p` 的唯一粒度为 `(snapshot_date, settlement_month, root_account_id, product)`，在线上正常数据下，同一 `(partnerId, accountId, productLineType)` 分组确实只会有 1 行**。

但在提交 `d458f01b45` 之前，`BusinessKey` 定义为 `(partnerId, productLineType)`（不含 `accountId`），同组包含多个客户的多行快照，因此当时设计了 `allocate(rows, commission)` 和 `for (row : rows)` 循环 `upsert`。`d458f01b45` 将 `BusinessKey` 细化为 `(partnerId, accountId, productLineType)`（第 286 行）后，未同步清理旧的拆分与循环写入逻辑，留下了以下两类不同性质的问题：

### 2. 分层缺陷拆解

#### 缺陷 A（条件触发 / 防御性缺陷）：同组多行快照覆盖错账 + `allocate()` 死逻辑
- **正常数据下是否触发**：若 DW 源表按 `(snapshot_date, settlement_month, root_account_id, product)` 严格唯一，每组 `rows.size() == 1`，`for (row : rows)` 只执行 1 次，**正常数据下不会触发同组覆盖错账**（故该子项实际属于**历史残留死逻辑 + 防御性缺陷**，并非正常跑批必现的 P0）。
- **异常/演进触发条件**：一旦未来 DW 源表增加更细粒度维度（如币种、子渠道）或某次 ETL 异常写入重复行，导致同组出现 2 行及以上快照（如 `+1000` 和 `-200`）：
  - 上半段（第 153-156 行）按多行语义将毛利 `reduce` 汇总为 `+800` 并算出返佣 `+80`；
  - 下半段（第 170-187 行）仍遍历 `for (PartnerGrossMarginProfitRow row : rows)`，每次用相同主键 `(id, snapshot_date)` 执行 `ON CONFLICT (id, snapshot_date) DO UPDATE`，第 2 行直接覆盖第 1 行的 `gross_profit`，最终落库为 `gross_profit = -200, commission_amount = +80`（毛利与返佣错账），且 `success += entry.getValue().size()` 会虚报成功数。
- **`allocate()` 彻底冗余**（第 244-275 行）：同组仅 1 个 `accountId`，先拆行分摊再 `result.merge(row.getAccountId(), amount, BigDecimal::add)` 全合并回同一 `accountId`，既无业务意义又徒增维护迷惑与舍入分支。

#### 缺陷 B（即使 1 组 1 行也真实存在的高风险）：`stableId()` 32-bit 哈希碰撞与负数漏洞
在 `PartnerGrossMarginCommissionServiceImpl.java:277-280`：
```java
private long stableId(LocalDate snapshotDate, LocalDate settlementMonth,
                      String partnerId, String accountId, String productLineType) {
    return Math.abs(Objects.hash(snapshotDate, settlementMonth, partnerId, accountId, productLineType));
}
```
- **与“同客户是否多行”无关**：即使每个 `(partnerId, accountId, productLineType)` 严格只有 1 行，`Objects.hash(...)` 返回的仍是 32 位 `int`（正整数空间仅 $2^{31} \approx 2.1 \times 10^9$）。按生日悖论，在约 **5 万条记录**规模下，**不同客户之间**的 5 元组就有 50% 概率撞出相同 `id`；一旦同属同一 `snapshot_date`，`ON CONFLICT (id, snapshot_date) DO UPDATE` 会**静默把客户 A 的返佣记录覆盖成客户 B 的数据**，且不会抛任何异常。
- 若 `Objects.hash(...) == Integer.MIN_VALUE`（`-2147483648`），`Math.abs(int)` 因整型溢出仍返回负数 `-2147483648L`。

### 3. 修复方案与历史数据兼容性提醒

1. **删除 `allocate()`，每个 `(partnerId, accountId, productLineType)` 分组只构建并写入 1 条聚合记录**：
   - `grossProfit` 写入聚合后的 `defaultValue(customerProductLineGrossProfit)`；
   - `commissionBeforeFloor` 与 `commissionAmount` 写入 `defaultValue(commission)`；
   - `successCount` 按实际保存的分组数（`+1`）累计，而非快照行数。
2. **替换 32-bit `stableId` 时的数据库兼容注意点（务必在改前确认）**：
   - **优先方案（推荐）**：检查 `partner_gross_margin_commission_p` 分区表 DDL，确认是否存在或可建立 `(snapshot_date, settlement_month, partner_id, account_id, product_line_type)` 业务唯一索引；若存在，将 `upsert` 的 `ON CONFLICT` 目标改为该业务唯一键（`id` 改为正常 64-bit 确定性哈希或雪花 ID），从根源彻底消除哈希碰撞。
   - **过渡方案**：若表结构短期只能按 `(id, snapshot_date)` 冲突更新，则将 `stableId` 升级为基于 SHA-256 截取 63 位正 `long`（`hash & Long.MAX_VALUE`，碰撞空间 $2^{63}$），但需注意：**升级后重跑历史已有 `snapshot_date` 时，新旧 `id` 不同会产生重复记录**；因此只应在新快照日期生效，或对历史快照重算前先清理旧 `snapshot_date` 下的旧记录。

## 四、`[P1-PERF-2]` N+1 雪崩 + 无分批 IN + 双连接池占用 + 大事务内同步 Feign HTTP

### 1. 子问题 A：配置查询 N+1 雪崩（2000 户 × 2 产品线 = 16,000+ SQL）

- **调用链**：
  `PartnerGrossMarginCommissionServiceImpl.calculate()`（第 117 行循环 `groups`）
  → `saveGroup()`（第 157 行）
  → `configService.queryEffectiveConfig(partnerId, accountId, productLineType)`（`PartnerGrossMarginConfigServiceImpl.java:166-199`）
- **单次调用 SQL 拆解**：
  1. `partnerGrossMarginConfigMapper.selectList(...)` — 查单组配置主表
  2. `partnerGrossMarginConfigDetailMapper.selectList(...)` — 查单组梯度明细
  3. `fillAccountDisplayInfo(...)` → `accountMapper.selectBatchIds(...)` — **无用查询**（计算完全不使用客户名、合伙人名、displayId）
  4. `fillModeWindows(...)` → `partnerCommissionModeMapper.selectList(...)` — **重复且无用查询**（外层 `queryEligibleGrossMarginCustomerIds` 已经查过模式表，且计算逻辑不使用 VO 中的 `effectiveTime`）
- **放大效应**：单合伙人或全量任务有 2,000 客户 × 2 产品线 = 4,000 分组时，单次任务发出 **16,000+ 条 SQL**（外加 4,000 次单条 `upsert`，合计 20,000+ SQL）。
- **修复方向**：
  - 保留 `PartnerGrossMarginConfigService.queryEffectiveConfig(...)` 不变，避免影响对外 Feign 接口 `PartnerCommissionFeign.getGrossProfitConfigDetail`（`PartnerCommissionFeign.java:93`）及 `PartnerGrossMarginConfigModeWindowTest`；
  - 新增专用于返佣计算的轻量批量加载协作者（例如 `PartnerGrossMarginConfigLoader`）：
    - 按 `partnerId` 分组，对每个 `partnerId` 的 `accountIds` 按 **500/批** 分批查 `partner_gross_margin_config`（按 `create_time DESC, id DESC` 排序，内存中同键 `putIfAbsent` 取最新）；
    - 将命中的 `configId` 按 **500/批** 分批查 `partner_gross_margin_config_detail`（按 `ladder_min_amount ASC` 排序）；
    - **完全不查 `account` 表和 `partner_commission_mode` 表**。
  - **预期收益**：2,000 户 × 2 产品线配置查询从 **16,000+ SQL 降至 ~12 条 SQL**（4 条主表 + 8 条梯度表）；若同步配合 `batchUpsert`（500 条/批），写入 SQL 从 4,000 条降至 8 条。

### 2. 子问题 B：`queryEligibleGrossMarginCustomerIds` 无分批 `.in(...)`

- **位置**：`PartnerGrossMarginCommissionServiceImpl.java:198-221`
  ```java
  return partnerCommissionModeMapper.selectList(new LambdaQueryWrapper<PartnerCommissionMode>()
                  .in(PartnerCommissionMode::getAccountId, customerIds)
                  .eq(PartnerCommissionMode::getCommissionMode, PartnerCommissionModeEnum.GrossProfitShare))
  ```
- **风险**：全量跑所有合伙人时，所有客户 ID 一次性塞入单条 `IN (...)`。PostgreSQL wire protocol 单条语句绑定参数硬上限为 **32,767**（`Short.MAX_VALUE`），超过直接报 `Tried to send an out-of-range integer as a 2-byte value` 导致整个月度结算任务崩溃。
- **修复方向**：按 `IN_QUERY_BATCH_SIZE = 500` 对 `customerIds` 分片循环查询，合并符合有效期的客户 ID 集合。

### 3. 子问题 C：`NOT_SUPPORTED` 双连接池占用 + 外层大事务内同步 Feign HTTP

#### 现状调用链（问题全景）

```text
 └── for (partnerAccountId : partnerAccountIds)

      ├── withdrawalPauseMapper.selectByAccountId(partnerAccountId)      [db1]
      ├── calculationService.calculate(param)
      │    ├── grossMarginCommissionService.calculate(param)             [@Transactional(REQUIRED) 加入外层 db1 事务]
      │    │    └── snapshotReader.readSnapshotRows(...)                 [@DS("dw1") + @Transactional(NOT_SUPPORTED)]
      │    │          >>> 挂起外层 db1 事务(db1 连接不归还池!) + 借用 dw1 连接 = 双连接池同时占用! <<<
      │    │    └── queryEligibleGrossMarginCustomerIds + 16,000+ SQL    [db1]
      │    └── feeTransactionService.processTransactions(...)            [@Transactional(REQUIRED) 加入外层 db1 事务]
      ├── buildPushRequest(param) -> commissionFeign.query...            [db1 本地查询]
      └── pushClient.pushBatch(request)                                  [同步 Feign HTTP! 在大事务内!]
            >>> 若第 50 个合伙人失败：前 49 个远程已入账，本地 db1 事务全部回滚 -> 跨服务账务不一致! <<<
```

#### 两个核心故障机理
1. **双连接池耗尽（`db1` + `dw1`）**：
   Spring 的 `Propagation.NOT_SUPPORTED` 在挂起外层 `db1` 事务时，只是把 `db1` 的 `ConnectionHolder` 从当前线程 `ThreadLocal` 暂存到 `SuspendedResourcesHolder`，**物理数据库连接并未归还 `db1` 连接池**。随后进入 `dw1` 数据源再借用一条数仓连接执行慢查询，造成单线程同时锁死两条跨库连接。并发跑批或 DW 查询变慢时，极易打满主库 `db1` 连接池，拖垮线上核心业务。
2. **违反 No HTTP In Transaction & 跨服务账务撕裂**：
   - `pushClient.pushBatch(request)` 位于 `PartnerMonthlyCommissionSyncServiceImpl.sync()` 的外层 `@Transactional` 内部，网络抖动/超时直接拉长本地数据库事务与锁持有时间；
   - 一旦循环到第 $k$ 个合伙人时远程超时、网络中断或 `validateBatchResponse` 契约校验抛异常：
     - **远程 `interlace_partner_service`**：第 $1 \dots k-1$ 个合伙人的批次已通过 HTTP 持久化入账；
     - **本地 `qbit-assets`**：由于外层是单一 `@Transactional`，异常触发整个 `db1` 事务回滚，第 $1 \dots k-1$ 个合伙人的 `partner_gross_margin_commission_p`、`partner_commission_fee_transaction` 以及 `account_fee_transaction.is_commission = true` 全部被撤销！
     - 下次重跑时，前 $k-1$ 个合伙人因 `is_commission` 被回滚回 `false` 会重新生成加点佣金交易，造成本地账务与远程账务彻底错乱。

#### 改造后目标调用链

```text
PartnerMonthlyCommissionSyncServiceImpl.sync(param)   [无外层 @Transactional]
 └── for (partnerAccountId : partnerAccountIds)
      ├── 快速前置校验: accountMapper.selectById + withdrawalPauseMapper.selectByAccountId  [无事务只读，暂停直接跳过]
      ├── calculationService.calculate(param)         [无外层事务]
      │    ├── grossMarginCommissionService.calculate(param)  [无外层 @Transactional]
      │    │    ├── 阶段1(无事务, @DS("dw1")): snapshotReader.readSnapshotRows  [仅占 dw1，用完即还，零 db1 占用]
      │    │    ├── 阶段2(无事务, db1只读): 分批 IN 查有效期 + 批量加载轻量配置 + 内存计算聚合
      │    │    └── 阶段3(短事务 TransactionTemplate): 见下方 P0-BIZ-5 行锁复查 + batchUpsert 短事务提交
      │    └── feeTransactionService.processTransactions(...) [独立事务提交该合伙人加点分佣，内部已有行锁复查]
      ├── buildPushRequest(param)                     [无事务只读查询已提交的三种返佣明细]
      └── pushClient.pushBatch(request)               [完全在事务外发起 Feign HTTP 推送]
            >>> 失败恢复：前 k-1 个本地与远程均已提交且一致；第 k 个本地已幂等落库，重跑时前 k-1 命中 RESULT_DUPLICATE，第 k 个补推成功 <<<
```

## 五、关联延伸：`[P0-BIZ-5]` 删去 `selectByIdForUpdate` 破坏暂停互斥锁及与 `[P1-PERF-2]` 的协同设计

第二张截图底部露出的一条问题已在代码中核实：

- **源码事实**：
  - 在 `b2b1d712b0`（PD-2638）中，为避免管理员执行暂停提现（`PartnerMerchantServiceImpl.java:581` 对 `account` 行加 `selectByIdForUpdate`）与月度返佣生成并发交错，原实现在 `PartnerMonthlyCommissionSyncServiceImpl.sync()` 加了 `@Transactional` + `accountMapper.selectByIdForUpdate(partnerAccountId)`。
  - `d458f01b45` 将 `PartnerMonthlyCommissionSyncServiceImpl.java:66` 改成了 `accountMapper.selectById(partnerAccountId)`，不仅**破坏了暂停写入与毛利落库的互斥保护**，还直接导致 `PartnerMonthlyCommissionPauseGuardTest.java` 中全部 12 个 mock/verify `selectByIdForUpdate` 的单元测试报错。
- **关键架构权衡（为什么不能简单把 `selectByIdForUpdate` 还原回 `sync()`）**：
  - 如果直接还原 `sync()` 的 `@Transactional` + `selectByIdForUpdate`，又会立刻重新触发 `[P1-PERF-2]`（长事务锁 `account` 行 + 循环挂起 `db1` 查 `dw1` + 事务内发 Feign HTTP，而且锁着 `account` 行发 HTTP 还会导致该合伙人的其他账户写操作全被行锁阻塞）。
- **推荐协同设计（兼顾互斥安全与短事务/无 HTTP 持锁）**：
  1. **入口快筛（无事务）**：`sync()` 循环开始先查 `accountMapper.selectById` 和 `withdrawalPauseMapper.selectByAccountId`，已暂停直接跳过（连 DW 和加点都不算）。
  2. **毛利落库短事务加行锁复查**：在 `PartnerGrossMarginCommissionServiceImpl` 阶段 3 的 `TransactionTemplate` 短写事务内：
     - 先执行 `accountMapper.selectByIdForUpdate(partnerId)` 锁住合伙人账户行；
     - 再复查 `withdrawalPauseMapper.selectByAccountId(partnerId)`，若并发期间刚被暂停则直接放弃落库并立即释放锁；
     - 未暂停则快速执行 `batchUpsert` 后立刻提交释放行锁（整个持锁时间压缩到毫秒级，无 DW、无 HTTP）。
  3. **加点分佣已具备同等保护**：`PartnerCommissionFeeTransactionService.java:222-232` 在其 `@Transactional` 内本来就已对 `partnerAccount` 执行 `selectByIdForUpdate` + 暂停复查。
  4. **推送前轻量复查 + 远程兜底**：`pushClient.pushBatch` 前可再查一次 `withdrawalPauseMapper`，即便在毫秒窗口内刚好发生暂停，远程 `interlace_partner_service` 也会返回 `RESULT_SKIPPED_PAUSED`（`reasonCode=WITHDRAWAL_PAUSED`）拒绝入账。
  5. **单测对齐**：同步更新 `PartnerMonthlyCommissionPauseGuardTest` 与新增 `PartnerGrossMarginCommissionServiceImplTest`，把互斥行锁的验证落到真正持锁的短写事务边界上（而非外层 HTTP 同步编排层）。
