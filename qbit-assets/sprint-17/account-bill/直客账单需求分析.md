# 直客账单需求分析

> 分析对象：直客月结账单需求及其关联的 API 月账单、返现、Net 轧差历史需求。
>
> 输出日期：2026-09-17
>
> 说明：本文用于开发评审和任务拆分。需求原文中的历史时间节点、版本切换日期和部分名称存在差异，本文会明确标注待确认项，不将其直接视为最终实现口径。

## 1. 需求结论

本需求的核心不是重新开发一套直客账单，而是将直客月结费用接入现有 API 客户账单体系，统一复用以下能力：

1. 月结费用账单生成和费用明细。
2. 返现账单生成和返现明细。
3. 月账单与返现账单的 Net 轧差计算。
4. Admin 账单查询、复核、导出和异常调整。
5. Merchant 客户端账单查看、明细下载、还款和还款记录。
6. 账单、轧差、扣款结果对应的邮件和站内信通知。

需要新增或保留的主要差异只有两类：

- 账单复核：直客账单生成后自动复核，操作人记录为 `System`；API 客户继续走原人工复核流程。
- 轧差扣款：直客从量子账户透扣，余额允许扣为负数；API 客户沿用现有逻辑，只扣可用余额，不足部分进入待还款流程。

## 2. 背景与目标

### 2.1 当前问题

直客月结费用目前走待办事项和独立扣款流程，API 客户则使用月账单、返现和 Net 轧差流程。两套流程导致：

- 财务需要维护两套账单和扣款口径。
- 直客无法完整复用客户端账单查询和还款能力。
- 账单、返现、轧差的金额和状态难以统一核对。
- 直客原有活跃卡扣费通知与统一账单通知可能重复或口径不一致。

### 2.2 需求目标

| 目标 | 验收结果 |
|---|---|
| 统一账单能力 | 直客和 API 客户均能生成月结账单、返现账单和 Net 轧差记录 |
| 统一账单入口 | Admin 使用“客户账单”一级菜单；Merchant 直客开放“账单”菜单 |
| 账单可追溯 | 账单、费用明细、返现、轧差和实际扣款能够相互关联 |
| 扣款差异化 | 直客可透扣为负；API 客户不足部分进入还款流程 |
| 通知统一 | 直客停止原“账户活跃卡扣费通知”，改用统一账单/轧差通知 |

## 3. 业务范围与不在范围内的内容

### 3.1 本次范围

- 直客月结费用接入 API 月账单生成链路。
- 直客账单自动复核并记录系统操作人。
- 直客参与返现和 Net 轧差流程。
- 直客 Merchant 端账单权限和页面能力开放。
- Admin 菜单迁移、命名调整和客户类型过滤放开。
- 统一明细下载、0 金额费用项过滤、Active Card Details 展示。
- 轧差结果的直客透扣和 API 客户原有不足额扣款逻辑。
- 统一邮件、站内信及中英文通知。
- 财务对账单和差额订单在 20 日后的受控调整能力。

### 3.2 暂不应默认扩大的范围

- 不重新设计现有 API 客户账单表结构，除非确认无法表达直客身份或客户类型。
- 不改变既有费用计算公式、返现标准和客户报价规则。
- 不删除历史账单或重算历史月份，除非另有数据修复方案。
- 不把 OpenAPI V3 的 `collection_fee_settlement` 返现账单与 API 客户 `api_client_bill` 的 `Rebate` 账单混为同一模型。
- 不将客户端历史账单强制迁移到新 Net 展示口径，需按版本切换规则兼容历史数据。

## 4. 现有账单模型与目标模型

### 4.1 现有核心对象

| 对象 | 作用 | 本次处理 |
|---|---|---|
| `api_client_bill` | 月结账单和返现账单主记录 | 复用；需要能识别客户类型和账单类型 |
| `api_client_bill_statement` | 月账单费用明细 | 复用；月结费用按统一口径写入 |
| `cash_back_bonuses` | 返现业务明细 | 复用；毛利返现必须能进入账单总额和明细 |
| `api_client_netting_bill` | 月账单与返现轧差结果 | 复用；直客和 API 客户均生成 |
| `api_client_debit_record` | 实际扣款/返现落地记录 | 复用；保留扣款来源和客户类型差异 |
| `bill_history_config` | 账单生成时的配置和明细快照 | 必须保留，支持账单调整后追溯和重新生成 |

### 4.1.1 表名兼容性决策

本次需求不建议重命名上述带有 `api_client` 前缀的表、字段或历史枚举。原因是这些名称已经不只被 Java 代码使用，还可能被以下链路直接依赖：

- Flink 作业和实时/离线 SQL。
- BI、对账、财务报表和数据仓库同步任务。
- 定时任务、脚本、数据修复脚本和监控告警。
- 客户端、网关或其他服务使用的接口字段和导出字段。

直接改名会把本次直客账单需求扩大为跨系统数据库迁移，容易造成历史数据断链、Flink 任务失败、报表口径变化和双写不一致。

推荐采用“物理名称保留、业务语义泛化”的方式：

1. 数据库继续使用现有表名，直客通过账户关系或客户类型参与同一账单流程。
2. 新增代码中的 Service、DTO、VO、文档和菜单使用更通用的 `CustomerBill`、`CustomerNettingBill` 等业务命名，避免继续扩大 `ApiClient` 语义。
3. 如果必须新增字段，优先增加客户类型、来源系统、账单来源等兼容字段，不改变既有字段含义。
4. 对外接口和导出字段先保持兼容；需要改名时采用新增字段、灰度双读/双写、下游迁移、观察期和最终废弃的分阶段方案。
5. Flink 和数据平台如果需要统一命名，优先新建逻辑视图、宽表或下游别名，不直接重命名源表。

只有在完成全量依赖盘点、下游迁移、历史回放校验和回滚方案后，才考虑下一阶段的物理表重命名；该工作不属于本次直客账单需求的必要范围。

### 4.2 账单金额口径

本次直客月结费用的首要来源应为新费率系统的 `account_fee_transaction`。该表中的 `deduction_node = 'monthly'` 表示费用进入月结节点，`fee`、`collection_fee`、`status`、`is_settled` 等字段分别用于金额和结算状态判断。

但当前客户并未全部迁移到新费率系统，因此不能只查询 `account_fee_transaction`。账单生成时需要分别查询两套来源：

1. 新费率系统：查询 `account_fee_transaction` 中属于账单周期、`deduction_node = 'monthly'` 且尚未结算的费用。
2. 旧费率系统：继续查询原有 API/直客费用来源和待收月结记录，覆盖尚未迁移客户。
3. 统一标准化：将两套结果转换为统一的月结费用对象，再按账户、费用类型、业务来源和原始费用记录合并。
4. 去重和防漏：不能简单把两次查询结果直接相加，必须使用稳定业务键去重，并保留来源系统和原始记录 ID，方便对账。

推荐的统一费用记录至少保留以下信息：

| 字段 | 用途 |
|---|---|
| `account_id` | 归属客户 |
| `source_system` | `NEW_RATE` 或 `LEGACY_RATE` |
| `source_id` / `transaction_id` | 防重复和追溯原始费用 |
| `fee_id` / `fee_name` | 费率和展示名称 |
| `deduction_node` | 确认是否进入月结 |
| `fee` / `collection_fee` | 区分客户应收和代收金额 |
| `status` / `is_settled` | 防止重复计入已结算费用 |
| `billing_period` | 归属账单月份 |

月账单金额应由账单周期内未收的月结费用和其他只能月结的费用组成，包括但不限于：

- 交易手续费和渠道费用。
- 月低消、活跃卡费、非活跃卡费。
- 交易失败费、身份验证费。
- 最低交易量承诺费。
- 制卡费、邮寄费、退款手续费、ATM 取现手续费等已纳入月结的费用。
- 财务调账和手工增加费用。

账单明细金额应统一遵循：

```text
有效金额 = adjust_amount 非空时取 adjust_amount，否则取 amount
```

计算、列表、PDF、CSV/ZIP 和客户端展示必须使用同一有效金额口径。金额为 0 的费用项应过滤展示，但不能因过滤展示行而错误改变账单总额。

## 5. 目标业务流程

### 5.1 月结账单生成

```text
账单周期结束
    ↓
获取直客和 API 客户的月结费用
    ↓
按账户、账单月生成 MonthlyStatement
    ↓
写入费用明细、历史配置快照和明细 ZIP
    ↓
按客户类型处理复核
    ├─ 直客：自动复核，操作人 = System
    └─ API 客户：沿用人工复核
    ↓
账单达到可展示条件后，开放客户端查询/下载
```

直客不应继续走“待办事项月度扣款”作为主流程。旧流程需要停止或改造成兼容层，避免同一账单被旧任务和新账单任务重复扣款。

### 5.1.1 月结账单和返现账单的生成时机

月结账单和返现账单是两个独立的生成任务，均先写入 `api_client_bill`，通过 `type` 区分：

| 账单 | 类型 | 当前代码入口 | 作用 |
|---|---|---|---|
| 月结账单 | `MonthlyStatement` | `ApiCustomerJob.billJobHandler()` → `apiClientBillService.initBill()` | 汇总账单周期内应收的月结费用 |
| 返现账单 | `Rebate` | `ApiCustomerJob.createRebateBillJobHandler()` → `dealCashBackBonusHistoryData()` | 汇总账单周期内客户应得的返现 |

当前代码中还存在按指定客户和账单月份补生成/重跑的任务：

- `create_month_bill`
- `create_rebate_bill`

这两个任务的 Java 代码只定义了 XXL-JOB 执行入口和参数处理，具体每天几点、每月几号执行，需要查看 XXL-JOB 管理后台的 Cron 配置。不能仅根据任务方法名推断最终执行日期。

历史需求资料存在不同时间口径：月结账单出现过每月 1 日、10 日和 15 日，返现账单出现过每月 3 日、5 日和 10 日左右。此次直客需求应先确认最终时间表，但业务顺序不能改变：

```text
生成 MonthlyStatement
    ↓
生成 Rebate
    ↓
两类账单分别完成审核
    ↓
生成 api_client_netting_bill，status = Pending
    ↓
20 日执行轧差扣款/返现
```

20 日是轧差结算和资金落地时间，不应理解为月结账单或返现账单的首次生成时间。

### 5.2 返现账单

返现账单继续使用原返现生成和审核流程，但需要确认直客是否已经具备返现资格及返现配置。返现账单至少应支持：

- 量子卡消费返现。
- 量子卡开卡返现。
- 加密资产交易返现。
- 量子卡毛利/Revenue Sharing 返现。

毛利返现要同时进入：

1. 返现账单总额。
2. 返现 PDF 总额。
3. 返现明细 ZIP 的独立 Sheet：`Infinity Card Revenue Sharing Rebate`。
4. `api_client_netting_bill.rebate_amount`。
5. 客户端返现/Net 展示。

### 5.3 Net 轧差

`api_client_netting_bill` 的产生前提是月结账单和返现账单已经生成，并且满足进入轧差的审核条件。它不是月结费用发生时即时写入，也不是 20 日扣款时才临时创建的唯一记录。

推荐拆成两个动作：

1. 轧差初始化：读取最新且审核完成的 `MonthlyStatement` 和 `Rebate`，计算并写入 `api_client_netting_bill`，初始状态为 `Pending`。
2. 轧差结算：20 日由 `quantum_card_api_customer_netting_bill_debit` 处理 `Pending` 记录，执行扣款、返现或平账，并写入 `api_client_debit_record`。

```text
月结账单金额 billAmount
返现账单金额 rebateAmount
        ↓
netAmount = billAmount - rebateAmount
        ├─ > 0：NettingDebit，需要客户付款/扣款
        ├─ < 0：NettingRebate，需要向客户返现
        └─ = 0：NettingEqual，直接结清
```

轧差记录按客户和账单月计算，不应把多个账单月累加成一个不可追溯的总差额。月账单或返现金额发生允许的变更时，需要重算 `bill_amount`、`rebate_amount`、`amount`、`type` 和相关状态，并记录原差额类型。

### 5.4 轧差扣款差异

| 客户类型 | 扣款规则 | 不足处理 |
|---|---|---|
| 直客 | 从量子账户直接扣除应收差额 | 允许账户余额变为负数，视为扣款成功或按最终状态定义落账 |
| API 客户 | 只扣可用余额 | 扣到 0，剩余金额进入待还款/主动支付流程 |

无论客户类型，扣款记录都必须关联账单月、轧差记录、扣款来源、账户和实际扣款金额。若一个 Net 拆成多笔资产账户交易，交易备注统一标识为“月账单扣款”或系统约定的等价来源。

## 6. 时间与状态设计

### 6.1 当前资料中出现的时间节点

不同历史文档出现以下口径：

| 节点 | 文档中出现的描述 | 处理建议 |
|---|---|---|
| 返现生成 | 每月 3 日或 5 日左右 | 以现有返现任务和最终审核时间为准 |
| 月结账单生成 | 每月 10 日或 15 日 | 本需求主文档写 10 日，但必须与现有任务核对 |
| 客户端展示 | 每月 18 日 | 作为审核通过后的展示节点候选 |
| 支付按钮开放 | 19 日 24:00 | 需确认直客是否同样适用 |
| Net/自动扣款 | 每月 20 日 | 需区分计算、自动扣款和通知三个时刻 |
| 20 日后调整 | 当月 20 日至月底 | 仅允许未结清记录，且不能跨月 |

具体执行日期以 XXL-JOB 管理后台实际配置为准。代码中可确认的是任务入口和处理顺序，不能从 `@XxlJob` 注解本身确认 Cron 时间。

### 6.2 推荐状态流

账单主记录：

```text
生成中 → 待复核 → 已复核 → 可展示 → 待结算 → 部分结算 → 已结清
                         └→ 复核驳回/重新生成
```

轧差记录：

```text
待计算 → 待处理 → 处理中 → 部分结算 → 已结清
                    └→ 重新计算
```

直客自动复核不代表可以跳过账单落库、明细生成和金额校验。自动复核前仍应确保账单金额、费用明细、账户客户类型和账单周期完整。

### 6.3 历史账单兼容

历史月份应继续按原账单展示和支付规则处理。新 Net 规则只适用于明确切换月份之后的账单。切换月份、历史账单查询方式以及历史账单是否生成新入口，需要在开发前固化。

## 7. Admin 端需求

### 7.1 菜单调整

新增一级菜单：`客户账单`。

迁移并更名：

| 原菜单 | 新菜单 |
|---|---|
| 客户管理—客户信息—返现明细报表（新） | 客户账单—返现账单 |
| API客户业务—API客户管理—客户月结账单列表 | 客户账单—月结账单 |
| API客户业务—API客户管理—客户账单查询 | 客户账单—结算账单 |

月结账单和结算账单查询不得继续只过滤 API 客户。查询结果至少应返回客户类型，便于财务区分直客与 API 客户的复核和扣款规则。

### 7.2 月结账单列表

需要支持：

- 按账户、账户名称、客户类型、账单月、复核状态、结算状态和创建时间查询。
- 展示账单总额、扣款方式、复核状态、结算状态、已结算金额、BD、AM、创建时间和更新时间。
- 展示账单明细、费用项明细和账单更新时间。
- 导出查询结果，添加时间范围最多三个自然月。
- 导出字段沿用现有 Excel 模板，直客和 API 客户使用同一导出结构。

### 7.3 财务调整

20 日后调整能力必须受限：

- 只允许调整当月账单。
- 只允许调整未结清订单。
- 已结清订单入口灰显，线下处理。
- 调整任意费用或返现后必须重新计算 Net。
- 重新计算需要同步更新客户端可见差额订单。
- 每一次调整需要记录操作人、操作时间、原值、新值、业务 ID 和原因。
- 需要明确是否暂停系统自动邮件/站内信，由财务人工处理。

## 8. Merchant 客户端需求

### 8.1 权限和菜单

向直客开放“账单”菜单及其全部功能权限，包括：

- 账单列表和月份查询。
- 月结账单/返现账单汇总。
- 费用和返现明细下载。
- Net 差额展示。
- 主动支付。
- 还款记录和交易流水跳转。

### 8.2 展示规则

- 账单只有在满足展示条件后才开放给客户。
- 无账单或无费用时展示明确的 `No fee` 状态，不生成误导性的 0 元账单按钮。
- 0 金额费用项不在 PDF、CSV/ZIP 和页面明细中展示。
- 同时存在月结和返现时展示合并后的 Net，同时保留月账单和返现明细下载入口。
- 直客和 API 客户共享页面和接口契约，但扣款说明文案按客户类型区分。
- 支持中英文通知和账单相关文案。

## 9. 通知需求

### 9.1 停止的通知

直客原有“账户活跃卡扣费通知”站内信和邮件停止发送，避免与统一账单通知重复。

### 9.2 统一通知

至少覆盖：

- 账单生成/可查看。
- 账单或返现审核完成。
- Net 需要扣款。
- Net 需要返现。
- 自动扣款全额成功。
- 自动扣款部分成功或失败。
- 存在待还款金额的周期性提醒。
- 20 日后账单调整导致 Net 更新。

通知内容必须带账单月、账户、账单或轧差业务 ID、金额、状态和客户端入口。对直客应明确“量子账户可能透扣为负”，对 API 客户应引导主动还款。

## 10. 数据、接口和实现影响

### 10.1 数据层

优先复用现有账单表，重点核对：

1. 账单主表是否存在客户类型或可稳定关联账户类型的字段。
2. 新费率系统和旧费率系统的客户迁移范围，迁移边界是账户级、费用类型级还是交易级。
3. 新费率系统 `account_fee_transaction` 的账单月份归属字段和时间口径，不能未经确认直接用 `create_time` 代替业务发生时间。
4. 新旧两套费用来源之间的稳定关联键，至少要确认 `account_id`、`source_id`、`transaction_id`、`business_id` 和 `fee_id` 的可用性。
5. 直客月结费用是否能转换为 `api_client_bill_statement` 明细。
6. 账单类型、账单月和账户唯一性是否能防止重复生成。
7. `bill_history_config` 是否能保存直客账单生成时的配置快照。
8. Net 表是否允许直客没有返现账单时 `rebate_id` 为空。
9. 扣款记录是否能区分直客透扣和 API 客户余额扣款。
10. 账单更新后能否可靠触发 Net 重算且保证幂等。

双查询必须具备以下保护：

- 同一客户同一账单月不能因为新旧系统同时返回同一笔费用而重复入账。
- 已经进入历史月结账单或已结算的旧系统记录不能再次计入。
- 新系统查询失败时不能静默使用旧系统结果生成“看似完整”的账单，应阻断或标记账单生成失败。
- 两套来源的查询结果应落入统一的待结算快照，后续重算使用快照和明确的来源记录，而不是每次无条件重新抓取。
- 账单明细应保留来源系统字段，便于财务回答“这笔费用来自哪套费率系统”。

### 10.2 服务层

建议按以下用例拆分：

- `MonthlyBillGenerationService`：统一生成月结账单。
- `BillReviewService`：按客户类型执行自动复核或人工复核。
- `NettingCalculationService`：计算和重算月度 Net。
- `SettlementDebitService`：封装直客透扣和 API 客户余额扣款差异。
- `BillAdjustmentService`：处理 20 日后的账单/返现调整、日志和通知。
- `BillExportService`：PDF、CSV/ZIP 和 Admin Excel 导出。

服务只负责编排，费用明细组装和 VO 转换应集中到独立 Converter/Assembler，避免在门面中混合远程调用、权限判断和对象转换。

### 10.3 接口层

Admin 与 Merchant 应尽可能共用账单领域服务，但保留各自的权限边界和返回对象。接口至少需要覆盖：

- 账单分页查询。
- 账单详情和费用明细查询。
- 返现账单详情查询。
- Net 差额查询。
- PDF、CSV/ZIP 下载。
- 主动支付/还款。
- 还款记录查询。
- Admin 调账、重新计算和重新返现。
- 月结账单列表导出。

所有修改类接口必须校验当前用户权限、账单状态、客户类型、账单月份和幂等条件，不能信任请求体中的账户身份。

## 11. 关键异常与幂等要求

| 场景 | 处理要求 |
|---|---|
| 同一客户同一账单月重复生成 | 保证幂等；明确最新账单标记和旧版本可见性 |
| 直客旧任务与新任务同时执行 | 旧任务停用或增加互斥/状态校验，禁止重复扣款 |
| 直客自动复核时明细未生成 | 不应进入可展示或结算状态，记录可定位日志 |
| 返现账单缺失 | 按“仅月结”场景计算，不应错误阻塞月结账单展示 |
| 月结账单缺失 | 按“仅返现”场景处理，Net 不应生成错误扣款 |
| 账单金额变更后 Net 已结清 | 禁止自动改已结清订单，进入财务线下处理 |
| 自动扣款部分成功 | 记录应扣、实扣、剩余金额和后续还款状态 |
| 重复点击主动支付 | 使用业务幂等键，避免重复扣款 |
| 生成文件失败 | 保留账单主记录，允许安全重试并避免重复附件 |
| 通知发送失败 | 不回滚资金交易；记录失败并支持重试 |

## 12. 验收场景

### 12.1 账单生成

- 直客存在月结费用时，能够生成 `MonthlyStatement`。
- 直客无月结费用时，不生成误导性账单或展示 `No fee`。
- 直客账单自动复核，操作人为 `System`。
- API 客户仍进入原人工复核流程。
- 同一客户、同一月份重复触发任务不会重复生成有效账单。

### 12.2 金额和明细

- 月结费用、低消、活跃卡费、非活跃卡费、MVC 等费用金额正确。
- `adjust_amount` 优先于 `amount`。
- 0 金额费用项在页面、PDF、CSV/ZIP 中均不展示。
- Active Card Details 能按账单周期生成并放入明细 ZIP。
- 毛利返现能够出现在返现总额、返现明细和 Net 计算中。

### 12.3 轧差和扣款

- 月账单大于返现时生成 `NettingDebit`。
- 返现大于月账单时生成 `NettingRebate`。
- 金额相等时生成 `NettingEqual` 并正确结清。
- 直客扣款后量子账户允许为负数。
- API 客户最多扣到可用余额，余额不足部分保持待还款。
- 一次 Net 拆成多笔资金交易时，每笔交易都能追溯到同一个 Net 和账单月。

### 12.4 调整和通知

- 20 日后调整未结清账单，Net 金额和类型同步更新。
- 已结清账单不可修改。
- 调账行为有完整操作日志。
- 直客不再收到旧活跃卡扣费通知。
- 统一账单通知按中英文模板发送且不重复发送。

## 13. 开发前必须确认的问题

1. 最终账单生成日到底是每月 10 日还是 15 日？
2. 返现生成、审核完成、客户端展示、支付按钮开放和 20 日扣款的准确时间分别是什么？
3. **已确认：直客准入条件**。不按所有直客账户统一生成账单，只查询 `account_fee_transaction`，当指定 `accountId` 在账单周期内存在 `deduction_node = 'monthly'` 的未结算月结费用时，才生成直客月结账单。
4. **已确认：直客客户类型**。直客定义为非 API 客户，账单查询和费用归集以 `accountId` 为主。账户类型变更不追溯改变已经生成的账单；账单生成时需要记录当时的客户类型快照，供后续复核、轧差和扣款使用。
5. **已确认基础能力：负余额**。量子账户本身支持负余额，因此直客透扣不需要新增账户负余额能力。仍需沿用 API 的扣款流水、账单状态、幂等和通知机制，明确透扣成功后的 `real_amount`、`deal_amount` 和账单结清状态。
6. **已确认：无返现账单场景**。直客只有月结账单时仍生成 Net 记录：`rebate_id = NULL`、`rebate_amount = 0`，根据月结金额生成 `NettingDebit`。没有月结账单但只有返现时按 `bill_amount = 0` 生成 `NettingRebate`；两者都没有时不生成 Net。
7. **已确认方向：保存账单客户类型**。建议在 `api_client_bill` 增加或复用账单客户类型字段，保存账单生成时的类型，而不是在扣款时重新查询账户当前类型。字段变更必须兼容 Java、Flink、报表和其他下游。
8. **已确认方向：调账权限与 API 一致**。20 日后调整沿用 API 当前规则，主要由财务操作；已结清账单不允许调整；调整需要记录操作人、调整前后金额、时间、原因和业务关联信息。具体角色权限沿用现有配置，不新增直客专属审批流。
9. **已确认：Net 版本策略与 API 一致**。已生成但未支付的 Net 被调账后，直接更新原 Net 记录，客户端展示最新结果；不保留完整旧版本，只保留 `old_type` 和操作日志等变更痕迹。
10. **已确认方向：历史账单可控回补**。直客当前使用新费率类型的客户较少，可以按需要对历史账单做回补或更新，但必须区分未结清和已结清账单：未结清账单可按新规则补建/更新；已结清账单只做数据对账或历史展示补齐，不能因为回补再次触发扣款。
