# 直客账单需求分析

> 本文用于直客月结账单的需求评审、代码分析、任务核对和开发拆分。
>
> 更新日期：2026-09-18

## 1. 一页结论

本需求不是重新建设一套直客账单，而是把直客月结费用接入现有客户账单、返现和 Net 轧差体系。现有 `api_client_*` 表和任务虽然名称带有 API，但已经被代码、Flink、报表和脚本广泛使用，本次不做物理重命名。

最终方案：

1. 直客按 `accountId` 识别，定义为非 API 客户。
2. API 客户按新旧迁移情况查询 `account_fee_transaction` 和 `api_client_transaction`；直客不进入 `api_client_transaction`，普通费用查询 `account_fee_transaction`，活跃卡费补查 `ActiveCardFee`。
3. 只有账单周期内存在符合月结查询条件的月结费用（`status = 'Closed'`）的客户才生成 `MonthlyStatement`；无月结费用不生成空账单，也不生成 Net。
4. 直客无返现时仍生成 Net，使用 `rebate_id = NULL`、`rebate_amount = 0`，结果为 `NettingDebit`。
5. 直客和 API 客户继续复用 `api_client_bill`、`api_client_bill_statement`、`cash_back_bonuses`、`api_client_netting_bill`、`api_client_debit_record` 等现有模型。
6. `api_client_bill` 需要记录账单生成时的客户类型快照，账户后续类型变化不影响历史账单。
7. 直客账单自动复核，操作人为 `System`；API 客户维持原人工复核流程。
8. 直客扣款沿用量子账户允许负余额的能力，余额不足时仍继续扣款并标记结清；直客不进入欠款通知、还款和负余额强制平账任务。
9. 20 日结算优先使用当前运行中的 Net 加锁和 Net 扣款任务；截图显示普通账单扣款任务处于 STOP，不能直接作为新流程入口。

## 2. 背景、目标和范围

### 2.1 当前问题

直客月结费用过去有独立的待办和扣款处理，API 客户使用月账单、返现和 Net 流程，导致账单口径、扣款、通知和对账存在两套实现。直客需要接入统一账单入口，并保留其自动复核和可透扣差异。

### 2.2 本次范围

- 直客月结费用接入统一月结账单生成。
- 直客账单自动复核并记录系统操作人。
- 直客参与返现和 Net 轧差；无返现时仍可生成扣款型 Net。
- Admin 客户账单查询、复核、导出和受控调账。
- Merchant 账单菜单、账单查看、明细下载、还款和还款记录。
- 账单、返现、Net、扣款结果的邮件和站内信通知。
- 新旧费率来源的双查询、标准化、去重和审计追溯。

### 2.3 不在本次范围内

- 不重命名既有 `api_client_*` 表、字段、Flink 作业或历史枚举。
- 不改变现有费用计算公式、返现标准和客户报价规则。
- 不删除历史账单，不因展示口径调整重新触发历史扣款或返现。
- 直客此前未进入统一账单体系，本次不回溯生成直客历史账单，只处理接入后的新账单。
- 不把 OpenAPI V3 的 `collection_fee_settlement` 返现模型直接等同于 `api_client_bill` 的 `Rebate`。

## 3. 业务口径

### 3.1 客户识别

直客以 `accountId` 为核心识别条件，定义为非 API 客户。账单生成时将客户类型写入账单快照；之后账户类型变化不回溯修改历史账单。

### 3.2 费用来源

客户没有全部迁移到新费率系统，需要按客户类型和实际数据来源组合查询，并在账单生成时统一标准化：

| 来源 | 查询原则 | 结果处理 |
|---|---|---|
| 新费率系统 | `account_fee_transaction` 中账单周期内、`deduction_node = 'monthly'`、`status = 'Closed'` 的费用 | 标准化为统一费用对象 |
| 旧 API 月结费用 | API 客户的 `api_client_transaction.fees` | 仅 API 客户查询，按现有 API 逻辑聚合 |
| 活跃卡费待办 | 直客的 `accountToDo` 中 `key = 'ActiveCardFee'` 且匹配 `accountId` 的记录 | 仅直客补查，解析 `feeDetails[].amount`，按 `MONTHLY_CARD_FEE` 写入 |

不同来源结果不能直接相加。统一费用对象至少保留 `account_id`、`source_system`、`source_id/transaction_id`、`fee_id`、`fee_name`、`deduction_node`、金额、结算状态和账单月份，用稳定业务键去重并支持原始记录追溯。

### 3.2.2 `getApiClientMonthlySettlementFee` 双查询规则

现有入口：

```java
List<ApiClientMonthFeeVO> getApiClientMonthlySettlementFee(QueryFilterDTO filter);
```

该方法需要根据客户类型选择实际来源组合；API 客户存在新旧迁移混合情况，因此 API 客户需要同时查询两套来源，直客不查询 `api_client_transaction`：

```text
getApiClientMonthlySettlementFee(filter)
  ├─ API客户：查询新费率月结来源
  │    account_fee_transaction
  │    deduction_node = monthly
  │    账单月份匹配、status = Closed
  ├─ API客户：查询旧费用
  │    api_client_transaction.fees
  │    status = Closed、账单月份匹配
  ├─ 直客：查询新费率月结来源
  ├─ 直客：补查 accountToDo.ActiveCardFee
  ├─ 按客户适用来源合并并去重
  └─ 统一转换为 ApiClientMonthFeeVO
```

这里的“两次查询”主要针对 API 客户：API 客户中已经迁移新费率的费用可能来自新表，尚未迁移的费用仍来自 `api_client_transaction`；同一个 API 客户甚至可能在同一账单月份同时存在两类来源。直客没有交易进入 `api_client_transaction`，因此直客只查询 `account_fee_transaction`，并补查 `ActiveCardFee`。

合并要求：

- 两次查询必须使用同一 `accountIds`、账单月份和结算口径，避免查询范围不一致。
- 统一转换后再聚合，不能先按来源分别生成两张账单。
- 有来源主键时使用 `source_system + source_id` 去重；没有主键时使用账户、账单月份、费用类型、provider 和原始明细 ID 组成业务键。
- 新旧来源的相同费用如果无法判断是否重复，不能静默相加，应记录冲突并进入补偿/人工核对。
- 新旧来源查询结果都要保留来源标识，便于财务对账和后续结算状态回写。

### 3.2.1 活跃卡费 `ActiveCardFee` 规则

部分没有配置新费率的直客，活跃卡费不在 `account_fee_transaction` 中，而是以账户待办记录保存。典型查询：

```sql
SELECT *
FROM "accountToDo"
WHERE "key" = 'ActiveCardFee'
  AND "accountId" = :accountId;
```

该待办通常在每月 1 日创建，记录的是**上一个月份**的活跃卡费用。例如待办创建于 2026 年 7 月 1 日时，其 JSON 可能包含 `billingMonth = 2026-06`。

活跃卡费最终不是新增直客专用类型，而是和 API 客户使用同一个账单明细类型：

```java
MONTHLY_CARD_FEE("monthlyCardFee", "活跃卡月费", "Monthly Card Fee", null)
```

因此，`BlueBancCardRecharge` 是 `feeDetails` 中的供应商/业务来源信息，不能直接替代账单明细类型；直客和 API 客户都应将该费用记录到 `api_client_bill_statement`，类型为 `MONTHLY_CARD_FEE`。

落库时还要保持 API 现有的 `provider` / `is_sum` 结构：

| 账单明细 | `type` | `provider` | `is_sum` | 作用 |
|---|---|---|---|---|
| 活跃卡费渠道明细 | `monthlyCardFee` | 使用 API 的供应商映射值，例如 `BB` | `false` | 保留渠道、卡段、数量和金额等明细 |
| 活跃卡费汇总行 | `monthlyCardFee` | `null` | `true` | 作为账单金额汇总和 `monthlyCardFee` 展示值 |

因此，直客复用现有 API 的 provider 映射规则，`BlueBancCardRecharge` 转换为账单明细使用的 `provider = 'BB'`；费用类型仍是 `MONTHLY_CARD_FEE`，不能新增直客类型。`is_sum = true` 的汇总行必须生成，因为现有账单总额和月费汇总查询按 `is_sum = true` 取数；渠道明细行保留 `is_sum = false`，用于明细展示和对账。

处理规则：

1. 以 JSON 的 `billingMonth` 作为费用归属月份，不能用待办创建月份替代。
2. 账单明细金额取 `feeDetails[].amount`，不能只使用 `rate`、`count` 或 `totalFee`；`totalFee` 用于校验明细合计。
3. 每条明细保留 `firstSix`、`provider`、`accountId`、`rate`、`count` 和 `amount`，用于 Active Card Details 展示和对账。
4. `provider = 'BlueBancCardRecharge'` 按现有 API 规则转换为账单明细的 `provider` 值，并将明细写入 `api_client_bill_statement`，类型统一为 `MONTHLY_CARD_FEE`；渠道明细 `is_sum = false`，汇总行 `is_sum = true` 且 `provider = null`。
5. `activeCardDetailsFile` 作为原始明细附件来源或追溯链接保留；生成统一账单 ZIP 时纳入 Active Card Details。
6. 同一个 `accountToDo`、账单月份和明细 ID 只能计入一次；账单重跑不能重复计入。
7. `totalFee = 0` 或所有 `amount = 0` 时，不生成可展示的活跃卡费明细，但仍需根据其他月结费用判断是否生成账单。

该来源本质上是“旧费率直客的活跃卡费月结来源”，应与新费率查询并列，而不是在账单生成后临时补一笔手工费用。

### 3.3 账单准入

- 有符合查询条件的月结费用：生成 `api_client_bill.type = MonthlyStatement`。
- 无符合查询条件的月结费用：不生成空账单，不生成 Net。
- 直客的“是否生成账单”按账单周期内费用判断，不按账户是否属于直客统一批量生成。

### 3.4 金额口径

```text
有效金额 = adjust_amount 非空时取 adjust_amount，否则取 amount
```

计算、列表、PDF、CSV/ZIP 和客户端展示统一使用有效金额。0 金额费用项可以不展示，但不能因此改变账单总额。费用范围包括交易/渠道费用、月低消、活跃卡费（包括 `ActiveCardFee` 待办映射的 `MONTHLY_CARD_FEE`）、非活跃卡费、MVC、失败费、验证费、制卡/邮寄费、退款/ATM 费用和财务调账等已纳入月结的项目。

### 3.5 返现和 Net

月结账单和返现账单是两个独立的 `api_client_bill` 主记录：

| 记录 | `type` | 作用 |
|---|---|---|
| 月结账单 | `MonthlyStatement` | 汇总应收月结费用 |
| 返现账单 | `Rebate` | 汇总客户应得返现 |

Net 计算规则：

| 月结账单与返现的关系 | Net 类型 | 处理 |
|---|---|---|
| 月结金额 > 返现金额 | `NettingDebit` | 对客户扣款 |
| 月结金额 < 返现金额 | `NettingRebate` | 向客户返现 |
| 金额相等 | `NettingEqual` | 结清，不产生实际扣款 |
| 无返现账单 | `NettingDebit` | `rebate_id = NULL`、`rebate_amount = 0` |

## 4. 现有模型和兼容策略

| 对象 | 作用 | 本次处理 |
|---|---|---|
| `api_client_bill` | 月结和返现账单主记录 | 复用；增加/使用客户类型快照和账单类型 |
| `api_client_bill_statement` | 费用明细 | 复用；写入统一月结费用 |
| `cash_back_bonuses` | 返现业务明细 | 复用；保证毛利返现进入返现总额和明细 |
| `api_client_netting_bill` | 月结与返现轧差结果 | 复用；直客和 API 均生成 |
| `api_client_debit_record` | 实际扣款/返现落地记录 | 复用；记录账单来源、Net 和客户类型差异 |
| `bill_history_config` | 生成时配置和明细快照 | 必须保留，支持调整追溯和安全重生成 |

### 4.1 为什么不改 `api_client` 名称

这些表名和字段已经被 Java、Flink、BI、财务报表、数据同步、定时任务、脚本和监控依赖。直接改名会造成历史数据断链、下游 SQL 失败和双写不一致。本次采用：

- 物理表名保持不变，业务语义按“客户账单”理解。
- 新增代码类、DTO、VO 和文档可使用 `CustomerBill`、`CustomerNettingBill` 等通用命名。
- 需要扩展时优先新增客户类型、来源系统、账单来源等兼容字段。
- 若未来必须改名，先做依赖盘点、视图/别名、双读双写、历史回放、观察期和回滚方案。

## 5. 端到端流程

本节把一次账单周期拆成四类记录：月结账单、返现账单、Net 轧差账单和实际扣款记录。四者不是四套独立业务，而是前后关联的四层记录：

```mermaid
flowchart LR
    A[账单周期结束] --> B1[新费率来源<br/>account_fee_transaction<br/>API和直客]
    A --> B2[旧API来源<br/>api_client_transaction.fees<br/>仅API客户]
    A --> B3[直客补充来源<br/>accountToDo.ActiveCardFee]
    B1 --> C[标准化、去重、按 accountId 聚合]
    B2 --> C
    B3 --> C
    C --> D{存在 status=Closed<br/>且 deduction_node=monthly 的费用?}
    D -- 否 --> D0[不生成 MonthlyStatement<br/>不生成 Net]
    D -- 是 --> E[api_client_bill<br/>type=MonthlyStatement]
    E --> E1[费用明细<br/>api_client_bill_statement]
    E1 --> E2[复核与账单展示]
    F[cash_back_bonuses<br/>返现业务数据] --> G[api_client_bill<br/>type=Rebate]
    E2 --> H[Net 初始化/计算]
    G --> H
    H --> I[api_client_netting_bill]
    I --> J[20日加锁]
    J --> K{Net结果}
    K -- 直客扣款 --> L1[量子账户扣款<br/>允许负余额]
    K -- API扣款 --> L2[按可用余额扣款<br/>不足进入待还款]
    K -- 返现 --> L3[量子账户返现]
    K -- 金额相等 --> L4[直接结清]
    L1 --> M[api_client_debit_record]
    L2 --> M
    L3 --> M
    L4 --> M
```

没有月结费用时不生成空账单；有月结费用但没有返现账单时，仍生成 `NettingDebit`，返现金额按 0 处理。

### 5.1 月结账单 `MonthlyStatement` 生命周期

#### 5.1.1 生成入口和前置条件

当前截图确认的主任务是 `quantum_card_api_customer_bill`，每月 10 日 00:00 执行；`create_month_bill` 是每日 10:15 的指定月份补生成任务，但当前 STOP。代码入口需要以 `ApiCustomerJob.billJobHandler()` 和 `apiClientBillService.initBill()` 为准。

生成前必须完成：

1. 确定账单月份和账单周期边界。
2. 以 `accountId` 判断非 API 直客及 API 客户范围。
3. API 客户查询新费率和 `api_client_transaction`；直客查询新费率并补查 `ActiveCardFee`。
4. 过滤账单周期内、`deduction_node = 'monthly'` 且 `status = 'Closed'` 的费用。
5. 解析 `ActiveCardFee` 的 `billingMonth`、`feeDetails[].amount` 和 `provider`，将明细按 `MONTHLY_CARD_FEE` 写入 `api_client_bill_statement`。
6. 按稳定业务键去重，不能把多类来源的同一费用相加两次。
7. 统一使用 `adjust_amount` 非空取 `adjust_amount`，否则取 `amount`。

#### 5.1.2 生成和状态流转

以下是业务状态，实际代码枚举名称需要开发前映射确认：

```mermaid
stateDiagram-v2
    [*] --> INIT: 发现账单准入客户
    INIT --> GENERATING: 创建主记录
    GENERATING --> GENERATED: 明细、金额、快照生成成功
    GENERATING --> GENERATE_FAILED: 查询/写入/附件失败
    GENERATE_FAILED --> GENERATING: 补偿或安全重试
    GENERATED --> REVIEW_PENDING: API客户进入人工复核
    GENERATED --> REVIEWED: 直客自动复核，操作人=System
    REVIEW_PENDING --> REVIEWED: 财务复核通过
    REVIEW_PENDING --> REJECTED: 财务复核拒绝
    REJECTED --> GENERATING: 修正后重新生成
    REVIEWED --> AVAILABLE: 达到展示条件
    AVAILABLE --> ADJUSTED: 未结清且有权限调账
    ADJUSTED --> AVAILABLE: 更新金额/明细后重新展示
    AVAILABLE --> SETTLED: Net或直接结算完成
    SETTLED --> [*]
```

| 阶段 | 记录和动作 | 约束 |
|---|---|---|
| `INIT/GENERATING` | 创建主记录，查询费用并写明细 | 不可展示为可支付账单 |
| `GENERATED` | 总额、明细、`bill_history_config` 和附件生成 | 未复核时不能进入正式结算 |
| `REVIEW_PENDING` | API 客户等待财务复核 | 不可作为最终账单 |
| `REVIEWED` | 直客自动复核；API 财务复核 | 继续等待展示/通知条件 |
| `AVAILABLE` | 客户可查询、下载并参与 Net | 未结清时可按规则调账 |
| `ADJUSTED` | 使用调整金额或人工费用重新计算 | 已结清账单不可调账 |
| `SETTLED` | Net、扣款或返现完成 | 禁止再次调账或重复扣款 |

生成失败时不能静默生成不完整账单。主记录已落库但明细或附件失败时，保留主记录并安全重试；同一 `accountId + billing_period + bill_type` 不能产生重复有效账单。

### 5.2 返现账单 `Rebate` 生命周期

返现不是月结明细中的负数行，而是独立的 `api_client_bill` 主记录，类型为 `Rebate`，明细来源于 `cash_back_bonuses` 等返现业务数据。

当前时间链路是：`cash_back` 每月 3 日 09:00 准备返现数据，`create_rebate_bill` 每月 18 日 00:00 生成返现历史账单。返现数据的审核条件、人工触发方式和重跑入口仍需查代码。

```mermaid
stateDiagram-v2
    [*] --> DATA_READY: 返现业务数据准备
    DATA_READY --> GENERATING: create_rebate_bill
    GENERATING --> GENERATED: Rebate主记录和明细生成
    GENERATING --> GENERATE_FAILED: 数据不足/写入失败
    GENERATE_FAILED --> GENERATING: 补数据或重跑
    GENERATED --> CONFIRMED: 返现金额可用于结算
    CONFIRMED --> NETTING: 与MonthlyStatement建立Net
    NETTING --> SETTLED: 返现完成或轧差结清
    SETTLED --> [*]
```

没有返现数据不等于月结账单失败。此时可以不生成 `Rebate` 主记录，但 Net 必须按 `rebate_amount = 0` 处理，不能漏掉直客月结扣款。

### 5.3 Net 轧差账单生命周期

Net 是某客户某账单月份的“月结应收和返现应付”的结算结果，不是新的费用来源。它至少关联一个 `MonthlyStatement`、一个 `Rebate` 或空返现标识、客户、账单月份、结算类型和最终资金动作。

业务上，Net 应在账单数据达到可计算条件后初始化；当前截图确认 20 日 00:00 加锁、20 日 10:00 执行扣款/返现。`api_bill_bill_notice` 是否负责 Net 初始化，需要通过代码调用链确认。

```mermaid
stateDiagram-v2
    [*] --> INIT: 账单数据满足Net准入
    INIT --> CALCULATED: 计算月结、返现和差额
    CALCULATED --> NO_ACTION: 金额相等
    CALCULATED --> PENDING_DEBIT: 月结金额较大
    CALCULATED --> PENDING_REBATE: 返现金额较大
    PENDING_DEBIT --> LOCKED: 20日锁定结算范围
    PENDING_REBATE --> LOCKED: 20日锁定结算范围
    NO_ACTION --> SETTLED: NettingEqual直接结清
    LOCKED --> PROCESSING: 执行扣款或返现
    PROCESSING --> DEBIT_SUCCESS: 扣款足额成功
    PROCESSING --> REBATE_SUCCESS: 返现成功
    PROCESSING --> PARTIAL: API余额不足或部分成功
    PROCESSING --> FAILED: 交易或系统失败
    PARTIAL --> UNPAID: 剩余金额进入待还款
    FAILED --> RETRYING: 按幂等规则重试
    RETRYING --> PROCESSING
    PENDING_DEBIT --> ADJUSTED: 20日后未结清且允许调账
    ADJUSTED --> CALCULATED: 更新原Net金额和类型
    DEBIT_SUCCESS --> SETTLED
    REBATE_SUCCESS --> SETTLED
    UNPAID --> RECOVERING: 欠款通知/还款/补扣
    RECOVERING --> SETTLED: 后续结清
    SETTLED --> [*]
```

| 环节 | 直客 | API 客户 |
|---|---|---|
| Net 生成 | 有月结费用即可生成，返现可为空 | 沿用原有月结/返现准入 |
| 余额不足 | 允许量子账户为负，继续透扣 | 只扣可用余额，不足部分待还款 |
| 未结清 | 直客透扣后不进入欠款通知、还款和负余额强制平账任务 | 沿用现有欠款和上月补扣链路 |
| 调账 | 与 API 一致，更新原 Net，保留 `old_type` 和日志 | 当前采用原记录更新方式 |

#### 5.3.1 轧差结果分支

轧差结果按“月结账单金额”和“返现账单金额”的大小关系处理：

```mermaid
flowchart TD
    A[轧差结果] --> B{月结金额与返现金额比较}
    B -->|月结 > 返现| C[生成还款账单/扣款结果<br/>返现账单标记已结清]
    C --> D{客户类型}
    D -->|直客| E[量子账户扣款<br/>允许余额变成负数]
    E --> F[月结账单标记已结清]
    D -->|API客户| G[按可用余额扣款]
    G --> H{是否足额}
    H -->|是| F
    H -->|否| I[剩余金额标记待还款<br/>进入手动还款/财务扣款流程]
    B -->|月结 = 返现| J[账单和返现均标记已结清<br/>不产生实际资金动作]
    B -->|月结 < 返现| K[生成返现入账记录]
    K --> L[账单和返现均标记已结清]
```

该分支确认了直客和 API 客户的差异仅发生在实际扣款阶段：直客允许透扣为负，API 客户余额不足时保留待还款金额；轧差计算和账单、返现结清关系保持一致。

### 5.4 实际扣款记录 `api_client_debit_record` 生命周期

Net 是结算决定，`api_client_debit_record` 是实际资金动作。一次 Net 可以对应多笔扣款/返现记录，但每笔都必须回溯到同一个 Net、账单月份、账户和扣款来源。

```mermaid
stateDiagram-v2
    [*] --> CREATED: 创建扣款/返现指令
    CREATED --> PROCESSING: 任务获取并加锁
    PROCESSING --> SUCCESS: 全额成功
    PROCESSING --> PARTIAL: 部分金额成功
    PROCESSING --> FAILED: 交易失败
    FAILED --> RETRY_PENDING: 可重试失败
    RETRY_PENDING --> PROCESSING: 重试且幂等校验通过
    PARTIAL --> UNPAID: 记录剩余待还款金额
    UNPAID --> PROCESSING: 后续还款或补扣
    UNPAID --> SUCCESS: 剩余金额结清
    SUCCESS --> [*]
```

必须保证重试不重复创建成功交易，直客负余额扣款和 API 部分扣款有明确来源标识，已结清 Net 不再被欠款恢复任务捞取。

### 5.5 一次账单周期的完整时序

```mermaid
sequenceDiagram
    participant Fee as 新费率/旧费率/ActiveCardFee
    participant Bill as 月结账单
    participant Rebate as 返现账单
    participant Net as Net轧差
    participant Debit as 扣款记录/量子账户
    participant Notice as 通知任务
    Fee->>Bill: 查询、过滤、去重月结费用
    Bill->>Bill: 生成MonthlyStatement和费用明细
    Bill->>Bill: 直客自动复核 / API人工复核
    Fee-->>Rebate: 准备返现业务数据
    Rebate->>Rebate: 生成Rebate和返现明细
    Bill->>Net: 提供月结应收
    Rebate->>Net: 提供返现应付；无返现按0
    Net->>Net: 计算Debit/Rebate/Equal
    Notice-->>Bill: 发送账单通知
    Net->>Net: 20日00:00加锁
    Net->>Debit: 20日10:00执行扣款/返现
    Debit-->>Net: 成功、部分成功或失败
    Net-->>Notice: 发送结算/未结清通知
    Notice-->>Debit: 欠款通知、还款通知
    Debit->>Debit: 后续还款、补扣或强制平账
```

关键顺序是：先形成账单，再形成返现，再形成 Net，最后执行资金动作。任何补生成或重跑都不能跳过账单关联、状态校验和幂等校验直接扣款。

## 7. Admin 和 Merchant 需求

### 7.1 Admin

- 客户账单作为统一入口，支持客户类型、账户、账单月份、账单类型、状态和金额筛选。
- 账单列表展示账单总额、返现、Net 类型、扣款状态、客户类型和生成时间。
- 支持费用明细、返现明细、Active Card Details、PDF/CSV/ZIP 下载。
- 直客账单生成后自动复核；API 维持原人工复核。
- 20 日后未结清账单调整沿用 API 规则：财务角色、原因必填、操作留痕；已结清账单不可修改。
- 调账后当前 API 直接更新原 Net，保留 `old_type` 和操作日志；直客保持一致，建议同时记录调整前后金额。

### 7.2 Merchant

- 非 API 直客开放账单菜单和账单查询权限。
- 支持月结账单、返现账单、Net 结果、明细下载、还款和还款记录。
- 无月结费用的直客不展示空账单或“No fee”伪账单。
- 统一中英文通知，避免旧活跃卡扣费通知和统一账单通知重复。

### 8.1 数据库

### 8.2 服务和任务

- 账单生成服务增加直客筛选和新旧费用双查询，不复制一套 API 账单服务。

## 13. 开发方案

### 13.1 总体技术方案

采用“统一账单编排 + 多费用来源适配 + 客户类型分支”的方案，不复制一套直客账单服务，也不改名现有 `api_client_*` 表。

```text
XXL-JOB
  → ApiCustomerJob
  → 客户账单编排服务
  → 费用来源适配层
      ├─ account_fee_transaction
      ├─ 旧费率普通月结来源
      └─ accountToDo.ActiveCardFee
  → 统一费用对象
  → 去重和账单准入
  → api_client_bill / api_client_bill_statement
  → 返现账单
  → api_client_netting_bill
  → api_client_debit_record
```

核心原则：

- 账单主流程只负责编排，来源差异放在费用适配层。
- 费用来源对象必须带 `source_system`、`source_id`、`billing_month` 和原始明细，便于去重和对账。
- 活跃卡费最终统一为 `api_client_bill_statement.type = monthlyCardFee`，即 `MONTHLY_CARD_FEE`。
- `provider` 和 `is_sum` 继续遵循 API 规则：渠道明细使用供应商映射值且 `is_sum = false`，汇总行 `provider = null` 且 `is_sum = true`。
- 直客只改变准入、复核和扣款策略，不改变账单、返现、Net 的物理模型。

| `qbit-core/src/main/resources/mapper/quantum/card/ApiClientBillStatementMapper.xml` | 确认金额汇总只取 `is_sum = true`，明细查询保留渠道行 |
| `qbit-core/src/main/java/com/qbit/job/qbitcard/ArrearsRecoverJob.java` | 仅按 API 现有逻辑处理欠款通知、还款、补扣和负余额强制平账，排除直客 |
| 费用来源适配类（建议放在账单领域包） | 封装 API 新费率、API 旧来源和直客 `ActiveCardFee` 查询，不把 SQL 混入账单编排服务 |
| 账单领域 Converter/标准化对象 | 将三类来源转换为统一费用项和 Active Card Details |

### 13.3 统一费用对象设计

建议新增内部 BO，不直接把 `accountToDo` JSON、费率交易 Entity 或旧系统对象传到账单 Service：

```text
BillFeeItem
  accountId
  billingMonth
  sourceSystem          NEW_RATE / LEGACY_RATE / ACTIVE_CARD_TODO
  sourceId              transactionId / accountToDoId / detailId
  feeType               MONTHLY_CARD_FEE 等统一类型
  provider              API 映射后的 provider，例如 BB
  sourceProvider        原始 provider，例如 BlueBancCardRecharge
  amount
  adjustAmount
  isSettled
  isSum
  detailData            firstSix、count、rate、activeCard 等
  detailFileUrl         activeCardDetailsFile
```

`ActiveCardFee` 转换规则：

1. 按 `accountId` 查询 `accountToDo`，条件为 `key = 'ActiveCardFee'`。
2. 解析 JSON 的 `billingMonth`，以它作为费用月份。
3. 每个 `feeDetails` 转成一条渠道明细，金额取 `amount`。
4. `provider` 按 API 现有映射转换；原始 `BlueBancCardRecharge` 放入来源字段或扩展明细，不能替换 `feeType`。
5. 渠道明细写入 `MONTHLY_CARD_FEE + is_sum=false`。
6. 按账单月份和账户聚合一条 `MONTHLY_CARD_FEE + provider=null + is_sum=true` 的汇总行。
7. 汇总行金额必须等于有效明细金额之和；重复运行不得再次插入。

### 13.4 月结账单开发步骤

#### 阶段一：现状核对和契约固定

- 固定账单月份口径：`account_fee_transaction` 使用交易归属月份，`ActiveCardFee` 使用 JSON `billingMonth`。
- 确认旧费率普通月结来源的表、状态字段和已结算更新时机。
- 确认 API 活跃卡费的 `provider` 映射方法，以及 `is_sum` 汇总行生成位置。
- 确认 `ApiClientBillServiceImpl` 当前的客户筛选、账单幂等和自动复核入口。
- 固定 API 新费率、API 旧来源的去重键，以及直客 `ActiveCardFee` 的待办/明细去重键：优先使用来源系统 + 来源主键；没有主键时使用账户 + 月份 + 类型 + provider + 原始明细 ID。

#### 阶段二：费用读取和标准化

- 为每个来源实现独立查询方法，统一接收 `accountIds` 和 `billingMonth`。
- 费用查询只读取账单周期内符合 `status = 'Closed'` 的可计费记录。
- `ActiveCardFee` 解析失败、月份缺失、明细金额为空或总额不一致时，记录账户、待办 ID 和批次，不静默跳过。
- 统一金额精度和舍入规则；账单计算使用 `adjust_amount` 优先规则。
- API 新费率和旧来源结果先合并并按稳定键去重；直客再合并 `ActiveCardFee`，输出各来源统计：读取数、去重数、计费数、0 金额数和异常数。

#### 阶段三：写入账单和明细

- 按 `accountId + billingMonth + MonthlyStatement` 做账单幂等。
- 写入客户类型快照，直客自动复核为 `System`，API 保持原流程。
- 写入 `api_client_bill_statement`，活跃卡费使用 `MONTHLY_CARD_FEE`。
- 渠道明细设置 `provider` 和 `is_sum=false`；总账汇总查询依赖的汇总行设置 `provider=null` 和 `is_sum=true`。
- 保存来源 ID、`billingMonth`、原始 provider 和 `activeCardDetailsFile`，必要时放入 `remarks` 或扩展字段。
- 账单主记录、明细、历史配置和附件生成需要在可恢复边界内处理，不能因附件失败产生第二张账单。

### 13.5 返现、Net 和扣款开发步骤

1. 保持 `create_rebate_bill` 现有生成逻辑，先确认直客是否已被客户筛选覆盖。
2. Net 初始化时按 `MonthlyStatement` 找返现账单；没有返现账单时构造 0 返现输入，不跳过直客。
3. 根据月结金额和返现金额生成 `NettingDebit`、`NettingRebate` 或 `NettingEqual`。
4. 20 日加锁前校验账单、返现、Net 是否已经生成且未被结算。
5. 20 日扣款时按客户类型分支：直客沿用负余额能力，API 沿用可用余额和待还款逻辑。
6. 每一笔资金动作写入 `api_client_debit_record`，带上 Net、账单月份、来源和客户类型。
7. 调账沿用 API：未结清时更新原 Net，记录 `old_type`、调整前后金额、操作人、原因和时间；已结清拒绝调整。

### 13.6 定时任务改造方案

| `quantum_card_api_customer_bill` | 复用主账单任务；API 客户查询新费率和旧 API 来源，直客查询新费率并额外覆盖 `ActiveCardFee` |

| `quantum_card_api_customer_netting_bill_debit_lock` | 复用加锁；加锁前排除无月结账单和已结算记录 |
| `quantum_card_api_customer_netting_bill_debit` | 复用扣款/返现；增加直客负余额分支和来源幂等校验 |

### 13.7 幂等、事务和并发控制

- 账单生成锁：按 `accountId + billingMonth + billType` 加分布式锁，使用现有 Redisson 规范。
- 来源去重：API 使用新费率/`api_client_transaction` 的来源键，直客使用新费率/`ActiveCardFee` 的来源键；同一 `ActiveCardFee` 明细不能重复落账。
- 账单重跑：已存在有效账单时只补齐缺失明细/附件，不能无条件插入新主记录。
- Net 扣款：按 Net ID 和扣款阶段幂等，已有成功扣款记录时不得再次调用资金扣款。
- 事务边界：账单主记录、明细和历史快照保持一致；外部资金扣款不放入长事务，资金结果通过状态和补偿记录落库。
- 部分失败：客户适用的来源查询必须有客户级状态，直客 `ActiveCardFee` 也要记录解析状态；来源不完整的客户进入待处理或失败，不生成看似完整的账单，其他正常客户继续生成。

### 13.8 测试方案

| 场景 | 预期 |
|---|---|
| 新费率客户 | 生成正确月结账单和 `is_sum=true` 汇总行 |
| 旧费率客户 | 不依赖新费率表，正确生成月结账单 |
| 直客仅有 `ActiveCardFee` | 按 `billingMonth` 生成 `MONTHLY_CARD_FEE`，渠道行和汇总行均正确 |
| `BlueBancCardRecharge` | `provider` 按 API 映射，`type` 仍为 `monthlyCardFee` |
| 多个 `feeDetails` | 每条明细金额正确，汇总行等于明细合计 |
| 重复执行 | 不重复账单、明细、Net 或扣款记录 |
| 无月结费用 | 不生成空账单和 Net |
| 有月结无返现 | 生成 `NettingDebit`，返现为 0 |
| 直客透扣 | 允许账户负余额，交易可回溯到 Net |
| API 余额不足 | 部分扣款并进入待还款，不影响直客逻辑 |
| 来源查询失败 | 按客户隔离；失败客户不静默生成不完整账单，产生可追踪失败记录，其他客户继续 |
| 已结清调账 | 拒绝修改并记录操作日志 |
| 通知重试 | 不重复发送和重复扣款 |

### 13.9 上线、灰度和回滚

1. 先以只读/对账模式运行三类费用查询，比较新旧账单金额，不写正式账单。
2. 选择一个新费率 API 客户、一个旧 API 来源客户、一个普通直客、一个仅有 `ActiveCardFee` 的直客进行灰度。
3. 灰度期间记录三类来源的金额、账单明细数、`is_sum` 汇总差异、Net 数量和扣款结果。
4. 确认财务对账、客户端展示、通知和 Flink/BI 数据同步无异常后扩大范围。
5. 通过配置开关关闭直客账单生成和直客 Net 分支，不删除已经生成的账单；对账后再执行补偿或回滚。
6. 回滚期间禁止重新启用会重复扣款的旧待办链路，先确认已生成账单和扣款记录状态。
