### 3.2 直客

直客月结账单只处理量子卡费用，且仅处理有效账户：

```text
account.status NOT IN ('Inactive', 'Cleared')
account.type NOT IN ('ApiClient', 'ApiClientCustomer')
```

```text
account_fee_transaction
  └─ business_id 关联 qbitCard

card_status_history
  └─ 按账期计算账期内有效的 Active 卡
      └─ qbitCard.provider 作为 provider

accountFeeService
  └─ 按账户和 provider 查询 MONTHLY_ACTIVE_CARD_FEE_CAAS 费率
```

直客和 API 都通过 `getActiveCardExtends` 使用同一套卡状态统计口径，再按 provider 和 `MONTHLY_ACTIVE_CARD_FEE_CAAS` 费率计算金额。直客不再读取 `accountToDo.ActiveCardFee` 作为账单金额来源；`accountToDo` 中的历史活跃卡数据仅作为旧逻辑和导出兼容数据保留。

主要方法：

```text
ApiClientBillServiceImpl.initDirectBill()
ApiClientBillServiceImpl.initDirectBill(accountIds, billMonths)
ApiClientBillServiceImpl.initDirectBillForMonth(...)
```

直客补充账单账户范围不再根据 `account_fee_transaction` 或 `accountToDo.ActiveCardFee` 是否有数据来确定，而是查询有效账户，并排除当前已经能被 API 月账单处理的账户：

```text
account.deleteTime IS NULL
account.status NOT IN ('Inactive', 'Cleared')
account.type NOT IN ('ApiClientCustomer')
account.id NOT IN (当前 API customerList 返回的账户)
```

这样即使账户当月没有任何收费，也会生成金额为 0、状态为 `FREE` 的直客月结账单。正常 API 账户只生成 API 月账单；API 账户如果因 `customerList` 的有效期、配置或上线条件未被选中，则进入直客补充账单。费用来源只负责补充明细，不负责决定客户是否进入账单范围。API 的 `customerList` 查询带有 `openApiClient`、`openApiClientConfig` 和 `account.type = 'ApiClient'` 条件，不能单独用于直客账户查询。

直客账单生成时写入：

```text
api_client_bill.customer_type = DIRECT
```

直客账单复核规则：

```text
DIRECT → check_status = Done
        → 写入 OpenApiAdminBillCheckStatus 操作日志
        → 操作人展示为 System

API → 按现有流程进入 Waiting，等待财务人工复核
```

定时任务入口统一为 `quantum_card_api_customer_bill`。原直客方法保留用于手动补账，但不再注册独立 XXL-JOB 调度任务。

### 5.1 RS 返现补差

RS 返现补差不是 `account_fee_transaction`，但它属于月结费用的一部分，直客不能因为没有 API 交易记录而漏掉。

查询入口仍复用 API 现有逻辑：

```text
ApiClientTransactionServiceImpl.revenueAdjustmentMap(filter)
  └─ CashBackBonusMapper.getRevenueAdjustments(filter)
      ├─ QuantumCardQIRSProfitCashBack
      └─ QuantumCardBZRSProfitCashBack
```

计算结果按账户、账期和 provider 生成 `REVENUE_ADJUSTMENT` 明细，同时追加账户汇总行。直客账单通过以下公开方法接入：

```text
ApiClientTransactionService.getRevenueAdjustmentMonthlyFees(filter)
  → ApiClientBillServiceImpl.initDirectBillForMonth(...)
  → api_client_bill_statement
```

因此直客月结费用由三部分组成：

```text
account_fee_transaction 量子卡月结费用
+ accountToDo.ActiveCardFee 活跃卡月费
+ RS 返现补差
```

## 六点一、PDF 和 ZIP 生成时机

### API 月账单 ZIP

API 月账单生成时，在 `dealComplexData(...)` 中调用：

```text
initAttachmentDetailZip(apiClientBill)
  ├─ initAttachmentCsv(apiClientBill)
  │   └─ getCardTransactionStatistics(...)
  ├─ QuantumCardActiveCardCsvHandler.exportUrl(...)
  └─ ossService.buildZipFileName(...)
```

生成成功后写入：

```text
api_client_bill.detail_url
```

其中 API CSV 会合并：

```text
api_client_transaction
+ account_fee_transaction
```

### PDF

PDF 默认不是月结定时任务生成，而是在用户下载或账单通知流程中按需生成：

```text
downloadStatementPdf(...)
  → dealDownLoadStatementMonthlyPdf(...)
  → buildAttachment(billId)
  → ApiClientTransactionService.getBillPdf(billId)
  → api_client_bill_statement
  → exportService.exportPdf(...)
```

PDF 的账单明细来源是 `api_client_bill_statement`，因此 API 和直客可以共用 PDF 生成逻辑；直客账单生成时已经写入统一明细表，后续不需要单独实现一套 PDF 模板。

### 直客 ZIP

直客账单生成时的 `saveDirectBills(...)` 在主账单和 `api_client_bill_statement` 落库后，依次预生成 PDF 和明细 ZIP，并分别写入 `api_client_bill.statement_url`、`api_client_bill.detail_url`，与当前直客需求保持一致。单个账户文件生成失败时记录日志，不影响同批其他账户；用户后续下载时仍可按需重试：

```text
downloadStatementDetailZip(...)
  → generatorStatementDetailZip(...)
  → initAttachmentDetailZip(...)
      ├─ initAttachmentCsv(...)
      │   └─ customer_type = DIRECT
      │       └─ getDirectCustomerFeeTransactionStatistics(...)
      ├─ QuantumCardActiveCardCsvHandler.exportUrl(...)
      └─ ossService.buildZipFileName(...)
```

因此直客 ZIP 的第一份 CSV 来自：

```text
account_fee_transaction
```

活跃卡明细 CSV 来自卡状态历史查询。查询账户时使用：

```sql
COALESCE(api_account_relation.root_id, card_status_history.account_id)
```

这样 API 客户按根账户查询，直客按卡所属账户查询。即使账期内没有活跃卡，`QuantumCardActiveCardCsvHandler` 也会生成只有表头的 CSV，因此最终 ZIP 始终包含费用明细 CSV 和活跃卡明细 CSV。

### 账单生成与文件生成的边界

```text
定时任务生成账单
  → api_client_bill
  → api_client_bill_statement

API 账单：生成时预生成 ZIP，PDF 按下载/通知触发
直客账单：生成时预生成 PDF 和 ZIP，分别保存 statement_url、detail_url；失败时下载时按需重试
PDF：统一读取账单明细生成
```

```java

```

执行过程：

```text
initDirectBill(...)
  └─ 处理账单月份
       └─ initDirectBillForMonth(...)
            ├─ 查询 account_fee_transaction 账户集合
            ├─ 查询 accountToDo.ActiveCardFee 账户集合
            ├─ 取两个来源账户 ID 的并集

            ├─ 查询已经生成的账单并保证幂等
            ├─ 查询 account_fee_transaction 月结费用
            ├─ 解析 ActiveCardFee
            ├─ 合并费用对象
            └─ saveDirectBills(...)
```

直客不会调用完整的 `getApiClientMonthlySettlementFee`，因为该方法会同时读取 API 旧来源 `api_client_transaction`。

### 第三步：看新费率月结费用

文件：

```text
qbit-core/src/main/java/com/qbit/openapi/service/impl/ApiClientTransactionServiceImpl.java
```

#### API 统一月结方法

```java
getApiClientMonthlySettlementFee(QueryFilterDTO filter)
```

该方法负责 API 客户新旧来源并行期间的兼容：

```text
getApiClientMonthlySettlementFee
  ├─ getApiClientMonthFees(filter)
  │    ├─ 旧 api_client_transaction 汇总
  │    └─ 新 account_fee_transaction 汇总
  ├─ getMonthProvider(filter)
  │    ├─ 旧 provider 汇总
  │    └─ 新 account_fee_transaction provider 汇总
  ├─ getMonthProviderExtends(filter)
  ├─ qbitAccountIncomeMap(filter)
  ├─ identityVerificationMap(filter)
  ├─ revenueAdjustmentMap(filter)
  ├─ 过滤 RS Scheme Fee
  ├─ 生成 provider 明细
  └─ 生成 is_sum 汇总明细
```

这里不能简单根据“客户是否已经迁移”选择一个来源，因为当前生产中存在部分迁移客户。必须同时查询新、旧来源，再根据业务键避免重复计费。

#### 直客/新费率专用方法

```java
getAccountFeeMonthlySettlementFee(QueryFilterDTO filter)
```

该方法只查询 `account_fee_transaction`，主要条件是：

```text
deduction_node = MONTHLY
status = Closed
create_time >= 账单月开始
create_time < 下个月开始
fee_name 属于量子卡费用集合
business_id 关联 qbitCard
```

查询结果先由 Mapper 按以下维度汇总：

```text

fee_name
qbitCard.provider
```

然后通过：

```java
AccountFeeTransactionMonthlyFeeConverter.convert(...)
```

转换为 `ApiClientFeeEnum`，最后生成 `ApiClientMonthFeeVO`。

### 第七步：看 Net 轧差生成


Net 的输入是同一账户、同一账单月份的：

```text

```

金额计算：

```text

```

```text

  → NettingEqual
  → 账单和返现均结清

账单金额 > 返现金额
  → NettingDebit
  → 产生待扣款金额

返现金额 > 账单金额
  → NettingRebate
  → 产生待返现金额
```

Net 不重复保存客户类型，而是通过：

```text
api_client_netting_bill.bill_id
```


处理顺序：

```text
debitNetting
  ├─ 初始化 Net
  ├─ 处理 NettingEqual
  ├─ 查询 Net 关联的 api_client_bill
  ├─ 读取 customer_type
  ├─ DIRECT → 直客透扣
  └─ API → 原 API 多钱包扣款
```

直客扣款规则：

```text
量子账户余额足够
  → 正常扣款

量子账户余额不足
  → 允许扣至负数
  → 账单结清
```

直客不再进入原 API 的：

```text
欠款通知
手动还款
负余额强制平账
```

## 十三、出现问题时的排查顺序

### 账单没有生成

1. 检查 XXL-JOB 是否执行。
2. 检查任务参数中的 `accountIds` 和 `billMonths`。
3. 查询 `account_fee_transaction` 是否满足 `MONTHLY + Closed`。
4. 查询 `accountToDo.ActiveCardFee` 的 `billingMonth` 是否匹配。
5. 检查账户是否被识别为 API 账户。
6. 检查 `api_client_bill` 是否已经存在同月份账单。

### 账单金额不正确

1. 查询 `api_client_bill_statement` 明细。
2. 区分 `is_sum = true` 汇总行和 provider 明细行。
3. 检查 `account_fee_transaction.fee_name` 映射。
4. 检查 `ActiveCardFee.feeDetails[].amount` 是否重复计入。
5. 检查 RS Scheme Fee 是否被过滤。

### 直客被错误进入 API 扣款

按以下链路查询：

```sql
SELECT
    nb.id AS netting_bill_id,
    nb.bill_id,
    b.customer_type,
    b.type AS bill_type,
    nb.type AS netting_type,
    nb.status AS netting_status
FROM api_client_netting_bill nb
LEFT JOIN api_client_bill b ON b.id = nb.bill_id
WHERE nb.account_id = :accountId
  AND nb.bill_month = :billMonth;
```

重点确认 `b.customer_type = 'DIRECT'`。

### CSV 没有明细

1. 根据账单的 `customer_type` 确认走 API 还是直客导出。
2. API 检查 `api_client_transaction` 和 `account_fee_transaction`。
3. 直客检查 `account_fee_transaction` 是否有量子卡关联。
4. 检查 ActiveCardFee 是否生成独立明细文件。
5. 检查 ZIP 生成和 OSS 上传日志。

## 十四、当前代码与文档的边界

以下内容不属于本次直客账单代码入口：

- 全球账户费用账单。
- 加密资产费用账单。
- Flink 对 `api_client_bill` 的下游同步逻辑。
- 财务系统对账脚本。
- XXL-JOB 管理后台的实际 Cron 配置。

这些系统只能依赖新增的 `api_client_bill.customer_type` 识别账单生成时客户类型，不能重新读取当前账户类型覆盖历史值。
