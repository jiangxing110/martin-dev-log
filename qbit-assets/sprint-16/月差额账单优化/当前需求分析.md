# 月差额账单优化：当前需求分析

> 分析分支：`jx/26/sprint-16/PD-1934/api-bill`  
> 分析日期：2026-09-05  
> 分析范围：当前项目 API 账单、返现账单、差额账单及关联导出/通知链路

## 1. 需求概览

本需求实际包含四个相关方向：

1. 月账单下载及明细中隐藏金额为 0 的费用项。
2. 将毛利返现纳入返现账单、返现明细及月差额计算。
3. Admin 客户账单查询增加账单更新时间，用于定位账单修改导致的差额重算。
4. 月账单明细 ZIP 增加独立的 `Infinity Card Active Card Details.csv`；返现明细 ZIP 增加独立的 `Infinity Card Revenue Sharing Rebate.csv`。CSV 不支持 Sheet；如产品要求真实 Sheet 2，需要另行改为 XLSX。直客账单并入差额后不再发送原账单邮件，统一按差额结果通知，并支持中英文。

其中第 4 项属于本需求的关联扩展，不能只按普通 API 字段调整处理。

## 2. 当前账单模型

### 2.1 月账单与返现账单

API 客户账单主表为 `api_client_bill`，实体：

`qbit-core/src/main/java/com/qbit/openapi/domain/entity/ApiClientBill.java`

通过 `type` 区分：

| type | 含义 | 主要数据来源 |
| --- | --- | --- |
| `MonthlyStatement` | API 客户月度费用账单 | `api_client_bill_statement` |
| `Rebate` | API 客户返现账单 | `bill_history_config` 及返现数据 |

月账单明细表为 `api_client_bill_statement`，重要字段如下：

- `type`：费用类型。
- `amount`：原始金额。
- `adjust_amount`：调账后的金额，存在时优先使用。
- `is_sum`：是否为汇总项。
- `provider`：渠道或明细来源。
- `update_time`：明细调账更新时间。

当前账单有效金额普遍按以下规则计算：

```text
effectiveAmount = COALESCE(adjust_amount, amount)
```

### 2.2 返现数据

返现业务表为 `cash_back_bonuses`，实体：

`qbit-core/src/main/java/com/qbit/common_all/funding/domain/entity/CashBackBonus.java`

现有字段已包含 `project`、`cash_back_amount`、`income`、`profit`、`cost`、`month`、`account_id` 等，可承载毛利返现数据。

返现项目枚举：

`qbit-core/src/main/java/com/qbit/common_all/funding/enums/CashBackBonusProject.java`

当前已经存在：

| 枚举 | value | 业务含义 |
| --- | --- | --- |
| `QUANTUM_CARD_QI_RS_PROFIT_CASH_BACK` | `QuantumCardQIRSProfitCashBack` | QI 卡 RS 毛利返现 |
| `QUANTUM_CARD_BZ_RS_PROFIT_CASH_BACK` | `QuantumCardBZRSProfitCashBack` | BZ 卡 RS 毛利返现 |

上述两个项目已加入量子账户返现父子项目集合。因此当前缺口重点不是新增底层枚举，而是确认它们是否完整进入返现账单初始化、Invoice/PDF、明细导出和差额计算。

### 2.3 差额账单

差额表为 `api_client_netting_bill`，实体：

`qbit-core/src/main/java/com/qbit/openapi/domain/entity/ApiClientNettingBill.java`

主要关联字段：

| 字段 | 含义 |
| --- | --- |
| `bill_id` | 月账单 ID |
| `rebate_id` | 返现账单 ID |
| `bill_amount` | 轧差时月账单金额 |
| `rebate_amount` | 轧差时返现金额 |
| `amount` | 最终差额 |
| `type` | `NettingDebit`、`NettingRebate`、`NettingEqual` |
| `old_type` | 差额类型修改前的类型 |
| `deal_amount` | 已处理金额 |
| `status` | 差额处理状态 |

当前规则为：

```text
月账单金额 > 返现金额：需要扣款，差额 = 月账单金额 - 返现金额
返现金额 > 月账单金额：需要返现，差额 = 返现金额 - 月账单金额
两者相等：直接结清
```

## 4. 三项主要需求分析

### 4.1 隐藏月账单 0 费用项

当前已有过滤，但不完整：

- `ApiClientBillStatementMapper.xml#apiBillStatementList` 已有 `amount > 0`，Admin 账单明细接口不会返回原始金额为 0 的项。
- 汇总 SQL `getBillTotalAmountByBillId(s)` 主要按 `is_sum` 和费用类型汇总，没有统一按最终有效金额过滤。
- PDF 数据来自 `apiBillStatementIsSumList`，当前未统一增加有效金额大于 0 的展示过滤。
- 额外费用存在父项/渠道子项结构，不能简单对所有记录过滤，否则可能破坏渠道明细和总额展示。

需求落点应覆盖：Admin 明细 API、客户端月账单、PDF、CSV/ZIP 及 Invoice 模板，并统一使用 `COALESCE(adjust_amount, amount)` 判断最终展示金额。

建议验收：一个未开通多项费用的账户，所有下载和明细接口均不显示 0 项，账单总额与实际非 0 项之和一致。

### 4.2 毛利返现纳入差额

当前链路：

1. `cash_back_bonuses` 保存各返现项目数据。
2. 返现账单 `api_client_bill(type=Rebate)` 的 `bill_history_config` 保存返现配置/汇总信息。
3. `dealRebateTotalAmount` 解析 `InitRebateCashbackInfo.amount` 并汇总返现金额。
4. `ApiClientNettingBillServiceImpl` 读取月账单和返现账单金额，写入 `bill_amount`、`rebate_amount` 并计算差额类型。

需要核对的具体缺口：

1. 返现账单初始化是否查询 QI/BZ RS 毛利返现记录。
2. `InitRebateCashbackInfo` 是否包含项目类型、返现记录 ID、金额等追溯字段。
3. 返现 Invoice/PDF 是否只处理消费返现、开卡返现、加密资产交易返现；毛利返现业务上属于消费返现大类，但展示需独立；返现明细 ZIP 增加独立文件 `Infinity Card Revenue Sharing Rebate.csv`，不称为 CSV 的第 4 个 Sheet。
4. 毛利返现 CSV 的本质是查询毛利返现涉及的卡交易，不是导出 `CashBackBonus` 汇总记录。字段按截图使用现有 `QuantumAccountTransactionDetailVO`：`VerifiedName`、`DisplayId`、`Transaction Time`、`Completion Time`、`AccountId`、`TransactionId`、`Transaction status`、`Transaction type`、`Card BIN`、`Card ID`、`CardLastFour`、`Cardholder Name`、`Card label`、`Budget name`、`OriginAmount`、`SettleAmount`、`Fee`、`Transaction currency`、`transactionNotes`；查询条件覆盖 BZ/I2C 和按月份规则纳入的 QI 非 HK 交易。
5. 返现账单新增/修改后，差额订单是否同步重算 `rebate_amount`、`amount`、`type`、`old_type`，并记录操作日志。
6. 返现账单与差额返现通知是否会重复发送；直客并入差额后应关闭原直客账单邮件，按差额结果发送中英文通知。

### 4.3 Admin 客户账单更新时间

当前分支后端已经具备：

- `ApiClientBillMapper.xml#billList` 已查询 `acb.update_time`。
- `QuantumCardApiCustomerBillVO` 已有 `Date updateTime`，并使用时间戳序列化。
- `ApiClientBillMonthBO` 已有账单更新时间导出字段。

因此需要先确认前端未显示的原因：接口实际响应、网关转换、前端字段名称、缓存或使用的是否为其他账单接口。

需要区分三个时间：

| 时间 | 字段 | 用途 |
| --- | --- | --- |
| 月账单更新时间 | `api_client_bill.update_time` | Admin 客户账单列表 |
| 账单明细调账时间 | `api_client_bill_statement.update_time` | 定位费用项变更 |
| 差额订单更新时间 | `api_client_netting_bill.update_time` | 定位差额重算/修改 |

如果业务要求记录“账单变化后差额订单被修改的时间”，仅返回月账单 `updateTime` 不一定充分，还需确认差额列表 VO 是否应返回差额订单更新时间，以及账单更新是否必然触发差额重算。

## 5. 关联需求分析

### 5.1 Active Card Details

需求描述要求月账单新增 `Infinity Card Active Card Details` 明细。由于当前导出链路以 CSV/ZIP 为主，建议在月账单明细 ZIP 中增加独立文件 `Infinity Card Active Card Details.csv`。CSV 没有 Sheet；只有改成 XLSX 后才使用 Sheet 2 的表述。

活跃卡明细必须复用 API 账单已有的活跃卡计费口径：从 `card_status_history` 取账单开始前每张卡的最后状态，再合并账单期间发生过 Active 状态变化的卡，按卡去重后导出。不能直接改用 `dws_sale_active_card`，否则可能与 API 账单 Active Card Fee 的计费数量不一致。

当前 API 账单费用明细主要是费用汇总及渠道拆分，活跃卡明细还需要确认：

- 数据来源是交易/卡状态历史还是月账单生成时的快照。
- 明细粒度是卡号、卡状态、渠道、活跃起止时间还是按渠道汇总。
- PDF、Excel、CSV/ZIP 是否都需要该 sheet。
- 中英文模板、列名和隐私脱敏规则。

不能直接复用 `api_client_bill_statement` 的费用项结构，建议作为月账单导出上下文中的独立明细集合处理。

### 5.2 邮件发送

当前差额计算和通知涉及：

`qbit-core/src/main/java/com/qbit/common_all/api/client/bill/service/impl/ApiClientNettingBillServiceImpl.java`

以及：

`qbit-core/src/main/java/com/qbit/common_all/api/client/bill/service/impl/ApiClientDebitRecordServiceImpl.java`

需重点确认：

- 直客月账单并入差额后，原 `MonthlyStatement`/`Rebate` 邮件是否仍由原流程发送。
- `NettingDebit`、`NettingRebate`、`NettingEqual` 三种结果对应的模板。
- 毛利返现纳入后，邮件中的返现总额、差额金额、账单链接是否一致。
- 中文/英文模板选择是否跟随客户语言配置。
- 失败、重试和重复触发是否幂等。

## 6. 建议的核对与验收顺序

1. 使用一条包含 QI/BZ RS 毛利返现的真实账户月份，核对 `cash_back_bonuses`、返现账单配置、Invoice 明细和差额表四处金额。
2. 对同一月账单验证 Admin 明细、客户端接口、PDF、CSV/ZIP，确认 0 项过滤一致。
3. 修改已复核账单或明细，验证账单更新时间、明细更新时间、差额订单金额/类型/更新时间及操作日志。
4. 验证直客并入差额后的邮件抑制、差额邮件发送、语言和重复触发。
5. 最后确认 Active Card Details 的数据源、字段、模板和脱敏要求，再拆分导出实现任务。
