# admin 销售维度毛利看板开发方案

## 摘要

在 admin 增加按月、按销售汇总的毛利看板。数据层沿用销售返佣的“近期估算视图 + 月度汇总快照 + 月度明细快照”模式，另建毛利专用数据集，不复用佣金金额或计佣规则。首期覆盖应收毛利和现有销售维度毛利；按整体实收口径计算的毛利暂缓。视图刷新、每月 8 号快照及每月 20 号后 API 月账单补入沿用销售返佣的触发节奏。

## 1. 背景与目标

销售返佣已有按销售维度计算和固化的近期视图、月度汇总快照与明细快照。admin 需要增加相近的销售毛利查询能力，按月份选择并展示各销售的收入、返现、成本及毛利。

本需求展示销售业绩口径，不计算销售佣金。复用现有返佣链路的运行模式与触发节奏，毛利指标使用独立视图及快照表，避免与返佣结果及计佣规则混用。

## 2. 范围

### 2.1 首期范围

- admin 增加按月查询、按销售名称汇总的毛利看板。
- 从日粒度销售指标源汇总收入与客户返现。
- 客户返现包含给客户的返现和代收返现。
- 返现总额还包含毛利返现。
- 计算应收口径收入、有效收入、总成本、应收毛利。
- 保留现有销售维度收入与销售毛利口径。
- 建立近期估算视图、月度汇总快照及月度明细快照。
- 沿用销售返佣视图刷新、每月 8 号快照固化、每月 20 号后 API 月账单补入的时点。
- 20 号补入后同步更新对应月份的快照汇总与明细，确保两者一致。

### 2.2 暂缓范围

- 整体实收口径毛利（Cashflow_GP）暂缓；首期不以该字段作为验收项。
- 不新增或调整销售返佣规则、佣金金额、佣金发薪逻辑。
- 不改变收入、成本或返现上游业务计算。
- 不在本方案中直接执行数据库 DDL、Flink 作业或 admin 发布。

## 3. 数据来源与粒度

### 3.1 主要收入与返现来源

dws_sales_metric_daily 是日粒度指标明细表，不是月度汇总表。视图应先按 report_date 将日明细汇总到月份，再按销售 ID 聚合。

| 字段 | 用途 |
|---|---|
| report_date | 日粒度业务日期；用于归属自然月 |
| root_account_id | 根账户维度及明细追溯 |
| product | 产品维度及明细追溯 |
| provider | 渠道/服务商维度及明细追溯 |
| sale_id | 销售维度键 |
| metric_code | 指标类型，如 main、client_rebate、client_collection_rebate |
| metric_type | 收入/成本类别 |
| metric_value | 原始金额，保留来源符号 |
| delete_time | 过滤已删除记录 |

源表注释注明月账单类来源日期记在月初；这类记录仍是源表中的明细记录，按其 report_date 所在月份汇总。

收入来源初步映射为 metric_code = 'main'、metric_type = 'income'。客户返现和代收返现分别读取 client_rebate、client_collection_rebate。需在实现前核实源表实际数据、符号及月账单应收和实时收入的区分字段。

### 3.2 毛利返现、成本和销售维度收入

- 毛利返现需映射到已有销售返佣/毛利数据链路的来源字段；当前提供的 dws_sales_metric_daily 指标样例只有 main、client_rebate、client_collection_rebate，尚未证明它包含毛利返现。
- 总成本沿用当前销售毛利口径，按月及销售归集，并保留负成本或冲销的来源符号。
- Cashflow_Rev_sale 需沿用现有销售毛利中“剔除部分收入”的规则；被剔除的收入项清单在实施前从现有看板/查询确认。
- 销售展示名称通过现有销售 ID 维表或 admin 当前销售返佣使用的映射取得；聚合主键使用 sale_id，名称仅用于展示。

## 4. 指标口径

| 字段 | 首期 | 定义 |
|---|---:|---|
| BD | 是 | 销售名称 |
| Pref_Rev | 是 | 总收入：实时收取的各项收入 + 本月月账单应收 |
| Rebate | 是 | 客户返现 + 代收返现 + 毛利返现 |
| Pref_Rev_effective | 是 | 应收总收入扣除返现后的有效收入 |
| Cost | 是 | 总成本，按来源符号保留 |
| Pref_GP | 是 | 应收毛利：Pref_Rev - Cost |
| Cashflow_Rev_sale | 是 | 销售维度实收收入，按现有规则剔除部分收入 |
| Cashflow_Rev_sale_effective | 是 | 销售维度实收收入扣除返现后的有效收入 |
| Cashflow_GP_sale | 是 | 现有销售毛利口径：Cashflow_Rev_sale - Cost |
| Cashflow_Rev | 暂缓展示 | 总实收收入：实时收取的各项收入 + 历史月账单实收 |
| Cashflow_Rev_effective | 暂缓展示 | 总实收收入扣除返现后的有效收入 |
| Cashflow_GP | 暂缓 | 整体实收毛利：Cashflow_Rev - Cost |

### 4.1 返现与符号处理

- client_rebate 与 client_collection_rebate 都属于返现扣减项；代收返现不可遗漏。
- 返现总额还需包含毛利返现。
- 金额保留源值正负号；负数按负数参与月度汇总和后续计算，不归零、不截断、不使用 ABS 转成正数。
- 有效收入按业务语义扣除返现一次。实现时以返现来源字段的实际符号约定为准：正数金额按扣减项处理，已记录为负数的返现成本按其负值参与计算，不能再将负数二次相减。
- 总成本同样不做非负限制；负成本/成本冲销保留其符号，并按收入 - Cost 计算毛利。
- 不因指标值为零或负数而过滤记录；删除状态仍按 delete_time IS NULL 处理。

## 5. 数据结构方案

新增毛利专用数据对象，名称为建议名，最终按现有 DWS 命名规范确认：

1. dws.mv_sales_gross_profit_recent_estimate：近期估算物化视图，按结算月/报告月、账户、产品、渠道、销售及来源类型保留可追溯明细，并提供销售月汇总指标。
2. dws.dws_sales_gross_profit_snapshot_p：月度销售汇总快照，按快照日期、结算月及销售 ID 保存看板指标。
3. dws.dws_sales_gross_profit_snapshot_detail_p：月度明细快照，保留账户、产品、渠道、日期、指标来源、销售 ID 和金额等追溯字段。

快照采用确定性业务键和 upsert，支持同一快照日期的重跑与 20 号补数。快照主表和明细表需在同一次批任务提交，避免只更新其中一张。

## 6. 刷新和快照时序

| 时点 | 处理 |
|---|---|
| 近期估算刷新 | 沿用销售返佣视图每 12 小时刷新节奏及现有刷新触发方式 |
| 每月 8 号 | 固化上一个结算月的销售毛利汇总与明细快照 |
| 每月 20 号后 | API 月账单生成后补入对应结算月，并按原快照日期幂等更新汇总和明细 |
| 手动补跑/回刷 | 提供结算月和快照日期参数，遵循现有返佣作业的重跑方式 |

20 号补账范围需与 API 月账单实际生成的账期一致。补账完成后，应重新汇总该结算月销售的收入、返现及毛利，并 upsert 主表和明细表；不可只增加明细而让看板汇总落后。

## 7. 看板交互

- 默认按月展示，每个销售一行。
- 以销售名称展示，后台使用 sale_id 关联。
- 展示应收收入、返现、有效收入、成本、应收毛利，以及现有销售维度收入和销售毛利。
- 整体实收毛利列暂不展示；后续启用时直接采用预留口径。
- 数值列保留负数显示，不归零。
- 月份默认值、是否支持月份区间、导出按钮、权限范围和排序方式沿用 admin 现有销售返佣页面；如现有页面没有对应行为，交互实施前补充确认。

## 8. 实施阶段建议

1. 口径核对：确认 dws_sales_metric_daily 日粒度数据、指标符号、账单应收/实收区分、毛利返现来源、销售毛利收入剔除清单及销售 ID 到名称映射。
2. 数据视图：创建毛利近期估算视图，先按日、月、销售逐层核对汇总，确保不丢负值和跨产品/渠道金额。
3. 快照数据集：创建月度汇总与明细快照表，实现 8 号固化、20 号 API 账单补入及幂等回刷。
4. admin 接入：新增按月销售毛利接口和表格，接入汇总快照并按当前返佣页的权限、查询和导出规范实现。
5. 验收：对照现有客户毛利/销售返佣来源核对指定月份、销售和金额；覆盖 8 号固化、20 号补账、负数、无数据销售和重跑场景。

## 9. 验收标准

- 每个结算月、每个销售只产生一条汇总行，销售名称映射正确。
- 日粒度收入与返现按 report_date 汇总至正确月份，月初记录不会落到其他月份。
- 应收收入、返现、有效收入、成本及毛利与对应来源明细可追溯、可对账。
- client_rebate 与 client_collection_rebate 均纳入返现扣减，毛利返现按确认后的来源并入 Rebate。
- 任意负数原样保留并参与计算；结果中不存在把负数截成 0 的逻辑。
- 每月 8 号快照覆盖上一个结算月；20 号 API 月账单补入后汇总和明细一致，重复执行不会重复累计。
- 首期不将整体 Cashflow_GP 作为交付字段；现有销售维度毛利字段仍按确认后的现有口径输出。

## 10. 实施前待确认

1. dws_sales_metric_daily 是否已包含所有产品/渠道需要的收入及两类返现；main 中实时收入、本月月账单应收的区分方式。
2. 毛利返现的数据源、正负号约定，以及它与客户返现/代收返现是否存在重叠，避免重复扣减。
3. 总成本来源及其是否与 dws_sales_metric_daily 中的成本指标部分重合。
4. 现有 Cashflow_Rev_sale 剔除收入项清单和销售毛利的验证基准。
5. 20 号 API 月账单对应的结算月、快照日期及在毛利场景中的汇总回写方式。
6. admin 现有销售返佣查询页中的月份默认值、权限与导出行为，以及“销售”是否只包含 sale_id。


## 补充：四个 admin 接口

首期提供两个分页查询接口和两个文件导出接口。所有接口复用销售返佣页面的 Admin 鉴权与数据权限校验；月份格式为 yyyy-MM。

### 月度销售汇总分页

- 方法与路径：GET /api/admin/sale/gross-profit/page
- 参数：settlementMonth 必填，格式 yyyy-MM；page 从 1 开始，默认 1；pageSize 默认 20，最大值沿用 admin 分页规范；saleId 可选，用于精确筛选销售。
- 响应：total、page、pageSize、items。
- 每条 item 包含 saleId、saleName、prefRev、rebate、prefRevEffective、cost、prefGp、cashflowRevSale、cashflowRevSaleEffective、cashflowGpSale、snapshotDate、dataStatus。
- dataStatus 标记 SNAPSHOT 或 ESTIMATE。对应月份已有快照时读汇总快照；尚无快照时读近期估算视图。

### 销售月度明细分页

- 方法与路径：GET /api/admin/sale/gross-profit/detail
- 参数：settlementMonth 和 saleId 必填；page、pageSize 使用相同分页约定；rootAccountId、product、provider、metricCode 可选筛选。
- 响应：total、page、pageSize、items。
- 每条明细至少包含 reportDate、rootAccountId、product、provider、saleId、metricCode、metricType、metricValue；金额保留源正负号。
- 已生成月份快照时读取明细快照；否则读取近期估算视图。明细应能追溯日粒度来源和报表指标构成。

### 月度销售汇总导出

- 方法与路径：POST /api/admin/sale/gross-profit/export
- 请求体：settlementMonth 必填；saleId 可选；筛选项与汇总分页接口一致。
- 导出范围为所有满足筛选条件的销售汇总记录，不受分页接口当前页限制。
- 复用返现金明细导出流程，由对应 ExportEnum 策略生成导出文件，并将结果加入 exportFiles。接口返回与文件交付方式沿用现有导出框架。
- 数据读取优先级与汇总分页接口一致，导出列与看板汇总列一致。

### 销售月度明细导出

- 方法与路径：POST /api/admin/sale/gross-profit/detail/export
- 请求体：settlementMonth、saleId 必填；rootAccountId、product、provider、metricCode 可选。
- 导出指定销售、月份及筛选条件命中的全部明细，不受明细分页接口当前页限制。
- 复用返现金明细导出流程，由明细 ExportEnum 策略生成文件并加入 exportFiles；读取和写出按批处理，避免一次性加载整月数据。
- 数据读取优先级与明细分页接口一致；导出列与明细分页接口字段一致，并补充销售名称。

### 查询与导出一致性

- 四个接口统一校验月份格式、销售数据权限和查询范围。
- 快照存在时查询和导出读取同一快照版本；快照不存在时统一回退到近期估算视图。
- 每月 20 号 API 月账单补入后，汇总和明细快照按原 snapshotDate 更新，使分页查询与两类导出读取一致的数据版本。
- 两个分页接口使用数据库分页；两个导出接口遍历完整筛选结果并分批处理，不受单页 page/pageSize 限制。
- 导出不将负数归零、过滤或转换符号。

### 导出实现约定（按返现金明细导出模式）

两个导出接口分别注册汇总与明细的 ExportEnum 策略，并按现有代码调用链收集导出文件：

- 汇总导出：构造 SalesGrossProfitExportDTO，调用 ReportFactory.getInvokeStrategy(ExportEnum.SALES_GROSS_PROFIT_REPORT.getValue()).exportUrl(dto)，再通过 appendExportFiles(exportFiles, ...) 加入导出结果。
- 明细导出：构造 SalesGrossProfitDetailExportDTO，调用 ReportFactory.getInvokeStrategy(ExportEnum.SALES_GROSS_PROFIT_DETAIL_REPORT.getValue()).exportUrl(dto)，再通过 appendExportFiles(exportFiles, ...) 加入导出结果。
- DTO 承载月份、销售筛选及各自的导出筛选条件；明细 DTO 要求 saleId。
- ReportFactory 策略负责对应 Excel 内容与文件地址生成；文件收集、下载交付和错误处理遵循返现金明细现有实现，不另造一套通知机制。

参考调用形式：

    appendExportFiles(exportFiles, ReportFactory.getInvokeStrategy(
        ExportEnum.QUANTUM_CARD_CONSUME_CASHBACK_REPORT.getValue()).exportUrl(cashbackDetailDTO));

以上 ExportEnum 名称和 DTO 名称为方案建议，开发时按代码库现有命名规范调整。

## 详细设计补充（评审稿）

以下字段、枚举名和接口 DTO 是可落地的建议结构；收入、成本、毛利返现的物理来源仍以第 11 节的核对结果为准。实施前先完成来源映射，再固定最终 DDL。

### 1. 数据处理链路

1. 从 dws_sales_metric_daily 读取未删除的日明细，保留 report_date、sale_id、root_account_id、product、provider、metric_code、metric_type、metric_value。
2. 将来源统一映射为报表组成项：实时收入、本月账单应收、历史月账单实收、客户返现、代收返现、毛利返现、成本及销售口径收入。映射阶段只分类来源，不抹掉原始符号。
3. 按 report_date 所属月份、sale_id、root_account_id、product、provider 聚合成估算明细视图。
4. 汇总估算明细形成每月每销售一行的估算视图，用于实时查询。
5. 每月 8 号固化上个结算月的明细快照和销售汇总快照。20 号 API 月账单补入后，刷新相关月份并按同一 snapshot_date 重算及 upsert 两张快照。
6. admin 两个分页接口读取汇总/明细；两个导出策略读取同样的数据源路由，保证屏幕与文件金额一致。

### 2. 估算视图粒度和字段

#### 2.1 月度销售汇总视图

建议视图名：dws.mv_sales_gross_profit_recent_estimate。

唯一业务粒度：settlement_month + sale_id。它面向销售列表，不把 root_account_id、product 或 provider 放入汇总主键。

字段建议：

| 字段 | 类型建议 | 说明 |
|---|---|---|
| id | bigint | 按 settlement_month、sale_id 生成稳定键 |
| settlement_month | date | 月份统一存月初日期 |
| sale_id | varchar(64) | 销售用户 ID |
| sale_name | varchar(255) | 刷新时解析的展示名称；为空时用销售 ID 兜底 |
| pref_rev | numeric(20,4) | 实时收入 + 本月月账单应收 |
| client_rebate | numeric(20,4) | 客户返现来源值，保留符号 |
| client_collection_rebate | numeric(20,4) | 代收返现来源值，保留符号 |
| gross_profit_rebate | numeric(20,4) | 毛利返现来源值，保留符号 |
| rebate | numeric(20,4) | 三类返现按确认后的符号口径合计 |
| pref_rev_effective | numeric(20,4) | 扣减返现后的应收有效收入 |
| cost | numeric(20,4) | 成本合计，保留负数及冲销 |
| pref_gp | numeric(20,4) | pref_rev - cost |
| cashflow_rev_sale | numeric(20,4) | 现有销售口径实收收入 |
| cashflow_rev_sale_effective | numeric(20,4) | 销售口径实收收入扣返现后的金额 |
| cashflow_gp_sale | numeric(20,4) | cashflow_rev_sale - cost |
| refreshed_at | timestamp(6) | 本次视图刷新标记 |

整体实收字段 Cashflow_Rev、Cashflow_Rev_effective、Cashflow_GP 暂不作为首期接口/表格必需列；若数据源合并成本低，可以在视图中预留，但不能将其误标为已交付功能。

#### 2.2 月度销售明细视图

建议在汇总估算视图之前建立内部明细视图，粒度为 settlement_month + sale_id + root_account_id + product + provider。provider 允许为空，空值必须作为独立维度保留，不能与任意具体 provider 合并。

字段在 2.1 的金额组成列之外，至少包含 report_date（按月聚合时可输出月份）、root_account_id、product、provider，以及用于审计来源的 metric_code / source_type。明细 API 展示客户、产品和渠道拆分；收入、返现和成本组成列应保留，方便财务对账。

### 3. 快照表结构草案

#### 3.1 汇总表 dws.dws_sales_gross_profit_snapshot_p

沿用销售佣金汇总快照的分区与主键模式：按 snapshot_date 做 RANGE 分区，主键为 (id, snapshot_date)，每年建一个分区；增加 settlement_month + sale_id 查询索引。

| 字段 | 类型建议 | 约束/说明 |
|---|---|---|
| id | bigint | not null；由 snapshot_date、settlement_month、sale_id 稳定生成 |
| snapshot_date | date | not null；通常为每月 8 号，分区键 |
| settlement_month | date | not null；目标结算月月初 |
| sale_id | varchar(64) | not null |
| sale_name | varchar(255) | 固化时销售展示名称，历史显示稳定 |
| pref_rev | numeric(20,4) | not null default 0 |
| client_rebate | numeric(20,4) | not null default 0 |
| client_collection_rebate | numeric(20,4) | not null default 0 |
| gross_profit_rebate | numeric(20,4) | not null default 0 |
| rebate | numeric(20,4) | not null default 0 |
| pref_rev_effective | numeric(20,4) | not null default 0 |
| cost | numeric(20,4) | not null default 0 |
| pref_gp | numeric(20,4) | not null default 0 |
| cashflow_rev_sale | numeric(20,4) | not null default 0 |
| cashflow_rev_sale_effective | numeric(20,4) | not null default 0 |
| cashflow_gp_sale | numeric(20,4) | not null default 0 |
| version | int4 | 默认 1 |
| remarks | varchar(1000) | 可空，记录 snapshot / api supplement / manual rebuild |
| create_time / update_time | timestamp(6) | not null；重跑时 update_time 更新 |

分区/索引建议：主键 (id, snapshot_date)；查询索引 (settlement_month, sale_id)。金额字段不得加 CHECK (amount >= 0)。

#### 3.2 明细表 dws.dws_sales_gross_profit_snapshot_detail_p

沿用销售佣金快照明细的快照日期分区模式。建议快照明细粒度为 snapshot_date + settlement_month + sale_id + root_account_id + product + provider；provider 为空视为独立业务键。

| 字段组 | 字段建议 |
|---|---|
| 快照键 | id、snapshot_date、settlement_month |
| 销售与客户 | sale_id、sale_name、root_account_id |
| 业务拆分 | product、provider |
| 来源追踪 | report_month、metric_code/source_type |
| 金额组成 | pref_rev、client_rebate、client_collection_rebate、gross_profit_rebate、rebate、pref_rev_effective、cost、pref_gp、cashflow_rev_sale、cashflow_rev_sale_effective、cashflow_gp_sale |
| 审计字段 | version、remarks、create_time、update_time、delete_time |

主键建议 (id, snapshot_date)，id 由快照日期、结算月、销售、客户、产品和 provider 的长度编码组成后计算稳定 hash；业务维度值需要明确 NULL 编码，避免空渠道和字符串空值冲突。增加 (settlement_month, sale_id, root_account_id) 及 (settlement_month, sale_id, product) 查询索引。

重跑时以确定性 id 做 upsert；若源数据重算导致旧明细消失，任务必须同步清理或软删除该结算月、快照日期范围内不再存在的明细，再提交汇总，以免旧快照残留。

接口路径为方案建议，可按 admin 当前 Controller 命名空间微调。月份均为 yyyy-MM，金额用 BigDecimal/numeric 语义传递，避免二进制浮点舍入。

#### 4.2 明细分页

GET /api/admin/sale/gross-profit/detail

响应字段：settlementMonth、dataStatus、snapshotDate、page、pageSize、total、items。每条 item 至少包含 rootAccountId、product、provider、saleId、saleName、prefRev、三类返现及 rebate、prefRevEffective、cost、prefGp、cashflowRevSale、cashflowRevSaleEffective、cashflowGpSale。

排序建议 rootAccountId ASC、product ASC、provider ASC；同一客户产品渠道只有一行，分页总数按该粒度统计。

DTO 建议 SalesGrossProfitExportDTO：settlementMonth 必填、saleId 可选。导出所有匹配销售，不受列表 page/pageSize 限制。Excel 列顺序：月份、销售 ID、销售名称、Pref_Rev、客户返现、代收返现、毛利返现、Rebate、Pref_Rev_effective、Cost、Pref_GP、Cashflow_Rev_sale、Cashflow_Rev_sale_effective、Cashflow_GP_sale。

注册汇总 ExportEnum 策略后，按返现金明细模式调用 ReportFactory 策略的 exportUrl(dto)，并通过 appendExportFiles(exportFiles, ...) 收集文件。文件名建议 sales-gross-profit-YYYY-MM.xlsx。

#### 4.4 明细导出

POST /api/admin/sale/gross-profit/detail/export

DTO 建议 SalesGrossProfitDetailExportDTO：settlementMonth、saleId 必填；rootAccountId、product、provider 可选。导出该销售该月所有匹配明细，不受明细分页页码限制。

Excel 列顺序：月份、销售 ID、销售名称、客户 ID、产品、渠道、应收收入、客户返现、代收返现、毛利返现、返现合计、有效收入、成本、应收毛利、销售维度收入、销售维度有效收入、销售毛利。

注册独立明细 ExportEnum 策略，调用方式与汇总导出一致。文件名建议 sales-gross-profit-detail-{saleId}-YYYY-MM.xlsx。沿用返现金明细导出的文件收集、错误处理和响应行为，不另外设计通知流程。

### 5. 数据路由、分页与导出行为

- 对结算月查询时，优先查该结算月最新有效 snapshot_date；不存在快照时查近期估算视图，并返回 dataStatus=ESTIMATE、snapshotDate=null。
- 存在快照时 page、detail 和两类 export 必须绑定同一个 snapshot_date，避免不同接口读取到不同版本。
- 汇总分页在数据库执行过滤、稳定排序和分页；明细分页先按确定的销售/月筛选，再分页，不在 Java 内存中全量加载后分页。
- 导出任务使用相同筛选器和数据路由，分批读取结果并流式写 Excel；导出不继承单页 page/pageSize，但应设置最大行数或文件分片策略，沿用现有导出框架限制。
- 管理员鉴权、销售数据范围校验、导出文件权限和错误返回复用销售返佣/返现金明细现有实现。
- 销售名称优先取快照 sale_name；估算视图取刷新时销售维表名称。名称为空时仍返回 sale_id，不丢弃该销售金额。

### 6. 计算和一致性规则

1. 先依据确认后的 source_type/metric_code 将收入分为实时收入、本月账单应收、历史账单实收和销售口径收入，再聚合，不可仅凭 report_date 猜测收入类型。
2. client_rebate、client_collection_rebate、gross_profit_rebate 分列保存，Rebate 由三者按源符号约定合并。Pref_Rev_effective 从 Pref_Rev 中扣减这三类返现一次；如返现来源已经为负数，直接按负值参与，禁止二次取负或再次减负数。
3. Cost 按现有业务口径取有符号成本汇总；Pref_GP = Pref_Rev - Cost；Cashflow_GP_sale = Cashflow_Rev_sale - Cost。
4. 每个衍生字段与其输入字段使用相同的销售、月份、成本范围，禁止在不同层级重复 JOIN 后造成金额倍增。
5. 保留真实零值和负值；禁止 GREATEST(value, 0)、ABS(value)、过滤 value > 0 等截断逻辑。
6. 汇总快照必须可由明细快照重新聚合复现；明细聚合后与主表金额逐字段相等。

### 7. 验收用例

| 场景 | 预期 |
|---|---|
| 正常月份收入及正成本 | Pref_GP 等于 Pref_Rev 减 Cost |
| 返现来源含 client_rebate 与 client_collection_rebate | 两项均出现在明细及汇总 Rebate 中，effective revenue 只扣减一次 |
| 返现、成本或收入出现负值 | 原始负号保留，汇总及导出显示负值，不归零 |
| provider 为 NULL | NULL provider 单独一组，不与空串或其他 provider 混并 |
| 8 号重复执行快照任务 | 同一 snapshot_date 下无重复主表或明细行，金额不累加两次 |
| 20 号 API 月账单补入后重跑 | 原快照日期的明细与汇总同步更新，汇总可由明细复算一致 |
| 销售没有名称或已离职 | sale_id 对应金额仍返回，名称可为空或按现有用户映射回退 |
| 查询分页边界及相同排序值 | 按稳定二级键分页，无重复、漏行 |
| 同一月份切换估算到快照 | dataStatus/snapshotDate 明确变化，四接口读取同一数据版本 |
| 明细导出结果超过单页大小 | 导出包含全部命中记录；后台分批处理，不受 pageSize 限制 |

### 8. 开发前必须关闭的口径阻塞项

- dws_sales_metric_daily 的 metric_code 是否能区分实时 main 与本月月账单应收；若不能，需要额外数据源或上游分类字段。
- 毛利返现及销售维度 Cost 的权威数据源与字段名；避免同一金额既从 sales metric 又从已有销售毛利视图重复相加。
- 代收返现和客户返现的源值符号样例，确认 Rebate 展示符号及 effective revenue 的唯一正确运算。
- Cashflow_Rev_sale 排除项、对应成本是否仍全额计入，以及现有销售毛利的对账月份。
- 20 号 API 月账单落属的 settlement_month 和历史快照重算边界。
- 实际 admin Controller 路径、分页封装、导出策略注册名、DTO 命名、Excel 生成限制应在目标代码库逐项对齐；本方案列出的接口和类型均为建议值。

### 第一步：建表并创建增量物化视图

**仓库：** martin-dev-log/bi-cost。

3. 新建销售毛利增量物化视图：先产出月度销售/客户/产品/渠道明细，再汇总为月度销售列表。查询结构只使用当前 ADBPG 支持增量维护的表达式；若某个 JOIN 或聚合不满足增量物化视图限制，先调整查询边界再建，不回退成无界全量刷新的普通视图。
4. 增量物化视图应输出返现组成字段，保留正负号；总成本和派生毛利按确定的来源口径计算。首期不交付整体 Cashflow_GP。

**交付物：** 两张快照表 DDL、增量物化视图 SQL、月度对账 SQL。

### 第二步：快照脚本

**仓库：** martin-dev-log/bi-cost。

1. 建立每月 8 号快照任务，读取上一个结算月的增量物化视图，写入同一 snapshot_date 下的汇总和明细快照。
2. 建立每月 20 号 API 月账单补入脚本。先更新/等待增量物化视图包含当期月账单，再按原 snapshot_date 重算目标结算月的明细和汇总。
3. 两张快照采用确定性主键和 upsert；补数使用完整目标月重算，不把补入金额累加到旧汇总。若源记录被删除或修正，任务同步移除或软删除快照中已失效明细。
4. 快照日期保持 8 号生成的日期；同月 20 号补入只更新该日期快照的数据版本。
5. 提供可传 settlement_month、snapshot_date 的手动回刷参数，并验证重复执行结果不变。

**交付物：** 8 号月快照脚本、20 号 API 月账单补入脚本、手动回刷/验证 SQL。
