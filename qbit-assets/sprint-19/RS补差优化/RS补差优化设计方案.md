# RS 月账单服务设计

## 意图

将 `*RS 返现补差费用` 的月账单查询和汇总规则集中到独立服务，供直客月账单和 API 月账单共同调用，维护方式与活跃卡 fee 对齐。

## 目标与范围

- 新增单一具体 RS 月账单服务，集中封装返现补差查询、账户维度组织及汇总行生成。
- API 月结编排和直客月账单生成流程都直接调用该服务，避免账单编排层各自持有规则。
- 保持现有费用来源、账单类型、费用类型和展示数据结构不变。

## 非目标

- 不新增管理端配置入口或数据库配置。
- 不改变 RS 补差计算规则、查询口径或账单展示行为。
- 不调整活跃卡 fee 服务或无关账单流程。

## 约束

- 沿用现有 `CashBackBonusMapper#getRevenueAdjustments` 数据来源和 `ApiClientMonthFeeVO` 返回结构。
- 服务置于现有账单业务域；API 和直客流程直接共用该服务的 provider 明细及汇总结果。
- 保持当前 API 账单的费用汇总结果，以及直客账单的汇总金额和 FREE/Pending 状态判定。
- 遵循仓库规范，不为单实现协作者新增接口。

## 方案

- 保留现状：继续在 `ApiClientTransactionServiceImpl` 中处理。改动少，但 RS 规则仍耦合在 API 账单编排边界。
- 新增单一具体 RS 月账单服务（采用）：对齐活跃卡 fee 的独立维护边界，API 月结和直客月账单生成流程都直接调用它。
- 新建一个统管所有月账单费用的通用服务：会把活跃卡等既有职责再聚合，超出本次 RS 统一维护范围。

## 实施选择

采用单一具体 `RevenueAdjustmentBillService`。保留 `ApiClientTransactionService` 现有公共方法作为兼容委托，但 API 与直客账单生成流程都直接调用新服务。新增测试覆盖 provider 明细、账户汇总和兼容委托行为，并检查两类账单的直接调用及拼接方式。
