# 消费返现明细导出优化开发方案

## 背景与目标

消费返现明细导出查询 `quantum_card_transaction_extend_p`。测试库表结构显示，该表按 `create_time` 做季度范围分区，数据规模可能达到数亿行。当前查询使用 `transaction_time` 和 `completion_time` 过滤，但不限制分区键 `create_time`，因此数据库无法按返现月份有效裁剪分区；查询同时关联账户、卡、持卡人和预算组表，并按页码执行分页，可能放大查询耗时和数据库负载。

本次优化目标是在不改变返现月份、账户范围、渠道、状态及导出字段语义的前提下，缩小扫描分区，降低大表查询中的关联与分页成本，并控制导出期间的内存和数据库并发压力。

## 当前查询涉及的字段

`quantum_card_transaction_extend_p` 已提供账户名称、账户 DisplayId、交易时间、完成时间、账户 ID、卡 ID、原始交易 ID、数字交易 ID、卡末四位、BIN、金额、手续费、备注、状态、渠道及交易范围等导出或筛选字段。

当前查询关联表用于补充：

| 表 | 关联字段 | 用途 |
| --- | --- | --- |
| `qbitCard` | `label`、`cardholderId`、`groupId` | 卡标签及后续关联键 |
| `cardholder` | `user_name` | 持卡人姓名 |
| `qbitCardGroup` | `groupName` | Budget 名称 |
| `account` | 无 CSV 展示字段 | 当前用于账户范围过滤 |

## 设计方案

### 1. 为分区键增加安全的时间范围

返现月份仍由 `completion_time` 决定，现有 `transaction_time` 业务过滤保持不变。另给 `create_time` 增加范围：

- 下界：返现月份开始时间向前推三个月。
- 上界：返现月份结束边界，使用左闭右开区间，即小于下月第一天。

例如导出 2026 年 9 月：`create_time >= 2026-06-01 00:00:00` 且 `create_time < 2026-10-01 00:00:00`；`completion_time` 仍限制在 2026 年 9 月。

查询中直接比较 `create_time` 列与时间参数，不对分区列做函数或类型转换，使 PostgreSQL 可以进行分区裁剪。按季度分区时，自然月加三个月回溯通常只需访问约两个季度分区。上线前确认生产库分区定义与测试库一致，并确认三个月覆盖允许的创建与完成时间跨度。

### 2. 主查询和 count 查询只访问扩展表

主查询先从 `quantum_card_transaction_extend_p` 读取交易行和已冗余字段。账户筛选改为直接基于 `qcte.account_id`：

- API 客户及子账户按 `api_account_relation` 限定账户 ID。
- 其他账户按根账户及子账户关系限定账户 ID。
- 渠道和 QI 范围使用扩展表已有的 `channel_provision`、`transaction_scope` 字段。

count 查询不再复用带展示字段关联的查询片段；如果采用流式分页，则不做导出前的全量精确 count。

### 3. 分页后批量补齐展示字段

每批查询完成后，根据当前页的 `card_id` 批量读取 `qbitCard` 的 `label`、`cardholderId`、`groupId`；随后分别按 ID 集合批量读取 `cardholder.user_name` 和 `qbitCardGroup.groupName`。通过内存 Map 回填 CSV 字段，避免主查询逐行关联，也避免逐行查询造成 N+1。

账户名称、DisplayId、末四位、BIN 等扩展表已有字段直接使用，不额外查询。

### 4. 使用游标分页并按批输出

以 `completion_time` 和唯一稳定的 `card_transaction_id` 组成排序与游标条件，按固定批量读取下一页，避免 `OFFSET` 越来越深导致后续页扫描成本增加。已完成交易应保证 `completion_time` 非空；游标排序字段必须能确定唯一顺序。

按文件行数阈值分段写 CSV，不将整个返现月份的全部记录一次性载入内存。分页并发设置上限，避免多个超大导出同时将查询请求压入数据库连接池。

## 实施步骤

1. 对照生产环境确认分区键、季度分区边界和父子表索引定义。
2. 保存当前消费返现 count 查询与分页查询的执行计划和耗时，作为基线。
3. 为查询加入 `create_time` 左闭右开范围，并验证执行计划只访问目标季度分区。
4. 将账户范围条件下推到 `qcte.account_id`，将 count 查询从展示关联中拆出。
5. 实现每页卡、持卡人、预算组批量补齐，并移除对应主查询 JOIN。
6. 将 offset 分页改成稳定游标分页，并按阈值分批写出文件。
7. 对相同账户、月份和筛选条件比较优化前后的行数、导出字段、查询耗时、扫描分区数与峰值内存。
8. 根据执行计划再决定是否补充分区索引。索引候选方向为账户 ID、完成时间、卡交易 ID；需结合账户过滤选择性和分区裁剪结果验证后确定，不先盲目加索引。

## 验收标准

- 查询结果与现有业务条件一致，行数、交易 ID、数字交易 ID、费用、账户及卡展示字段无遗漏或重复。
- `create_time` 范围触发预期的季度分区裁剪；执行计划不扫描无关分区。
- count 不再执行账户、卡、持卡人、预算组展示关联；主查询不再执行这些逐行关联。
- 导出翻页不依赖大 offset，不对每个分页重复做全量 count。
- 大文件按批写出，分页并发受限，峰值内存不随整月总行数线性增长。
- 覆盖三个月回溯边界、跨季度月份、账户及子账户筛选、QI 范围筛选、最后一页和多文件切分场景。

## 风险与前置确认

- 三个月创建时间回溯必须覆盖真实的交易生命周期；若存在创建时间晚于完成时间且延迟超过上界的记录，需为写入延迟留边界，否则会漏数。
- 测试库的分区结构需要与生产环境核对，不能仅凭测试库 DDL 推断生产分区。
- 游标分页必须使用稳定排序，并处理同一完成时间下的唯一 ID tie-breaker。
- 展示字段从实时关联改为分页后批量补齐时，应保持原有软删除和空值展示行为。
- 新增索引应在目标分区执行计划和数据分布基础上确定，并评估写入开销与存储成本。
