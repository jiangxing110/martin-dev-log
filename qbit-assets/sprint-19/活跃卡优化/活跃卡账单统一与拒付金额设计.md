# 活跃卡账单统一处理与金额拒付历史配置设计

## 意图

统一直客/API 月账单活跃卡费用和 ZIP 活跃卡明细的服务入口，集中维护账期、provider 与卡状态查询；同时在 API 月账单 `bill_history_config` 补充金额维度的拒付数据。

## 目标与非目标

- 抽取活跃卡账单服务，统一承载账单费用计算和活跃卡明细查询；直客/API 账单及 ZIP 导出都调用该服务。
- `bill_history_config` 保存 `rejectPayAmount`（拒付金额）、`conAmount`（无验证消费金额）和 `rejectPayRateAmount`（金额拒付率）。
- 保留 API 与直客当前各自的费率类型和金额计算规则，不在本需求内改变收费口径。
- 不增加 PDF 或账单详情模板对金额拒付数据的展示，不调整拒付罚款规则，不回填历史账单。

## 方案

1. **共享活跃卡账单服务，按用途保留查询形态（选定）**：服务统一账期/provider/状态规则和费用计算入口；账单收费使用 provider 汇总查询，ZIP CSV 使用逐卡明细查询，避免费用计算加载全部卡明细。费用计算保留调用方现有的 `AccountFeeType`，确保收费口径不变。
2. **逐卡数据作为唯一入口**：账单和 ZIP 都读取逐卡结果，再聚合费用。数据入口更少，但账单生成需要加载全部卡片，成本较高。

采用方案一。金额拒付方面复用现有风控结果的拒付金额、无验证消费金额与金额拒付率，透传并序列化到历史配置。

## 约束与验收

- 活跃卡费用汇总查询与逐卡明细查询继续分开，但都由统一服务提供。
- 直客与 API 继续使用各自既有费率类型、费率门槛、provider 映射与豁免规则。
- 两条 API 账单生成路径保存三个金额字段；旧历史 JSON 可兼容反序列化。
- 新金额字段不进入 PDF 参数或模板；拒付罚款计算不变。
