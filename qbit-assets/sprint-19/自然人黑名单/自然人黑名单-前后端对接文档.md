# 自然人黑名单前后端对接文档

> 本文按 `qbit-assets` 当前自然人黑名单 Controller、DTO、VO 和 Service 实现整理，供前端联调及删除处置调用方接入使用。接口路径以实际 Controller 为准；KYC/SumSub 的 Node 调用属于内部校验流程，不是本管理端接口。

## 1. 基本约定

- 管理端接口前缀：`/api/admin/natural-person-blacklists`。
- 管理端 HTTP 接口统一使用 POST；查询条件和业务参数放在 JSON body 中，导入检查使用 multipart/form-data。字段名为 JSON camelCase。
- 管理端请求按现有登录态和后台鉴权方式携带认证信息；操作人由后端通过 `UserContext.getUser()` 获取，不放在请求参数或请求体中。
- 统一响应为 `Result<T>`：`code`、`message`、`data`。成功时 `code=200`、`message="success"`。
- 分页参数为 `current`（页码，从 1 开始）和 `size`（每页条数，默认 10；名单分页最大 500）。
- 时间字段返回 Java `Date` 序列化结果；前端按项目统一时间格式化组件展示。
- 列表和详情的身份值默认脱敏；原文由单独的“小眼睛”接口读取。原文查询和明文导出的按钮权限由前端权限体系控制。

## 2. 接口清单

| 功能 | 方法 | 路径 | 请求 | 响应 |
| --- | --- | --- | --- | --- |
| 分页查询名单 | POST | `/api/admin/natural-person-blacklists/page` | JSON：分页及筛选条件 | `Result<Page<NaturalPersonBlacklistVO>>` |
| 查询名单详情 | POST | `/api/admin/natural-person-blacklists/detail` | JSON：`blacklistId` | `Result<NaturalPersonBlacklistVO>` |
| 查看身份原文 | POST | `/api/admin/natural-person-blacklists/identity/plaintext` | JSON：`blacklistId`、`identityId` | `Result<NaturalPersonBlacklistIdentityVO>` |
| 手工新增 | POST | `/api/admin/natural-person-blacklists` | JSON | `Result<Long>`，data 为名单 ID |
| 解除单条 | POST | `/api/admin/natural-person-blacklists/release` | JSON：`blacklistId`、`remarks` | `Result<Void>` |
| 批量解除 | POST | `/api/admin/natural-person-blacklists/batch-release` | JSON | `Result<List<NaturalPersonBlacklistBatchReleaseVO>>` |
| 全局分页查询命中明细 | POST | `/api/admin/natural-person-blacklists/hits` | JSON：分页及筛选条件 | `Result<Page<NaturalPersonBlacklistHitItemVO>>` |
| 查询命中明细原文 | POST | `/api/admin/natural-person-blacklists/hits/details` | JSON：`hitId`、`blacklistId`、`identityType` | `Result<NaturalPersonBlacklistHitDetailVO>` |
| 上传并检查导入文件 | POST | `/api/admin/natural-person-blacklists/imports/check` | multipart 文件 | `Result<NaturalPersonBlacklistImportResultVO>` |
| 确认批量导入 | POST | `/api/admin/natural-person-blacklists/imports/confirm` | JSON | `Result<NaturalPersonBlacklistImportResultVO>` |
| 异步导出 | POST | `/api/admin/natural-person-blacklists/export` | JSON 筛选条件 | `Result<Void>`，文件按现有异步导出通知流程获取 |
| 删除处置联动加黑 | 内部 Service 调用 | `NaturalPersonBlacklistService.addFromDisposition(...)` | Java 方法参数 | 返回新建名单 ID（`Long`）；不是 HTTP 接口 |

> 操作日志继续复用管理端统一 `admin-graphql` 的 `adminOperationLogs` 查询，按名单 `recordId` 查询；这里不增加黑名单专用日志 HTTP 接口。

## 3. 删除处置联动加黑（内部 Service 契约）

删除处置业务在处置成功且满足加黑条件后，直接调用 Assets 内的 Service 方法；该能力不暴露给前端，也不新增 HTTP 路由。

```java
Long blacklistId = naturalPersonBlacklistService.addFromDisposition(
        createDTO,
        businessType,
        businessId,
        accountId
);
```

方法签名：

```java
Long addFromDisposition(
        NaturalPersonBlacklistCreateDTO request,
        String businessType,
        String businessId,
        String accountId
)
```

| 参数 | 说明 |
| --- | --- |
| `request.email` | 邮箱，可与证件信息同时提供；按邮箱规则规范化 |
| `request.countryCode` | 国籍 ISO alpha-2 代码；提供证件时必填 |
| `request.idType` | 系统现有证件类型；提供证件时必填 |
| `request.documentNumber` | 证件号；提供证件时必填 |
| `request.remarks` | 加黑原因，必填，最多 255 字符 |
| `businessType` | 处置业务类型，必填，写入 `sourceBusinessType` |
| `businessId` | 处置业务 ID，必填，写入 `sourceBusinessId`；稳定性和重试复用由调用方保证 |
| `accountId` | 关联账户 ID，可空；用于名单关联和操作日志 |

成功时创建 `ACTIVE` 名单，来源为 `DISPOSITION`，写入身份信息和操作日志，并返回新名单 ID。方法带事务，名单、身份和操作日志写入随事务提交或回滚。身份已存在等业务异常会向调用方抛出（例如身份冲突 `11010101016`、身份格式错误 `11010101017`）。

**失败处理、重试、补偿和幂等由删除处置调用方负责。** 此 Service 不承诺按 `businessId` 去重，也不提供回执查询或重放接口。调用方应在自身处置流程中处理异常，并用稳定的处置业务 ID 实现所需幂等策略。

调用方需要在其模块中注入并调用 `NaturalPersonBlacklistService`；若处置代码位于独立应用，不能直接注入该 Java Bean，则需由双方另行确认跨应用调用方式，本方案当前没有定义 HTTP/Feign 接口。

## 4. 名单查询

### 请求参数

`POST /api/admin/natural-person-blacklists/page`

筛选和分页条件放入 JSON body。

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `current` | integer | 否 | 页码，默认 1 |
| `size` | integer | 否 | 每页条数，默认 10，最大 500 |
| `status` | string | 否 | `ACTIVE` 生效中、`RELEASED` 已解除 |
| `source` | string | 否 | `MANUAL` 人工、`IMPORT` 导入、`DISPOSITION` 处置联动 |
| `identityType` | string | 否 | `EMAIL` 邮箱、`NATIONALITY_ID` 国籍+证件组合 |
| `countryCode` | string | 否 | ISO 3166-1 alpha-2 国籍代码 |
| `idType` | string | 否 | 现有证件类型枚举值 |
| `keyword` | string | 否 | 邮箱或证件号；按对应规则规范化后匹配 |
| `importBatchNo` | string | 否 | 导入批次号 |
| `createTimeFrom` | date/time | 否 | 加黑时间起始值 |
| `createTimeTo` | date/time | 否 | 加黑时间结束值 |

筛选项可组合使用。前端列表不要展示 `identityValue` 原文；列表数据中的身份项用 `maskedValue` 展示。

### 分页响应示例

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "current": 1,
    "size": 10,
    "total": 1,
    "pages": 1,
    "records": [
      {
        "id": 9988,
        "status": "ACTIVE",
        "source": "IMPORT",
        "remarks": "确认证件买卖，已删除卡片并清退",
        "sourceBusinessType": null,
        "sourceBusinessId": null,
        "importBatchNo": "IMP-20261025-123456789",
        "createdUserId": "admin-id",
        "createdUserName": "风控运营",
        "hitCount": 3,
        "createTime": "2026-10-25T08:00:00Z",
        "releasedUserId": null,
        "releasedUserName": null,
        "releasedTime": null,
        "identities": [
          {
            "id": 12001,
            "identityType": "NATIONALITY_ID",
            "countryCode": "SG",
            "idType": "PASSPORT",
            "maskedValue": "******7A",
            "identityValue": null
          }
        ]
      }
    ]
  }
}
```

Page 字段使用 MyBatis-Plus `Page` 序列化结构，主要读取 `current`、`size`、`total`、`pages`、`records`。
`createdUserId` 和 `releasedUserId` 保留操作人 userId；`createdUserName` 和 `releasedUserName` 是后端按 userId 批量查询得到的昵称。用户不存在或无昵称时名称回退为 userId，系统操作显示为“系统”。`hitCount` 是该名单关联的命中事件总数，前端按名单状态选择操作人：`ACTIVE` 显示加黑人，`RELEASED` 显示解除人。

## 5. 详情及查看身份原文

### 名单详情

`POST /api/admin/natural-person-blacklists/detail` 返回名单及身份维度，身份原文不返回。请求体只需提供 `blacklistId`。

```json
{
  "blacklistId": 9988
}
```

### 小眼睛原文查询

`POST /api/admin/natural-person-blacklists/identity/plaintext`

请求体提供名单 ID 和身份维度 ID：

```json
{
  "blacklistId": 9988,
  "identityId": 12001
}
```

返回对应身份项，包括脱敏展示值和原文 `identityValue`。建议前端按现有私密信息权限控制按钮，仅点击后调用此接口；关闭详情或离开页面时清理前端暂存的明文。

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "id": 12001,
    "identityType": "EMAIL",
    "countryCode": null,
    "idType": null,
    "maskedValue": "a***9@example.com",
    "identityValue": "alice@example.com"
  }
}
```

## 6. 手工新增和解除

### 手工新增

`POST /api/admin/natural-person-blacklists`

邮箱和证件信息至少提供一种。证件信息必须完整提供 `countryCode`、`idType`、`documentNumber`；两种身份可在一条名单中同时填写。`remarks` 最长 255 字符。

```json
{
  "email": "alice@example.com",
  "countryCode": "SG",
  "idType": "PASSPORT",
  "documentNumber": "E1234567A",
  "remarks": "确认身份信息被多个账户复用"
}
```

成功响应 `data` 是新建名单 ID。若邮箱或证件维度已存在于生效名单，返回身份冲突错误。

### 解除单条

`POST /api/admin/natural-person-blacklists/release`

```json
{
  "blacklistId": 9988,
  "remarks": "风险已复核，申请解除"
}
```

`remarks` 可省略，最多 255 字符。成功返回 `data: null`。

### 批量解除

`POST /api/admin/natural-person-blacklists/batch-release`

```json
{
  "ids": [9988, 9991, 9974],
  "remarks": "批量复核后解除"
}
```

`ids` 至少一项，最多 500 项。接口返回逐条结果；前端按每项 `success` 展示成功或失败，不能只依据 HTTP 请求整体成功就认为每条都已解除。

```json
{
  "code": 200,
  "message": "success",
  "data": [
    {
      "id": 9988,
      "success": true,
      "message": "解除成功"
    },
    {
      "id": 9991,
      "success": false,
      "message": "记录不存在或无法解除"
    }
  ]
}
```

## 7. 命中记录和操作日志

### 命中记录

`POST /api/admin/natural-person-blacklists/hits`

这是独立全局分页，不要求指定黑名单 ID。分页和筛选条件放入 JSON body，每个结果项对应一次命中事件中的一个命中名单维度。主要字段如下：

| 字段 | 含义 |
| --- | --- |
| `id` | 命中记录 ID |
| `createTime` | 命中时间，使用命中记录创建时间 |
| `blacklistId` | 命中的黑名单记录 ID |
| `identityType` | 命中身份维度 |
| `maskedValue` | 脱敏后的维度值 |
| `cardholderId` | 持卡人 ID |
| `accountId` | 账户 ID |
| `scene` | 命中业务场景 |

筛选请求示例：

```json
{
  "current": 1,
  "size": 10,
  "hitTimeFrom": "2026-10-01T00:00:00+08:00",
  "hitTimeTo": "2026-10-28T23:59:59+08:00",
  "identityType": "NATIONALITY_ID",
  "identityValue": "1234567",
  "holderOrAccountId": "acc_7890"
}
```

打开命中详情后，通过 `POST /api/admin/natural-person-blacklists/hits/details` 获取对应命中维度的原文。命中记录 ID、名单 ID 和维度都放入 JSON body：

```json
{
  "hitId": 50001,
  "blacklistId": 9988,
  "identityType": "NATIONALITY_ID"
}
```

命中记录本身表示“已拦截”，不单独保存固定结果码。

命中记录保留在数据库中，不在前端自行推断保留期限。

### 操作日志

复用统一 GraphQL `adminOperationLogs`，使用 `recordId = 名单 id` 过滤。日志业务范围包括名单新增、解除、详情/原文查看、导出及命中相关操作；GraphQL 请求体和字段选择按管理端现有日志页面实现复用。

## 8. 批量导入（检查与确认）

### Excel 模板

- 支持 `.xls`、`.xlsx`，最多 5000 条数据行（不含表头）。
- 表头名称必须与下表一致：`邮箱`、`国籍`、`证件类型`、`证件号`、`加黑原因`。
- 每行至少有邮箱或完整证件三项；邮箱和证件可以同时填写。
- 检查阶段逐行检查文件内容、文件内重复和活动名单重复，不写入名单。
- 有问题的行标记失败，其他通过行可以继续确认导入（部分成功）。

| Excel 表头 | 后端字段 | 说明 |
| --- | --- | --- |
| `邮箱` | `email` | 可空；忽略大小写并去除首尾空白 |
| `国籍` | `countryCode` | 可空；有证件信息时必填，有效 ISO alpha-2 代码 |
| `证件类型` | `idType` | 可空；有证件信息时必填，取现有证件类型枚举 |
| `证件号` | `documentNumber` | 可空；有证件信息时必填 |
| `加黑原因` | `remarks` | 说明名单原因 |

### 检查文件

`POST /api/admin/natural-person-blacklists/imports/check`

Content-Type 为 `multipart/form-data`，文件字段名固定为 `file`。检查成功响应中的 `importBatchNo` 要保留，确认导入时原样提交。此批次号用于名单记录追溯；系统当前没有持久化导入批次表，也没有通过批次号重新查询回执的接口。

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "importBatchNo": "IMP-20261025-123456789",
    "totalCount": 2,
    "successCount": 1,
    "failedCount": 1,
    "rows": [
      {
        "rowNo": 1,
        "row": {
          "email": "alice@example.com",
          "countryCode": "SG",
          "idType": "PASSPORT",
          "documentNumber": "E1234567A",
          "remarks": "身份信息重复使用"
        },
        "success": true,
        "message": null,
        "blacklistId": null
      },
      {
        "rowNo": 2,
        "row": {
          "email": null,
          "countryCode": "XX",
          "idType": "PASSPORT",
          "documentNumber": "A123",
          "remarks": "需复核"
        },
        "success": false,
        "message": "身份信息或加黑原因格式不正确",
        "blacklistId": null
      }
    ]
  }

```

### 确认导入

`POST /api/admin/natural-person-blacklists/imports/confirm`

```json
{
  "importBatchNo": "IMP-20261025-123456789",
  "rows": [
    {
      "email": "alice@example.com",
      "countryCode": "SG",
      "idType": "PASSPORT",
      "documentNumber": "E1234567A",
      "remarks": "身份信息重复使用"
    }
  ]
}
```

后端会重新校验并逐行写入，接口同步返回回执。建议前端保留检查接口返回的所有行对象及其顺序，并将这些行连同批次号提交；服务端确认回执的 `rowNo` 按此次提交数组从 1 重新编号。确认接口不支持超时后安全重放：用户确认提交后应禁用重复提交，并在响应未返回时提示先人工核对名单和批次号，再决定后续动作。

成功行的 `blacklistId` 有值，失败行 `success=false` 并带 `message`。确认可能部分成功，前端展示成功数、失败数和逐行错误，并允许导出/下载失败明细；不要因一行失败将整批显示为失败。

## 9. 异步导出

`POST /api/admin/natural-person-blacklists/export`

请求体复用名单查询筛选字段（不需要 `current`、`size` 时可以不传）：

```json
{
  "status": "ACTIVE",
  "source": "IMPORT",
  "importBatchNo": "IMP-20261025-123456789",
  "createTimeFrom": "2026-10-01T00:00:00Z",
  "createTimeTo": "2026-10-25T23:59:59Z"
}
```

接口只返回受理结果 `Result<Void>`，导出是明文名单异步任务。前端按项目既有异步导出通知和文件下载流程提示用户，不等待本接口返回文件内容。导出范围使用当前筛选条件。

## 10. 身份值规范化与重复判断

- 邮箱：去除首尾 Unicode 空白，转小写后校验格式；邮箱匹配不区分大小写。
- 证件号：去除首尾 Unicode 空白，转大写后匹配。
- 国籍：去除首尾 Unicode 空白，转为大写，并校验 ISO 3166-1 alpha-2 代码。
- 证件类型：去除首尾 Unicode 空白，大小写不敏感匹配系统既有 `NamesIdentificationTypeEnum`，保存为枚举规范名。
- 证件唯一身份组合为 `countryCode + idType + documentNumber`；邮箱独立作为另一身份维度。
- 手工新增支持一条记录同时有邮箱和证件；重复校验按各身份维度执行。

## 11. 错误处理

业务错误沿用全局错误响应。黑名单相关错误码如下；错误文案以错误码平台配置及实际响应 `message` 为准：

| 错误码 | 语义 | 前端处理建议 |
| --- | --- | --- |
| `11010101014` | KYC 命中黑名单 | 认证失败；展示统一风险提示，不展示命中身份详情 |
| `11010101015` | 黑名单查询不可用 | 按 fail-closed 处理，提示稍后重试 |
| `11010101016` | 身份信息与生效黑名单冲突 | 表单提示身份已存在，保留输入供检查 |
| `11010101017` | 身份信息格式无效 | 在对应输入项展示校验错误 |
| `11010101018` | 导入文件无效 | 检查文件扩展名、模板表头、内容和 5000 行限制 |
| `11010101019` | 黑名单记录不存在 | 提示记录可能已删除或状态已变化，并刷新列表 |

导入文件中的逐行错误多数通过回执行的 `success=false` 和 `message` 返回，不应全部按全局 HTTP 请求错误处理。

## 12. KYC / SumSub 对接边界（TODO）

- KYC 在 Node 项目进入 SumSub 节点前调用 Node 内部实现：查询黑名单，命中时写入命中记录并拒绝认证；不新增前端调用的跨服务 HTTP 接口。
- 命中用户提示采用统一话术：“认证未通过，证件存在风险”；英文按错误码配置的文案展示。不得向用户暴露名单来源、原因或其他账户信息。
- 数据库查询或命中记录写入失败时按 fail-closed 处理，使用 `11010101015`。
- Node 内的具体调用点、认证来源覆盖范围和字段映射仍需 KYC/SumSub 方案确认；此项不会改变本文件第 2 节所列管理端接口。
