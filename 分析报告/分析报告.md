# 自然人黑名单国家码变更引发持卡人创建失败故障报告

## 一、报告目的

本报告用于还原自然人黑名单国家码格式调整的完整流程、说明持卡人创建接口受影响的原因，并提出流程改进措施。报告用于复盘和改进，不用于追责。

## 二、故障概况

- **故障接口**：生产环境 Open API v3 创建持卡人
- **请求方法**：POST
- **影响表现**：接口返回 HTTP 503
- **业务错误码**：`011040`
- **错误信息**：`Verification is temporarily unavailable. Please try again later.`
- **调用栈定位**：异常发生在 `CardholderBlackListService.checkBlackList`，由 `CardholderOpenApiV3Service.createCardholder` 调用
- **涉及字段**：请求中的 `nationality`，示例值为 `CN`

## 三、事件经过

1. **需求约定为两位码**：自然人黑名单原始需求文档按 ISO alpha-2 两位国家码设计。Admin 黑名单页面国家选项也使用两位码，例如阿尔及利亚显示为 `DZ`；黑名单列表记录中的国家码也显示为 `SG`、`MY` 等两位码。
2. **合规导入三位码失败**：功能上线后，合规使用三位国家码（例如 `DZA`）进行批量导入，导入失败。按原始需求约定，两位码才是黑名单导入格式；但当时这一失败被理解为系统无法支持业务数据格式。
3. **产品反馈持卡人库为三位码**：产品根据持卡人数据库中存储的三位国籍码，判断黑名单也应使用三位码。这里把持卡人数据字段的存储格式与黑名单导入契约混为一谈。
4. **研发调整国家码逻辑**：为尽快解决合规导入问题，研发依据持卡人库的三位码开始调整黑名单国家码逻辑。调整前没有完整核对原始需求、Admin 页面、导入校验、持卡人创建时的黑名单检查以及历史黑名单数据之间的影响。
5. **持卡人创建受影响**：国家码调整波及持卡人创建接口的黑名单检查。创建请求仍可能携带两位码（如 `CN`），而调整后的校验/规范化逻辑按三位码处理，导致黑名单检查抛出异常。该运行时异常被统一转换为业务码 `011040` 和 HTTP 503，最终表现为“验证暂不可用”。

## 四、故障原因

### 直接原因

国家码格式调整改变了黑名单校验所依赖的国家码规范，但持卡人创建入口及相关数据仍使用原有格式。导入链路与在线创建校验链路没有保持相同的规范化契约，导致请求中的两位国籍码无法通过变更后的校验，黑名单预检查失败并使创建接口返回 503。

### 根本原因

国家码在不同业务边界的含义和格式没有明确区分：

- 黑名单管理/导入侧按需求和 Admin 页面使用 ISO alpha-2 两位码；
- 持卡人数据库中已有 ISO alpha-3 三位码；
- 两种格式被当成同一个字段标准，进而根据持卡人表数据修改黑名单规则。

同时，变更前缺少完整的影响范围分析和跨入口回归验证。国家码逻辑被修改后，批量导入问题与持卡人创建校验之间的关联没有在改动前充分识别。

### 错误呈现因素

黑名单服务将运行时异常统一映射为 `011040` / HTTP 503。这个响应没有区分国家码格式校验失败与真正的基础设施不可用，增加了定位成本，也让问题看起来像外部验证服务暂时故障。根据当前调用栈，异常发生在本地黑名单检查阶段；没有证据显示请求已经进入外部 KYC provider。

## 五、影响范围

- 受影响链路包括自然人黑名单国家码导入/校验，以及依赖黑名单预检查的持卡人创建流程。
- 当在线创建请求提供的国家码格式与调整后的黑名单校验规则不一致时，黑名单检查可能失败，进而使持卡人创建返回 503。
- 黑名单记录即使可以按某种格式导入，如果在线创建侧没有规范化到同一格式，也存在无法正确命中的风险。
- 本次创建流程在黑名单检查前已执行持卡人插入。失败后对应记录是否回滚，应根据事务边界及生产数据核实。
- 需确认变更实际发布版本、发布时间、导入成功记录、受影响请求数，以及是否有失败后遗留的持卡人记录，作为最终影响统计依据。

## 六、处理与验证建议

1. 以业务边界统一规范：黑名单管理和导入遵循原始需求及 Admin 页面，采用 ISO alpha-2 两位码；持卡人侧收到或存储的 alpha-3 三位码，在进入黑名单匹配边界时显式转换为 alpha-2。
2. 如果业务确需修改黑名单标准，应将其作为契约变更处理，先明确唯一规范化格式，再同步评估导入、校验、在线匹配、去重、查询、导出、已有数据兼容及历史数据迁移。
3. 为国家码转换补充端到端验证，覆盖：黑名单两位码导入、持卡人三位码转换后成功命中、两位码请求正常校验、未命中路径，以及异常映射路径。
4. 缩小运行时异常到 503 的统一映射范围，保留参数/契约错误的可识别业务错误码，并在日志中记录请求 ID、账户 ID和底层异常原因。
5. 排查故障时间窗口内的 503 请求和持卡人记录，确认实际影响范围及事务回滚结果。

## 七、流程改进

- **先回到需求基线**：线上反馈与原始需求不一致时，先确认是数据录入错误、需求表达不清还是代码缺陷，不直接用某张数据库表的现值替代接口契约。
- **建立字段格式说明**：对“国籍/国家码”注明所属业务、标准（ISO alpha-2 或 alpha-3）、输入格式、存储格式和转换边界，避免不同团队把相同名称理解成同一格式。
- **改动前画清调用链**：国家码等共享字段发生变化时，至少检查后台新增、批量导入、数据库读写、持卡人创建、KYC 预检查、去重查询和导出链路。
- **设置兼容性回归清单**：跨边界格式调整必须验证新旧输入格式、正反向转换和历史数据匹配；必要时先做兼容读取，再分阶段变更存储契约。
- **明确反馈与排期机制**：合规或运营提出紧急问题时，先记录影响和临时方案，再完成最小范围评估与回归，避免时间压力使输入格式问题演变为在线创建故障。

## 八、结论

本次故障由黑名单国家码标准调整引发：原始黑名单需求和 Admin 页面使用两位码，合规按三位码导入失败后，因持卡人数据库存在三位码而推动格式调整；调整没有充分评估持卡人创建链路，导致在线黑名单预检查收到的两位码与新规则不兼容，异常最终被映射为 503。

复盘重点是完善跨业务边界的字段契约、变更影响分析和端到端验证机制，避免相似的格式调整再次影响其他入口。
