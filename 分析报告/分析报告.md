# 账户 b04da43a-0be5-44ae-a5c2-b8e8fdbeecd7 实体卡 Fee 月结为 0 分析

> 分析日期：2026-11-10  
> 涉及项目：qbitpay_service、qbit-assets  
> 交易：00ba26ee-9138-48d4-856b-a5d6bb035fd0  
> 卡片：418e30b2-d42b-4170-916d-52100b7466ab

## 摘要

这笔交易的制卡费配置不是 0：账户 b04da43a-0be5-44ae-a5c2-b8e8fdbeecd7 对应 I2C BIN 45492418 的 API 月结制卡费配置为 **10 USD**。8 月 19 日交易时账户已处于月结，因此即时交易记录为 0 是预期行为；8 月 20 日 sync_caas_month_tx 应按 8 月 19 日原交易时间重算并将 10 USD 写入 API 月结费用记录。

重算返回 0 的直接原因是：请求中的交易时间一路传到了 I2C 费率查询，但 account_fee_item 查不到制卡费配置后回退到旧 accountFee 表时，代码丢弃了请求时间，改用 new Date()。月结判断因此把 T+1 历史交易误判为“当前月结交易”，返回 0，而没有按历史交易走 ApiMonthlyAsync 并匹配 _Caas 费率。

## 交易与配置事实

- api_client_transaction 对应交易 00ba26ee-...，fees 中 cardProductionFee.amount 为 0，状态 Closed。
- qbitCardWalletTransaction 对应记录备注为“制卡费”、businessType = TransferOut、状态 Closed，transactionTime = 2026-08-19 15:34:51.964 +00；金额字段为 0。
- 卡账户是 b04da43a-...，provider 为 I2cCardRecharge45492418，BIN 为 45492418。
- 旧 accountFee 配置中，账户级 QuantumCardMakeCardFeeByApi = 10，以及 QuantumCardMakeCardFeeByApi_Caas = 10，都在交易时间前生效；CAAS 费率行 provider 为 I2c、providerField 为 45492418。
- 通用 QuantumCardMakeCardFee = 12 是非 API 通用费率，不是这笔 API 客户交易应使用的费率。
- 提供的 account_fee_item 导出中没有 QuantumCardMakeCardFee 对应配置，因此运行时会进入旧 accountFee 回退逻辑。
- physical_card_design_relation 中该卡样的两条记录账户 ID 是全零 UUID，不等于卡账户 ID，不能触发 I2C 代码中的“本账户自有卡样免制卡费”分支。

## 跨项目调用链

1. qbit-assets 的 XXL-JOB sync_caas_month_tx 默认同步前一日时间范围，调用 ApiClientTransactionService.syncAccountOtherData。
2. syncAccountOtherData 遍历包括 CARD_PRODUCTION_FEE 在内的月结费用类型，调用 ApiClientTransactionFactory.syncApiTransactions。
3. ApiClientQbitCardWalletTransactionServiceImpl 筛选 Closed、TransferOut、备注包含“制卡费”、交易时间落在任务区间内的钱包流水；对本笔调用 cardProductionFee()。
4. cardProductionFee() 根据卡和实体卡样式选择 API 制卡费类型，并将原始 transactionTime 放入 /bill/month/fee 请求。
5. qbitpay_service 控制器的 QuantumCardMakeCardFeeByApi 分支将 time 传给 qbitCardFactoryService.getMakeCardFee。Factory 原样转发给 I2C，I2C 的 getMakeCardFeeV2 也将该时间格式化后写入 feeInput.time。
6. AccountFeeItemService.getFeeRate() 未命中 account_fee_item 后，调用旧费率回退；这里将时间参数写死为 new Date()，没有使用 feeInput.time。
7. 月结判断将当前批次时间视作当前交易，进入 ApiMonthlyCurrent；该分支会把费率设为 0。于是 /bill/month/fee 返回 0，Java 同步任务将 cardProductionFee=0 写回/更新 api_client_transaction。
8. qbit-assets 月结账单旧来源直接汇总 api_client_transaction.fees[].amount。此记录金额仍为 0；同时未查到对应 account_fee_transaction 月结流水，所以账单最终没有这笔 10 USD。

## 根因

AccountFeeItemService.getFeeRate() 在回退旧 accountFee 时忽略 feeInput.time，导致 T+1 重算使用批次执行时间来判断月结状态。正确分类应基于原始交易时间：对于 8 月 19 日、8 月 20 日之后重算的月结交易，应走 ApiMonthlyAsync，从 QuantumCardMakeCardFeeByApi_Caas 匹配到 10 USD；当前实现却基于 8 月 20 日“现在”走 ApiMonthlyCurrent 并返回 0。

这不是 qbitCardFactoryService.getMakeCardFee(..., time) 或 I2C provider 丢失参数；这两层均有转发 time。丢失发生在 account_fee_item 未命中后的旧费率回退。

## 修复建议

1. 在 AccountFeeItemService.getFeeRate() 的旧表回退调用中，使用 feeInput.time ?? new Date()，并确认后续 getCaasMonthFee 和旧费率查询都使用同一交易时间。
2. 增加回归覆盖：API 月结交易时间为 8 月 19 日，任务执行时间为 8 月 20 日，旧表仅存在 QuantumCardMakeCardFeeByApi_Caas = 10 时，月结重算应返回 10；实时月结交易仍应按当前策略返回 0。
3. 修复后，重跑/补跑该交易所属账期的月结同步，并确认 api_client_transaction.fees 中该交易 cardProductionFee 更新为 10，再重新核对账单及收款记录。
