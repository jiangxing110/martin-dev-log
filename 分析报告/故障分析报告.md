# 自然人黑名单国家码调整引发持卡人创建失败故障分析报告

## 1. 报告说明

本文记录自然人黑名单国家码格式调整及其引发持卡人创建接口失败的过程和原因，供团队复盘改进。分析关注需求、数据契约和变更流程

## 2. 故障摘要

| 项目 | 内容 |
| --- | --- |
| 故障功能 | 自然人黑名单国家码批量导入及持卡人创建黑名单校验 |
| 受影响接口 | 生产环境 Open API v3 创建持卡人 |
| 外部表现 | HTTP 503，业务错误码 `011040` |
| 失败阶段 | 本地黑名单预检查阶段 |
| 请求示例 | `nationality: CN`（两位国家码） |
| 核心原因 | 为支持三位码导入而调整黑名单国家码口径，调整波及在线创建校验；请求值格式与变更后的校验规则不兼容 |

## 3. 背景与原有约定

自然人黑名单原始需求采用 ISO alpha-2 两位国家码。Admin 黑名单页面的国家选项和列表也显示两位码，例如阿尔及利亚为 `DZ`，新加坡为 `SG`，马来西亚为 `MY`。因此，黑名单管理和导入侧的约定是两位码。

与此同时，持卡人数据表中已有 ISO alpha-3 三位国籍码，例如阿尔及利亚为 `DZA`。这是持卡人数据侧的存储格式。两侧格式不同本身并不意味着黑名单需求有误，系统需要在业务边界完成明确的格式转换。

## 4. 事件经过

1. 黑名单按原始需求和 Admin 页面约定，以两位国家码进行录入和批量导入。
2. **合规使用三位码导入失败**：功能上线后，合规使用三位码（如 `DZA`）批量导入，导入失败。按原始需求约定，两位码才是黑名单导入格式，但当时大家首先关注的是业务数据导入失败这一现象。
3. **产品和合规都认为标准应为三位码**：产品和合规都依据持卡人数据中使用三位码的情况，认为黑名单也应使用三位码，并以比较紧急的方式向研发反馈。不同业务环节对“国家码”的实际使用没有形成共同确认的字段格式说明。
4. **周四大发布后的周五处理**：该问题发生在周四大发布后的周五。面对产品和合规一致的三位码判断及紧迫反馈，研发当时认为此前实现或理解可能有问题，优先着手调整国家码逻辑，没有先回到原始需求文档和 Admin 页面核对，也没有完整梳理调用链影响。
5. 国家码调整影响了持卡人创建的黑名单校验。创建请求中的 `nationality` 仍可能是两位码（如 `CN`），与调整后的校验口径不兼容，黑名单预检查抛出异常。
6. `CardholderBlackListService.checkBlackList` 将该运行时异常转换为业务码 `011040` / HTTP 503，对外表现为“Verification is temporarily unavailable”。

## 5. 故障原因分析

### 5.1 直接原因

国家码格式变更没有同时保证批量导入端和在线校验端使用兼容的规范化规则。变更后，持卡人创建请求中的两位国籍码未能通过黑名单校验，导致创建流程在黑名单预检查阶段失败。

### 5.2 根本原因

**业务契约未统一，变更影响分析不足。**

“国籍/国家码”在两个业务边界中指向不同格式：黑名单管理采用两位码，持卡人表使用三位码。排查导入失败时，将持卡人表的格式当作黑名单导入标准，推动了跨模块规则调整，但没有在修改前验证完整调用链。

### 5.3 促成因素

- **页面、需求和数据表的口径没有形成统一说明。** 两位码页面与三位码持卡人数据同时存在，缺少字段级格式约定和转换责任说明。
- **问题分诊环节缺失。** 合规导入失败后，产品和合规带着“三位码才是正确标准”的判断紧急联系研发，但未先由测试依据原始需求、Admin 页面和导入模板复现并判断是代码缺陷、输入格式不符、需求不一致还是历史数据兼容问题，业务判断因此直接进入代码修改环节。
- **紧急反馈与发布节点压缩了分析时间。** 产品和合规都认为应使用三位码，并在周四大发布后的周五紧急反馈。研发因此先怀疑原实现有缺陷并着手修改，未先回到原始需求和 Admin 页面确认，也未先评估该字段被哪些入口和业务使用。这描述的是当时的共同工作情境，不代表对任何一方归责。
- **错误映射隐藏了具体原因。** 黑名单服务将运行时异常统一包装为 503，客户端无法看出是国家码校验不兼容。

## 6. 影响范围

### 已确认

- 至少有一笔生产创建持卡人请求在黑名单检查阶段返回 503，调用栈定位到 `CardholderBlackListService.checkBlackList`。
- 故障发生在调用外部 KYC provider 之前；现有调用栈不支持将其判断为外部验证服务故障。
- 国家码格式调整影响了持卡人创建流程的黑名单检查。

### 需要补充统计

- 变更发布的具体版本和时间窗口。
- 变更窗口内因 `011040` 失败的请求总量和涉及账户数。
- 黑名单三位码导入是否曾成功落库，以及这些记录是否能够被在线检查命中。
- 创建流程在黑名单校验前插入的持卡人记录，异常后是否因事务回滚；如未回滚，是否存在未完成记录。

## 7. 改进措施

### 7.1 问题分诊与字段契约

问题按以下顺序处理，并在每一步留下结论，避免业务反馈未经验证就直接变成代码变更：

1. **反馈受理（合规/业务方）**：提交工单或故障记录，提供导入文件样例、操作步骤、环境/版本、错误提示、预期结果和实际结果。产品和研发可以同步了解，不要求业务方停止沟通。
2. **复现并判断是否为 Bug（测试）**：在对应版本复现问题，并对照已批准的原始需求、Admin 页面和导入模板。测试输出明确结论：代码行为违反现有需求（Bug）；输入不符合现行契约；需求、页面或模板之间不一致；或需要兼容历史数据。未完成这一步，不将“导入失败”直接定性为代码缺陷。
3. **确认业务规则（产品）**：若原始需求、页面、模板和实际使用口径不一致，由产品明确最终标准、适用范围和验收条件。数据库现有值只能作为影响分析依据，不能单独替代业务契约。
4. **分析和实施（研发）**：测试确认存在 Bug，或产品明确需要变更契约后，研发再分析根因和影响链路，列出涉及入口、存量数据、兼容方案及回滚方式，经评估后实施。
5. **回归与验收（测试/产品/业务方）**：测试验证修复及受影响的相邻流程；产品或业务方确认目标规则满足需求；通过后再发布，并记录版本和验证结果。

**进入代码修改的关口：** 先有测试复现/分类结论；如涉及规则变化，还要有产品确认的目标契约和验收标准。紧急故障可并行拉通排查，但永久性代码变更仍需补齐问题分类、影响评估和回归记录。

黑名单国家码口径：

- 黑名单录入和批量导入遵守原始需求及 Admin 页面，使用 ISO alpha-2 两位码。
- 持卡人侧的三位码在进入黑名单匹配边界时转换为两位码。
- 在接口文档、导入模板和后台字段说明中明确输入格式、存储格式及转换位置。

### 7.2 建立格式变更影响检查

共享字段格式发生变更前，列出并检查以下链路：

- Admin 手工新增和编辑；
- 批量导入、重复检查和错误反馈；
- 黑名单存储、查询、去重和导出；
- Open API 创建持卡人及后续 KYC 入口；
- 现有黑名单数据和持卡人历史数据；
- 错误码、事务回滚和失败后记录状态。

### 7.3 加强回归验证

覆盖两位码导入、三位码持卡人输入的边界转换、命中、未命中、无效国家码、导入失败和在线检查异常等主要路径。涉及存量标准改变时，另外制定数据迁移和兼容方案。

### 7.4 改善故障可观测性

区分参数/契约校验失败与数据库、基础设施不可用，不将所有运行时异常折叠为同一个 503。服务端日志保留账户 ID、请求 ID及底层异常原因，便于从错误码追溯具体故障。

## 8. 结论

本次故障的完整因果链为：黑名单原始需求及 Admin 页面使用两位码 → 合规用三位码导入失败 → 持卡人表中的三位码被误当成黑名单统一标准 → 国家码逻辑在缺少端到端影响分析的情况下调整 → 调整波及持卡人创建黑名单校验 → 两位码请求与新校验口径不兼容 → 本地黑名单异常被映射为 `011040` / HTTP 503。

后续应以明确的业务字段契约为依据，在不同数据边界进行受控转换；涉及共享字段的变更必须先完成调用链影响分析和跨入口回归验证。该复盘用于改进协作和变更机制，不用于追责个人。
