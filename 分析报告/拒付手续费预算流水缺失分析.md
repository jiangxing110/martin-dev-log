# 拒付手续费预算流水缺失分析

> 分析日期：2026-11-03  
> 分析对象：商户资金对账中预算余额与资金流水相差 4.00 USD 的问题

## 摘要

对账差额为 **4.00 USD**，对应 **8 笔拒付手续费，每笔 0.50 USD**。这 8 笔已存在于 `public."Transaction"`，交易类型均为 `Declined_Fee`，状态均为 `Closed`；但在 `public."qbit_card_group_transaction"` 中没有对应的预算流水记录。

代码核对发现，预算流水创建监听器依赖交易类型映射生成预算流水，而当前代码的映射表没有 `Declined_Fee`。映射为空时方法会直接返回，因此不会创建预算流水。这是本次差额的代码层根因。

所有缺失交易都能关联到有效、Active 的预算组，因此不是预算组不存在或失效导致。8 笔中，7 笔发生在 2026-09-08；另 1 笔发生在 2026-09-28。后者的单笔事件为何没有落流水，现有查询结果无法还原，需要结合当时应用日志进一步核实。该例外不改变当前代码映射缺失会导致拒付费预算流水被跳过这一结论。

## 一、对账现象

对账单的期初、期末余额差额为 4.00 USD。流水核对结果显示，缺失项是拒付手续费，而不是一笔本金交易：

- 缺失笔数：8 笔。
- 每笔手续费：0.50 USD。
- 缺失合计：8 × 0.50 = **4.00 USD**。
- 交易表：8 笔均存在，类型为 `Declined_Fee`，状态为 `Closed`。
- 预算流水表：8 笔均未查到对应记录。

因此，资金交易本身已经记账；差异出在拒付手续费没有同步形成预算组流水。

## 三、代码原因

交易创建事件处理路径如下：

1. `TransactionEventListener.onTransactionCreate` 对预算卡交易调用 `createQbitCardGroupTransaction`。
2. `createQbitCardGroupTransaction` 根据 `Transaction.type` 查询预算组交易类型映射。
3. 映射结果为空时直接返回，不执行预算流水保存。
4. 当前 `getQbitCardGroupTxMap` 映射了转入、转出、制卡费、撤销、消费、退款等类型，但缺少 `TransactionTypeEnum.Declined_Fee`。

对应代码位置：

- [`TransactionEventListener.java`](/Users/martinjiang/IdeaProjects/qbit-assets/qbit-core/src/main/java/com/qbit/core/vcc/settle/TransactionEventListener.java#L162)：映射为空时提前返回；后续只有通过该分支才会保存预算流水。
- [`TransactionEventListener.java`](/Users/martinjiang/IdeaProjects/qbit-assets/qbit-core/src/main/java/com/qbit/core/vcc/settle/TransactionEventListener.java#L556)：`getQbitCardGroupTxMap` 当前缺少 `Declined_Fee` 映射。
- [`TransactionTypeEnum.java`](/Users/martinjiang/IdeaProjects/qbit-assets/qbit-core/src/main/java/com/qbit/common/enums/TransactionTypeEnum.java#L248)：交易类型 `Declined_Fee` 已定义。
- [`QbitCardTransactionGroupTypeEnum.java`](/Users/martinjiang/IdeaProjects/qbit-assets/qbit-core/src/main/java/com/qbit/common/enums/qbitCard/QbitCardTransactionGroupTypeEnum.java#L32)：预算流水类型 `Declined_Fee` 已定义。

因此，问题不在两种枚举不存在，而在将交易类型转换成预算流水类型的映射遗漏。

## 四、结论与范围

**结论：**本次 4.00 USD 差额表现为 8 笔拒付手续费已进入交易账，但预算组流水未同步记录。当前代码中拒付手续费类型映射缺失，导致该交易事件在预算流水保存前提前结束。

组查询结果已排除“预算组不存在/失效”。缺失的 7 笔集中在 2026-09-08 的“支付部门”组；另 1 笔发生在 2026-09-28 的“Google Cloud AI Assistant”组。后一笔虽然预算组有效，但仅凭静态数据无法确定当时事件是否未投递、监听器处理异常或运行版本差异。需要交易 ID 对应的事件日志才能区分这些运行时原因。

## 五、建议处理

1. 修复映射：将 `TransactionTypeEnum.Declined_Fee` 映射到 `QbitCardTransactionGroupTypeEnum.Declined_Fee`。
2. 增加回归覆盖：验证拒付手续费交易创建后会生成对应的预算组流水，且交易 ID、预算组、余额 ID、手续费一致。
3. 对现存 8 笔做幂等补流水：先确认流水确实不存在，再按交易表中的账户、组、余额、时间、状态和手续费生成记录；不要直接重复插入。
4. 针对 2026-09-28 02:03:56 的交易 `2609281003083057` 查应用事件日志，确认运行时是否出现监听器未执行或处理异常。
5. 修复和补数后重新对账，确认 4.00 USD 差额归零。

## 六、复核 SQL

以下 SQL 可在同一数据库中复现本次交易与预算流水核对结果。关联 "Transaction" 的 UUID 主键与流水表字符型 transactionId 时，统一转为 text，避免 uuid = character varying 报错。

### 6.1 核对交易是否存在预算流水

```sql
SELECT
    t."transactionDisplayId",
    t."id" AS transaction_id,
    t.type AS transaction_type,
    t.status AS transaction_status,
    t."sourceType",
    t."senderBalanceId",
    COALESCE(
        NULLIF(t."senderFee", 0),
        NULLIF(t."recipientFee", 0),
        0
    ) AS tx_fee,
    f."id" AS flow_id,
    f."businessType" AS flow_type,
    f."balanceId" AS flow_balance_id,
    f."groupId",
    f."fee" AS flow_fee,
    f."createTime" AS flow_create_time,
    f."deleteTime" AS flow_delete_time,
    CASE
        WHEN f."id" IS NULL THEN '预算流水缺失'
        WHEN f."fee" = COALESCE(
            NULLIF(t."senderFee", 0),
            NULLIF(t."recipientFee", 0),
            0
        ) THEN '一致'
        ELSE '手续费不一致'
    END AS check_result
FROM public."Transaction" t
LEFT JOIN public."qbit_card_group_transaction" f
    ON f."transactionId" = t."id"::text
   AND f."accountId"::text = t."accountId"::text
WHERE t."transactionDisplayId" IN (
    '2609081032332585',
    '2609081032332588',
    '2609081033332920',
    '2609081033332925',
    '2609081033332930',
    '2609081033332934',
    '2609081033333023',
    '2609151420716968',
    '2609190315427836',
    '2609271734974409',
    '2609281003083057',
    '2609281951177459',
    '2609281951177464',
    '2609290135236726',
    '2609300535465631',
    '2609301550544374'
)
ORDER BY t."transactionDisplayId", f."createTime";
```

### 6.2 核对交易余额关联的预算组

```sql

    t."transactionDisplayId",
    t."accountId",
    t."senderBalanceId",
    g."id" AS group_id,
    g."groupName",
```
