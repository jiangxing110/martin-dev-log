# PD-3056 账户年审提醒测试人员操作手册

**版本日期：** 2026-11-18  
**测试范围：** 新版年审通知、D+15/D+27 重复提醒、冻结日期参数、提交后停止提醒  
**适用环境：** 开发或测试环境

## 1. 测试前准备

1. 确认部署的代码包含以下 GraphQL Mutation：
   `sendAnnualReviewReminders(accountId: String!)`。
2. 使用管理员账号调用测试 Mutation。
3. 准备一个专用测试账户，确认账户有可收邮件地址，并且可查看站内信。
4. 确认测试环境通知模板已存在：
   - 模板名：`Odd_Account_Review_Request_V2`
   - 已配置邮件和站内信
   - 邮件正文中的冻结日期占位符为 `<%freezeDate%>`
5. 确认该测试账户只有一条符合测试条件的 `Processing` 年审 Case，避免一次调用触发多条 Case。

> 此接口会实际发送邮件和站内信。只能在测试环境、专用测试账户上调用，不能用于生产验证。

## 2. 获取测试 Case

先查询测试账户的年审 Case，记录原始 `createTime`，用于测试后恢复：

```sql
SELECT id, "accountId", status, "createTime"
FROM public."oddAccountReview"
WHERE "accountId" = '测试账户UUID'
ORDER BY "createTime" DESC;
```

选一条状态为 `Processing` 的测试 Case，并记下它的 `id`。本手册通过修改这条测试 Case 的 `createTime` 模拟 D+15 和 D+27。

## 3. 调用测试接口

接口按 `accountId` 筛选该账户符合条件的 Case。请求示例：

```graphql
mutation SendAnnualReviewReminder($accountId: String!) {
  sendAnnualReviewReminders(accountId: $accountId)
}
```

Variables：

```json
{
  "accountId": "测试账户UUID"
}
```

接口响应 `true` 只代表调用完成，不代表一定有符合条件的 Case 或通知已送达。每次调用后还要检查测试邮箱、站内信和 `operationLog`。

## 4. 测试 D+15 及冻结日期

将测试 Case 的创建时间改为上海时间当天往前 15 天：

```sql
UPDATE public."oddAccountReview"
SET "createTime" =
  (date_trunc('day', now() AT TIME ZONE 'Asia/Shanghai') - interval '15 days')
  AT TIME ZONE 'Asia/Shanghai'
WHERE id = '测试Case的UUID'
  AND "accountId" = '测试账户UUID'
  AND status = 'Processing';
```

调用第 3 节的 Mutation。预期结果：

- 测试账户收到一封新版年审邮件和一条站内信。
- 邮件中的 `freezeDate` = Case 创建日 + 30 天，也就是测试当天 + 15 天。
- `operationLog` 中该 Case 新增 `AnnualReviewReminderD15` 记录。

以 2026-11-18 为例，模拟的 Case 创建日是 2026-11-03，邮件中的冻结日期应为 **2026-12-03**。

## 5. 验证 D+15 幂等

保持 Case 日期和状态不变，再调用一次 Mutation。预期：

- 不会再次发送 D+15 邮件或站内信。
- 不会重复新增 `AnnualReviewReminderD15` 记录。

代码用既有 `operationLog` 阶段记录防止重复提醒。

## 6. 测试 D+27

将同一条测试 Case 的创建时间改为上海时间当天往前 27 天：

```sql
UPDATE public."oddAccountReview"
SET "createTime" =
  (date_trunc('day', now() AT TIME ZONE 'Asia/Shanghai') - interval '27 days')
  AT TIME ZONE 'Asia/Shanghai'
WHERE id = '测试Case的UUID'
  AND "accountId" = '测试账户UUID'
  AND status = 'Processing';
```

再次调用 Mutation。由于第 4 节已写入 D+15 记录，预期这次只发送 D+27 提醒，并新增 `AnnualReviewReminderD27` 记录。

以 2026-11-18 为例，模拟的 Case 创建日是 2026-10-22，邮件中的冻结日期应为 **2026-11-21**。

如果 D+27 Case 没有 D+15 记录，当前实现会补发尚未记录的 D+15 和 D+27 两个阶段；这是为了补偿定时任务漏跑的情况。

## 7. 验证提交后停止提醒

使用另一条测试 Case，通过正常客户流程提交年审信息，使 Case 不再处于 `Processing`（通常进入 `Pending`）。调用 Mutation 后预期：

- 不发送 D+15 或 D+27 提醒。
- 不新增该阶段的提醒记录。

不要为了这个场景直接修改生产 Case 状态。

## 8. 验证首次触发通知

首次触发通知由正常创建年审 Case 的流程发送，不由本手册中的提醒 Mutation 发送。请在测试环境通过正常年审触发流程创建测试 Case，并检查：

- 通知使用 `Odd_Account_Review_Request_V2`。
- 邮件和站内信均到达测试账户。
- `freezeDate` 为该 Case 创建日 + 30 天。

## 9. 清理与注意事项

- 测试前记录原始 `createTime`；测试结束后恢复，或使用一次性测试 Case。
- 提醒阶段的 `operationLog` 是幂等依据。恢复 `createTime` 不会清除阶段记录；不要删除审计日志来重复测试，重复测试请使用新的测试 Case。
- 日期按上海时区计算。优先使用上面的动态 SQL，不要将示例日期用于其他测试日期。
- 一个账户可能有多条符合条件的 `Processing` Case；Mutation 会处理该账户所有符合时间窗口的 Case。
- `Request` 状态属于补充材料通知场景，不参与 D+15/D+27 未提交提醒。
- `freezeDate` 只作为模板参数显示预计冻结日期；本通知方法本身不执行账户冻结。
